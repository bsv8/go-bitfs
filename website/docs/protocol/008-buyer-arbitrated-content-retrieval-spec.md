# 008 · v4 Buyer arbitrated content retrieval specification

008 completes the 007 custody story with the Buyer pickup path. When Seller
and Buyer cannot reach each other directly but both can reach the Arbiter,
the Seller still custodies the exact payload bundle through Kind 8 and the
Arbiter still signs the paid receipt through Kind 9. The Buyer locates that
custody record with an independently computable `ArbitrationClaimID`, proves
itself with a signature under its own buyer key, and retrieves the exact
Kind 8/9 evidence pair including the precise payload bundle.

This is a one-shot v4 hard switch: Kind 10 and Kind 11 exist only in the
shapes below. There is no legacy decoder, no feature flag, no dual shape, and
no field-presence guessing.

## Wire documents

### Kind 10 · ArbitrationContentRequest (Buyer → Arbiter)

The wire truth is `[4, 10, arbitration_claim_id, retrieval_nonce, buyer_retrieval_signature]`:

```text
ArbitrationContentRequest = [
  4,
  10,
  arbitration_claim_id,
  retrieval_nonce,
  buyer_retrieval_signature
]
```

Constraints:

```text
arbitration_claim_id      = bstr .size 32
retrieval_nonce           = bstr .size 32   ; MUST NOT be all zero
buyer_retrieval_signature = bstr .size (1..256)
```

The request carries nothing else. It does not repeat the Buyer public key,
RefundTemplateTxID, PaymentAuthorizationHash, OpeningProof, TermsCBOR, or
ClaimCBOR: the Arbiter recovers every role key from the stored Claim named by
the Claim ID. The maximum wire size is derived from the subfield limits:
1 array head + 1 version + 1 kind + 34 + 34 + 259 = **330 bytes**.

#### Buyer signing domain

```text
buyer_retrieval_signing_cbor = deterministic-CBOR([
  4,
  10,
  arbitration_claim_id,
  retrieval_nonce
])

buyer_retrieval_signature = SignMessage(BuyerKey, buyer_retrieval_signing_cbor)
```

`SignMessage` is the fixed project semantic: one SHA-256 over the exact
signing CBOR `deterministic-CBOR([4, 10, claim_id, nonce])`, then a low-S DER ECDSA signature. The Buyer never signs the
bare Claim ID bytes, the bare nonce bytes, any string concatenation, hex,
JSON, the complete five-element request, or an arbitration transaction
sighash.

The nonce is generated by the Buyer **application** from a cryptographic
random source and passed explicitly into the SDK. The SDK never generates,
stores, or deduplicates nonces; timestamps, counters, Claim ID prefixes, and
all-zero values are all invalid nonces.

#### Claim ID reuse

The Claim ID algorithm is unchanged from 007:

```text
ArbitrationClaimID = SHA-256(deterministic-CBOR([4, 8, exact_claim_cbor]))
```

Because the ID binds the exact ClaimCBOR — which in turn binds the pool
source context, RefundTx, Buyer-signed exact TermsCBOR, and the ordered
content hashes — the Buyer can compute the identical Claim ID from only its
OpeningProof plus the exact signed 003. No Seller Claim signature, payload,
or Kind 9 is required on the Buyer side.

### Kind 11 · ArbitrationContentResponse (Arbiter → Buyer)

The wire truth is `[4, 11, exact_arbitration_request_cbor, exact_arbitration_response_cbor]`:

```text
ArbitrationContentResponse = [
  4,
  11,
  exact_arbitration_request_cbor,
  exact_arbitration_response_cbor
]
```

Both children are `bstr` embeddings of persisted bytes:

- `exact_arbitration_request_cbor`: the exact canonical Kind 8 saved in the
  arbiter custody store, containing ClaimCBOR, SellerClaimSignature, and
  ContentPayloadsCBOR;
- `exact_arbitration_response_cbor`: the exact canonical Kind 9 persisted in
  the same record, containing the Receipt and ArbiterReceiptSignature whose
  Receipt binds the same Claim ID.

The shell adds **no** new Arbiter signature, because no second source of
truth is created. No third outer signature exists on Kind 11:

```text
SellerClaimSignature    -> exact ClaimCBOR -> Buyer signed TermsCBOR -> ordered content hashes

ArbiterReceiptSignature -> exact ReceiptCBOR -> same Claim ID -> fee + Arbiter transaction signature

ContentPayloadsCBOR[i]  -> SHA-256 -> ordered content hashes[i]
```

The Buyer must verify that entire chain. Kind 11 only returns two already
signed pieces of evidence at once. Payload bytes appear exactly once, inside
the embedded Kind 8. The response does not repeat claim_id,
content_payloads_cbor, receipt_cbor, public keys, OpeningProof, FundingTx,
PaymentAuthorizationHash, or any raw candidate, and it never claims that the
Seller arbitration transaction has been broadcast, mined, or finally settled.

The maximum wire size derives from the current Kind 8/9 limits:

```text
1 array head + 1 version + 1 kind
+ 5-byte bstr head + MaxArbitrationRequestBytes   (16,843,609)
+ 3-byte bstr head + MaxArbitrationResponseBytes  (568)
= 16,844,188 bytes
```

If a future change moves a child limit, this total must be re-derived from
the actual constants and pinned by tests again.

## Verification chain

Reception of Kind 11 is valid only when all of the following pass:

1. strict deterministic decode of Kind 10, then of both embedded documents;
2. Claim ID recomputed from the embedded Kind 8 Claim equals the Kind 10
   Claim ID and the Kind 9 Receipt Claim ID;
3. Buyer/Seller/Arbiter keys recovered from the fixed role order of the
   Claim's pool locking script;
4. Buyer signature over `[4, 10, claim_id, nonce]`;
5. Buyer signature over the exact 003 TermsCBOR;
6. Seller signature over the exact `[4, 8, claim_cbor]`;
7. payload count, order, sizes, canonical child CBOR, and per-item SHA-256;
8. Arbiter signature over the exact `[4, 9, receipt_cbor]`;
9. the Arbiter transaction signature verified over the candidate rebuilt
   with the Receipt fee;
10. the embedded ClaimCBOR byte-for-byte equal to the locally rebuilt expected ClaimCBOR (hash equality alone is insufficient).

Acceptance is time-independent: expired quotes, passed delivery deadlines,
and matured refunds never invalidate already signed custody evidence inside
its retention window. No fake clock or fake block height is involved.

Kind 11 expresses successful retrieval only. NotFound, NotReady,
Unauthorized, NonceReused, Gone, and RateLimited travel on the application
error channel; there is no optional status union inside Kind 11.

## What 008 deliberately does not do

- No buyer arbitration close, fast refund, forced close, buyer+arbiter
  co-signed close transaction, or Seller challenge window exists. If the
  seller never submitted 007 or the record is gone, the buyer waits for the
  seller or broadcasts its presigned RefundTx after `nLockTime`.
- Kind 6 `ContentDelivery` is not reused and `buyer.AcceptDelivery` is not
  called: 008 acceptance returns payloads plus audit data and does not produce a 005 PaymentUpdate; it does not sign any buyer transaction, does
  not modify the previous PaymentState, and does not construct any close
  transaction.
- The Claim ID is not a download token: requests carrying only a Claim ID
  without a valid Buyer signature never receive content.
- The nonce is not encryption and does not replace TLS: production transports
  must provide confidentiality, integrity, and arbiter endpoint identity.
