# 005 最小付款凭证与确定性交易重建一次性硬切换施工单

## 0. 施工性质、覆盖关系与唯一目标态

本施工单把 Kind 7 / 005 累计付款更新一次性硬切换为“授权哈希 + Buyer 交易签名”的最小付款凭证。Buyer 和 Seller 不再在线上传输费用池 ID 或未签名状态交易；双方分别用相同的 003、OpeningProof 和 previous PaymentState 确定性构造同一笔付款状态交易，Buyer 对它签名，Seller 重建后验签、补签并合并。

这是上线前的破坏式协议切换：一次改完、一次验收、一次合并，不分阶段发布，不提供旧/新双写，不保留旧字段 alias、旧构造器、兼容 decoder、自动探测或运行时迁移适配层。协议 major 与 transport family 暂时继续使用 `4` / `bitfs.protocol.v4`；旧五元 v4 005 bytes 必须明确拒绝。

本施工单覆盖 `.david/施工单/2026-08-22/001-003与004批量内容授权交付一次性硬切换施工单.md` 中所有“005 wire 不变”“005 golden bytes 不变”“005 仍显式携带池 ID/未签名交易”的条款。该施工单确定的 003/004 最终结构、批次原子性和 `PaymentAuthorizationHash = SHA-256(003 TermsCBOR)` 继续有效。

如果施工时发现 v4 已被独立外部客户端、持久化队列或生产节点实际使用，必须停止同版本硬切换并升级为新 major/transport family；不得让两个互不兼容的 005 都自称可互操作的 v4。本单继续使用 v4 的前提是项目仍处于允许全体参与方同步替换的上线前阶段。

施工开始前必须记录 `git status --short` 和目标文件 diff 基线，在当前工作树上逐文件修改。不得使用 `git reset --hard`、`git checkout --`、整文件覆盖或清理未跟踪文件来获得“干净起点”，也不得回退与本单无关的用户改动。

最终唯一 wire 真值：

```text
Kind 7 / 005 CumulativePaymentUpdateCBOR = deterministic CBOR([
  4,
  payment_authorization_hash,
  buyer_transaction_signature
])
```

最终 Go wire 类型：

```go
type PaymentUpdate struct {
    Version                   uint64
    PaymentAuthorizationHash  []byte
    BuyerTransactionSignature []byte
}
```

从 `PaymentUpdate` 中彻底删除且不保留 deprecated 字段：

- `RefundTemplateTxID`
- `UnsignedStateTxRaw`

本次不改变：

- 001、002、003、004、006、007 的 wire 数组形状；
- `ContentRequestTerms.RefundTemplateTxID`，它仍是 003 签名条款的一部分；
- OpeningProof、ContentDeliveryState、PaymentState 中费用池身份与本地状态的表达；
- MultisigPool v4 的状态交易构造、三输出顺序、费用、sequence、locktime、sighash 和签名合并规则；
- `pool.UnsignedPayment`、`pool.PaymentUpdateInput`、`pool.PaymentState.RawTx` 等内部/公开交易计算类型；
- 007 仲裁请求中的 `UnsignedStateTxRaw`。007 面向没有 Seller 本地数据库的 Arbiter，必须保持证据自足，不能机械套用 005 的最小信封。

## 1. 缘由简述

### 1.1 `RefundTemplateTxID` 在 005 中是重复关联字段

003 的规范 `TermsCBOR` 已经由 Buyer 签名，并包含：

- `QuoteTermsHash`
- `RefundTemplateTxID`
- 目标 `PaymentSequence`
- 绝对累计 `SellerAmountAfterSat`
- 内容 hashes 与交付截止时间

005 的 `PaymentAuthorizationHash` 唯一等于该 `TermsCBOR` 的 SHA-256。因此 005 再携带一次 `RefundTemplateTxID` 不增加付款授权或密码学约束，只增加第二份可能冲突的路由值。

删除后的准确语义是：应用先用 `PaymentAuthorizationHash` 查回保存的精确原始 003，再从 003 取得 `RefundTemplateTxID`，加载 OpeningProof、previous PaymentState 和 004 后保存的 ContentDeliveryState。Hash 是内容寻址键，不是可逆编码；不得声称能直接“从 hash 解出池 ID”。

### 1.2 `UnsignedStateTxRaw` 不是 RefundTemplate，但可确定性重建

必须区分两笔交易：

- RefundTemplate/RefundTx 是到期退款模板，主要把费用池余额按退款规则返还；
- 005 unsigned state transaction 是本轮累计付款状态，按 `[Buyer, Seller, Arbiter]` 三输出分配金额，并携带本轮 `PaymentSequence`。

二者可以花费同一个费用池来源，但不是同一笔交易，不能互换、替代或复用签名。

005 删除 `UnsignedStateTxRaw` 的真正理由是它已由以下证据唯一决定：

```text
OpeningProof
+ previous PaymentState
+ 003.PaymentSequence
+ 003.SellerAmountAfterSat
+ 固定 MultisigPool v4 构造规则
= exact unsigned payment state transaction
```

Buyer 在验收 004 后用这组输入调用 `BuildPaymentUpdate` 并签名；Seller 收到最小 005 后用同一组输入再次调用 `BuildPaymentUpdate`。只有对 Seller 重建出的精确交易验签成功，005 才成立。

### 1.3 删除派生 bytes 后只有一个状态交易真值

旧 005 同时传递业务授权 hash、发送方提供的交易 bytes，以及可由双方上下文重新构造的交易规则。新设计不再让网络报文提交第二份候选交易表示：

- sequence 和 Seller 累计金额以 Buyer 已签的 003 为业务授权真值；
- 输入 outpoint、三输出、Buyer 余额、Arbiter 零金额、费用和 locktime 以 OpeningProof、previous state 与 MultisigPool v4 为交易真值；
- Buyer 交易签名证明 Buyer 同意这笔确定性重建的交易；
- Seller 不信任报文中的金额或 raw transaction，因为 005 已不携带它们。

## 2. 不能改变或误解的基础规则

### 2.1 Hash 绑定不等于 Hash 可解码

`PaymentAuthorizationHash` 能证明“取回的 003 是否就是被引用的 003”，但不能单独提供 003 内容。应用必须有从 hash 到原始签名 003 及本地上下文的可靠索引。

正确关系：

```text
PaymentAuthorizationHash
  -> application lookup
  -> exact SignedContentRequest / TermsCBOR
  -> recompute SHA-256 and byte-compare
  -> RefundTemplateTxID / target sequence / target seller amount
```

禁止关系：

```text
PaymentAuthorizationHash
  -> 猜测、扫描 payload、读取当前连接隐含 pool、或把 hash 当作 pool ID
```

同一费用池可产生多个不同的 `PaymentAuthorizationHash`；它是一次 003 授权 ID，不是永久池 ID，也不是访问授权令牌。

### 2.2 Buyer 签名域不改变

`BuyerTransactionSignature` 仍是 Buyer 对精确 unsigned payment transaction 的 MultisigPool v4 交易 sighash 签名：

```text
sighash = SHA-256d(BSV transaction preimage), ForkID|All
signature = low-S DER ECDSA over sighash
```

删除 raw transaction 只改变传输，不改变签名对象。不得改成签 `PaymentAuthorizationHash`、003 `TermsCBOR`、005 CBOR、交易 txid、hex 文本或 JSON；不得走普通消息 `SignMessage` 路径造成错误哈希次数。

### 2.3 交易重建必须走唯一核心实现

Buyer 与 Seller 都必须调用现有 `MultisigPoolEngine.BuildPaymentUpdate`，输入固定为：

```go
pool.PaymentUpdateInput{
    Opening:              opening,
    Previous:             previous,
    PaymentSequence:      requestTerms.PaymentSequence,
    SellerAmountAfterSat: requestTerms.SellerAmountAfterSat,
}
```

不得在 Buyer/Seller workflow 各自复制一套手写交易构造，不得从 RefundTx patch 输出，不得接收业务层提供的 Buyer 金额、费用、Arbiter 金额或 raw transaction。任何跨角色、跨语言构造不一致都是协议错误，不能通过“相信 Buyer 原文”降级绕过。

### 2.4 删除范围只限 005 传输容器

- `pool.PaymentUpdate` 不再有池 ID 和 raw transaction。
- `pool.UnsignedPayment` 继续表达内存中的未签名交易，供构造、验签和合并使用。
- `pool.PaymentState.RawTx` 继续保存完整双签交易，供提交、后续状态构造和恢复使用。
- OpeningProof 与 003 继续包含/派生 `RefundTemplateTxID`。
- Seller 的 `ContentDeliveryState` 继续作为“已完成 004 后允许接收哪张 005”的本地角色证据，并与原始 003 交叉核对。
- 007 的 ArbitrationRequest 继续携带完整 OpeningProof、完整 003、unsigned candidate 和 Seller 签名，Arbiter 不依赖 Seller 本地 lookup。

## 3. 最终 API、路由与验证流程

### 3.1 编解码边界

`EncodePaymentUpdate` 只接受最终两项业务字段并编码三元数组。`DecodePaymentUpdate` 只接受 exact 三元数组、major 4、32 字节授权 hash 和非空 Buyer 签名；必须执行 deterministic CBOR 复编码逐字节检查、拒绝尾随数据并返回深复制。

旧五元 v4：

```text
[4, refund_template_txid, payment_authorization_hash,
 unsigned_state_tx_raw, buyer_transaction_signature]
```

旧四元 v3、缺字段、多字段、错误 major、indefinite-length、tag、非规范长度和尾随 bytes 一律返回稳定的无效证据错误。不得按数组长度选择旧 decoder。

### 3.2 应用路由前置条件

Seller 应用接收 Kind 7 后必须：

1. 严格解码三元 005，只取得授权 hash 与 Buyer 签名。
2. 以 `PaymentAuthorizationHash` 精确加载本次保存的原始 `SignedContentRequest` 和 `ContentDeliveryState`。
3. 从原始 003 取得 `RefundTemplateTxID`，再加载对应 OpeningProof 与该池的业务当前 previous PaymentState。
4. 在应用自己的事务/CAS/行锁中保证同一费用池同一时刻只推进一个目标 sequence。
5. 把所有显式证据交给无状态 SDK；SDK 不查询数据库、不扫描池、不持锁。

建议应用唯一索引：

```text
payment_authorization_hash -> {
  exact_signed_003,
  content_delivery_state,
  refund_template_txid,
  processing_status
}
```

`refund_template_txid` 可以作为数据库派生索引保存，但消费时必须与 003 和 OpeningProof 重新比较，不能成为第二授权真值。

### 3.3 Buyer 生成 005

`buyer.Workflow.AcceptDelivery` 的公开参数无需新增：它已经显式收到 request、opening、previous、quote、delivery 和验证输入。完整验收 004 后：

1. 重新计算并验证 `PaymentAuthorizationHash`。
2. 从 003 读取目标 sequence 和绝对累计 Seller 金额。
3. 用 OpeningProof、previous 和目标值调用唯一 `BuildPaymentUpdate`。
4. 用 Buyer 角色交易签名入口签署构造出的 exact unsigned transaction。
5. 本地立即用固定 verifier 回验签名。
6. 只构造 `{Version, PaymentAuthorizationHash, BuyerTransactionSignature}` 返回给应用发送。

构造出的 `UnsignedPayment` 只在本次调用内用于签名与自验，不进入 005 wire。应用如需审计可按自身策略保存它，但不能把该副本重新塞入协议容器。

### 3.4 Seller 接收 005

公开 API 硬切换为显式接收原始 003：

```go
func (workflow *Workflow) AcceptPayment(
    ctx context.Context,
    opening *pool.OpeningProof,
    previous *pool.PaymentState,
    authorization *bitfs.SignedContentRequest,
    deliveryState *ContentDeliveryState,
    update *pool.PaymentUpdate,
    blockHeight uint32,
) (*pool.SignedPayment, error)
```

不保留旧签名 overload、变参兼容、包装 alias 或隐式 Store lookup。应用必须先按 hash 找到原始 003，再显式传入。

固定验收顺序：

1. clone 所有可变输入；结构校验最小 005。
2. 重新计算 `SHA-256(authorization.TermsCBOR)`，与 005 `PaymentAuthorizationHash` 逐字节比较。
3. 用 OpeningProof 的 Buyer 公钥调用 `VerifySignedContentRequestForOpening`，验证精确 003 Buyer 签名。
4. 从 003 取得 `RefundTemplateTxID`，与 OpeningProof 派生 ID、previous.PaymentState、ContentDeliveryState 全部交叉比较。
5. 验证 Seller workflow 私钥属于 OpeningProof Seller，OpeningProof 完整且费用池尚可接受正常 forward payment。
6. 验证 previous 是该 OpeningProof 下的完整已接受或已仲裁状态，不信任调用方只填的序号/金额壳。
7. 验证 `requestTerms.PaymentSequence == previous.PaymentSequence + 1`，且不是最终关闭哨兵。
8. 验证 `ContentDeliveryState.PaymentAuthorizationHash`、目标 sequence、绝对 Seller 金额与 003 完全一致，证明本地确实为这张授权生成过 004。
9. 用 OpeningProof、previous、003 目标 sequence/金额调用唯一 `BuildPaymentUpdate` 重建 unsigned payment。
10. 用固定 Buyer verifier 验证 005 Buyer 签名覆盖重建交易；任何错 opening、错 previous、错金额、错 sequence、错费用或错输出都会导致失败。
11. Seller 对同一重建交易签名，调用唯一 Buyer+Seller merge 入口生成完整 `SignedPayment`。
12. 将授权 hash 写入返回的 `PaymentState.PaymentAuthorizationHash`；SDK 不保存、不广播、不宣布节点接受。

金额永远不是从 005 读取：

```text
003.SellerAmountAfterSat
  == previous.SellerAmountSat + 已验证批次价格
  == reconstructed unsigned output[Seller]
```

### 3.5 API 与基础设施边界

SDK 仍然无状态：按 hash 查询、数据库事务、同池串行化、幂等响应、outbox、广播、超时对账和重试都属于应用。新增 `authorization` 参数是显式协议证据，不是让 SDK 恢复 Store。

SDK 返回完整交易后，应用必须先持久化候选 raw/txid/sequence/auth hash，再按自己的 finality-deferred 节点策略提交。只有节点策略确认后才能推进业务 accepted-payment 记录；构造或验签成功不等于链下池/节点已经接受。

## 4. 明确禁止的实现

- 禁止同时接受旧五元和新三元 v4 005。
- 禁止保留 `PaymentUpdate.RefundTemplateTxID` 或 `PaymentUpdate.UnsignedStateTxRaw` 作为 deprecated/omitempty/仅本地字段。
- 禁止在 wire 外再包一层隐式 pool ID、query parameter、transport header 或 session 字段来偷偷恢复旧设计；若部署层确需路由，必须建立授权 hash 到上下文的应用索引。
- 禁止声称 `UnsignedStateTxRaw == RefundTemplate`，禁止用 OpeningProof 的 RefundTx 直接验 Buyer 005 签名。
- 禁止把 Buyer 交易签名改为对授权 hash 的普通消息签名。
- 禁止仅凭 `PaymentAuthorizationHash` 猜出 003、池、金额或 sequence；找不到原始 003 就不能验收。
- 禁止只信任 ContentDeliveryState 的目标值而不重新验证原始 003；本地状态必须与原始授权交叉核对。
- 禁止从 004 payload、报价价格或数据库累计金额单独构造付款；完整目标已由 003 Buyer 签名确定。
- 禁止 Buyer 与 Seller 分别手写状态交易、修补 outputs、fee、sequence、locktime 或 unlocking script。
- 禁止 Seller 在重建失败时要求 Buyer 重发旧 `UnsignedStateTxRaw` 作为 fallback。
- 禁止把错误 previous 强行改成当前 latest 后继续验同一签名；previous 改变会改变交易和 sighash，应按 stale/乱序处理。
- 禁止从 007 删除候选 raw，禁止修改 006 immediate-close API 或把 005 最小信封套到 006/007。
- 禁止删除 `UnsignedPayment`、`PaymentState.RawTx` 或交易向量；本次只优化 005 transport。
- 禁止用普通广播节点模拟 finality-deferred 替换规则。
- 禁止手改 `website/generated-api`、构建产物或生成的中文 API 页面来掩盖源码/翻译未同步。

## 5. 特殊情况与固定处理

| 特殊情况 | 必须怎么做 | 不能怎么做 |
|---|---|---|
| 收到 005，但找不到 hash 对应的原始 003 | 暂存到有界队列/死信或请求对端重发 003；上下文补齐后重新走完整验证 | 扫描所有池、按连接猜池、只凭签名尝试不同交易直到验过 |
| 找到多个相同 hash、但原始 TermsCBOR 不同 | 视为数据库损坏或安全事件，全部拒绝并告警 | 任取一条、按时间最新或按签名能过的一条继续 |
| 原始 003 hash 与 005 hash 不同 | 拒绝为错误授权引用 | 用 003 中池 ID 覆盖 005 hash |
| 003 池 ID 与 OpeningProof 派生 ID 不同 | 拒绝错池证据 | 改写 003、DeliveryState 或 previous 以凑一致 |
| ContentDeliveryState 缺失 | 不走正常 005；应用可恢复确实持久化过的 004 状态，否则进入人工/业务恢复 | 只凭 003 和 Buyer 签名宣称 Seller 已正常交付并接受付款 |
| same-pool 005 乱序到达，前序仍在处理 | 按池串行化并有界等待；前序完成后重新加载 previous 再判断 | 并行补签两个相同 base 的状态，或跳号接受 |
| 005 是已成功处理的精确重放 | 应用用 auth hash + Buyer signature/业务记录返回已保存结果或幂等状态；SDK 本身仍是纯验证 | 再次推进 sequence、再次记账或生成另一份业务结果 |
| hash 相同但 Buyer 签名不同 | 用重建交易逐一验签；若已有已接受结果，只允许字节一致的业务幂等策略，否则告警/拒绝 | 因 hash 相同就忽略签名差异 |
| previous 已推进，当前授权永久 stale | 拒绝并保留审计证据；是否退款、重购或人工处理由应用决定 | 把授权目标金额/sequence 自动改写到新前态 |
| previous 暂时不可用或数据库超时 | 返回可重试的应用错误，不调用 Seller 签名，不推进状态 | 用空 PaymentState、只填序号金额的伪状态或缓存猜测继续 |
| Buyer/Seller 重建出的 unsigned bytes 不一致 | 硬失败并记录 opening ID、sequence、实现版本和 tx hash；修复确定性构造/依赖版本 | 回退到报文携带 raw、忽略差异或让 Seller 签 Buyer 任意 bytes |
| 费用池在 004 后、005 前已过期 | 正常 005 拒绝；007 同样受未过期边界约束，窗口已过时只能进入退款冲突处理、对账或人工恢复 | 绕过时效检查补签普通 forward payment，或假设过期后仍能发起 007 |
| 旧五元 v4 005 在切换后到达 | 严格 decoder 拒绝，要求发送方升级并重新发送最小 005 | 运行时转换、双 decoder、按长度静默兼容 |
| 切换前队列中仍有旧五元 005 | 上线门禁优先排空；若业务不能丢弃，只能在停机窗口用一次性离线工具验证旧 raw 等于按上下文重建的 raw 后提取 hash+签名，运行时仍只接受新结构 | 未验交易一致性就丢弃 raw 后迁移，或把离线迁移器留在生产 decoder |
| 已存在独立外部 v4 客户端 | 停止同 major 施工，改定 v5/新 family 和明确迁移策略 | 两种不兼容 shape 共用 v4 并依赖试探解析 |
| Seller 已合并交易，但节点提交超时/结果不明 | 先保存完整 raw 与 txid，按 txid/outpoint 对账；确认后再推进 accepted state | 重新构造不同交易、盲目重签或仅凭超时认定失败 |
| 007 仲裁 | 继续使用自足的 OpeningProof + 原始 003 + unsigned candidate + Seller 签名 | 因 005 能重建就要求 Arbiter 查询 Seller 数据库或删除 007 raw |

## 6. 一次性实施顺序与切换门禁

以下顺序只用于降低同一个原子迭代的施工风险，不表示允许分步发布、合并或双栈运行。

1. 冻结施工前同一 fixture 的 OpeningProof、previous PaymentState、003、旧 unsigned payment、Buyer sighash/signature 和最终合并交易，作为“只改传输、不改交易”的对照向量。
2. 更新 `spec/v4/payment.cddl` 和新的 005 golden 测试骨架，固定最终三元 shape，并加入旧五元 v4 拒绝测试。
3. 破坏式收缩 `pool.PaymentUpdate`、CBOR encoder/decoder/validator/clone；删除两个旧字段，不留 alias。
4. 修改 Buyer 004 验收尾部：仍构造/签署/自验 unsigned payment，但只把 hash 与签名放进 005。
5. 修改 Seller `AcceptPayment` API，显式增加原始 003；按固定顺序验证 hash、003、opening、previous、DeliveryState，再本地调用 `BuildPaymentUpdate` 重建、验 Buyer 签名、补签和合并。
6. 同一次提交更新所有调用点、unit/integration/golden/negative tests、demo、CDDL、英文规范、中文翻译和 API 注释。
7. 增加确定性重建回归：Buyer 构造 raw、Seller 独立重建 raw、固定 fixture raw 三者逐字节相等；最终合并交易与施工前对照逐字节相等。
8. 执行全仓静态搜索、Go tests/race/vet、跨语言交易向量和网站生成/构建；检查没有生成噪声和旧字段兼容路径。
9. 切换前确认所有参与方二进制同步升级、旧 005 队列为空、数据库已具备 auth-hash lookup；满足门禁后一次性部署。

任何中间态——例如 Buyer 已发三元 005 而 Seller 仍解析五元、wire 已收缩而 Seller 还读取 raw、Seller 已重建但不验证原始 003、decoder 同时接受两种 v4——都不能提交、发布或作为可工作的分支交付。
