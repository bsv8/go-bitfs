# SDK 安全易用性与显式状态一次性硬切换施工单

## 0. 施工性质、缘由与唯一目标态

本施工单在 **BitFS Wire v1 已经统一且尚未上线** 的前提下，对 Go SDK 做一次不保留旧公开 API 的破坏式硬切换。全部代码、测试、Demo、当前文档和生成文档必须在同一个原子迭代中切换完成；施工顺序只用于控制实现风险，不表示分阶段发布，也不允许任何中间态合并到主分支。

本次改造的唯一目标是：

> 保留无状态、无存储、无网络、无广播副作用的纯协议内核；在其上建立一条角色驱动、exact wire 优先、显式外部事实、受约束签名能力、不可变已验证 checkpoint 和统一错误模型组成的唯一推荐 SDK 路径，使正常用法直接、危险用法困难，同时保证所有 Wire v1 报文、签名预映像和交易语义逐字节兼容。

缘由如下：

1. 当前协议层已经严格，但普通调用方仍需手工串联 `wire.Unmarshal...`、角色 Workflow、ID 派生、状态加载和 `wire.Marshal...`，容易丢失 exact bytes、传错 Kind 或遗漏“先持久化、后发送”；
2. `OpeningProof`、`PaymentState`、Quote、Authorization 等裸对象可被任意组合，公开方法参数过长，SDK 无法在类型层表达“这份状态已经验证到哪一步”；
3. Workflow 直接持有 `*ec.PrivateKey`，会把生产进程锁死在软件私钥，无法安全接入 HSM、KMS、硬件钱包或远程签名服务；
4. 多个公开入口内部读取 `time.Now()`，隐藏了会影响过期判断的外部事实，导致临界点行为难以复放、审计和确定性测试；
5. `bitfs.ErrInvalidEvidence`、`pool.ErrInvalidEvidence` 和普通字符串错误并存，调用方难以稳定区分畸形报文、密码学拒绝、业务前置条件、状态冲突和可重试结果；
6. `github.com/bsv8/go-bitfs/bitfs` 包名重复且职责实际是 001/003/004 内容交易凭证；`arbitration` 同时承载纯证据规则和持有 Arbiter 身份的 Workflow，包边界不够清楚；
7. `CreateQuote(draft, recommendedFilename)` 等入口存在两个同义输入源；部分 `Accept...` 方法实际还会产生新签名或完整交易，名称没有准确暴露副作用；
8. 项目尚未上线，此时一次性清理公开边界的成本远低于上线后长期维护 alias、双 API、双文档和迁移适配器。

本施工单明确取代此前当前施工单中的两项旧决策：

- 废止“Workflow 必须直接持有官方 BSV 私钥、禁止 Signer”的要求，改为 SDK 构造签名 digest、外部 Signer 只执行密钥操作、SDK 固定自验签；
- 废止“公开 API 不接收时间、统一在内部读取系统时钟”的要求，改为影响协议判断的时间与区块高度均由调用方作为显式事实传入。

此前施工单中以下边界继续有效：SDK 不接管 Store、数据库事务、锁、网络、节点广播、内容仓库、重试、对账、业务最新状态和多租户授权；`RefundTemplateTxID`、Wire v1、Kind 1–11、确定性 CBOR、固定签名域和 MultisigPool 交易规则继续作为协议真值。

## 1. 不可突破的兼容边界

### 1.1 必须逐字节保持不变

本次允许 Go 包、类型、方法、错误和本地 checkpoint 发生破坏性变化，但下列协议事实不得变化：

- `protocol.WireVersion == 1`；
- Kind 1–11 的数值、方向和业务含义；
- 每个完整报文的 `[1, wire_kind, ...]` 数组长度、字段顺序、整数值和 bstr 内容；
- 所有独立 `*_cbor` 子文档的 deterministic-CBOR 编码；
- 所有 typed ID 的输入字节与 SHA-256 算法；
- `WireSignatureInput("bitfs/wire-signature", 1, kind, exact_document_cbor)` 的语义；
- low-S DER 要求；
- MultisigPool 的 locking script、输出顺序、金额、手续费、locktime、ForkID|All sighash、签名合并与 raw transaction；
- Kind 11 unavailable/available 分支及 available 的 exact `content_payloads_cbor` attachment；
- CDDL、Wire 文档和既有 golden vectors 表达的全部业务规则。

以下断言必须成立：

```text
旧实现产生的 Kind 1–11 bytes == 新实现产生的 Kind 1–11 bytes
旧实现产生的交易 raw bytes   == 新实现产生的交易 raw bytes
旧实现使用的签名 digest       == 新实现交给 Signer 的 digest
旧实现接受/拒绝的协议证据     == 新实现接受/拒绝的协议证据
```

ECDSA signer 若使用不同但合法的 nonce，DER 签名本身可以不同；兼容比较必须同时覆盖固定测试 signer 下的逐字节相等，以及任意合法 signer 下的 digest、角色、low-S 和验签结果相等。已经产生并准备发送的 exact 报文仍必须原样持久化和重放，不能用“签名仍然有效”代替 exact replay。

### 1.2 明确不触发 Wire 版本变化

- 不新增 WireVersion；
- 不新增 `MultisigVersion`；
- 不在任何 `*_cbor` 子文档内增加 version 或 type；
- 不为本地 checkpoint 增加 wire 字段；
- 不因为 Go API 改名、包移动、Signer 或 Facts 引入而修改 CDDL；
- `spec/v1/wire-messages.cddl` 若非修正文档注释，不应产生结构 diff。

## 2. 最终架构与依赖方向

最终包职责如下：

```text
应用程序
│
├── buyer / seller / arbiter        唯一推荐的角色 API
│   ├── 接收 exact 入站 bytes
│   ├── 严格解析并完成业务验证
│   ├── 调用受约束 Signer
│   ├── 返回 exact 出站 Artifact
│   └── 返回必须由应用保存的不可变 checkpoint
│
├── content / pool / arbitration    高级纯领域 API
│
├── wire                            Wire v1 exact Artifact 与严格分派
│
└── protocol                        共享值类型、Facts、Signer、ID、签名域和错误
```

生产依赖方向只能是：

```text
protocol
  ↑
content      pool
   \         /
    arbitration
       ↑
      wire
       ↑
buyer / seller / arbiter
```

允许角色包同时直接依赖所需领域包。禁止 `protocol`、`content`、`pool`、`arbitration` 反向依赖角色包；禁止 `wire` 依赖角色包；禁止为解决 import cycle 把角色编排重新塞回领域包。

### 2.1 包名硬切换

| 旧位置 | 最终位置 | 最终职责 |
|---|---|---|
| `bitfs/` | `content/` | 001 报价、003 内容/付款授权、004 内容交付的 DTO、编码和纯验证 |
| `arbitration/` 中纯规则 | `arbitration/` | Kind 8–11 DTO、编码、证据链、取回结果与纯验证 |
| `arbitration.Workflow` | `arbiter.Workflow` | 持有 Arbiter 签名能力的 007/008 角色编排 |
| `buyer.Workflow` | `buyer.Workflow` | Buyer 角色 API，构造器与方法硬切换 |
| `seller.Workflow` | `seller.Workflow` | Seller 角色 API，构造器与方法硬切换 |
| `wire.Packet` | `wire.Artifact` | 已严格验证 outer header 和 canonical shape 的 exact bytes |

不保留 `bitfs` 转发包、type alias、deprecated wrapper 或旧 import path；不保留 `arbitration.NewWorkflow`。历史施工单和 `spec/legacy` 可以保留历史名称，但当前 README、代码、Demo、网站和 API 文档只能出现新入口。

## 3. 共享基础 API 最终形态

### 3.1 强类型值

`protocol` 至少提供：

```go
type Hash32 [32]byte
type Digest32 [32]byte
type PublicKey [33]byte
type Satoshis uint64
type BlockHeight uint32
type PaymentSequence uint32
type RetrievalNonce [32]byte

type FileQuoteTermsID [32]byte
type PaymentAuthorizationID [32]byte
type ArbitrationClaimID [32]byte
type ContentRetrievalRequestID [32]byte
type ContentPayloadsID [32]byte
```

要求：

- 所有 byte parser 检查精确长度、压缩公钥有效性和全零哨兵；
- `Bytes()` 返回副本；
- ID 提供 `String`、`Parse...`、`MarshalText`、`UnmarshalText`、`IsZero`；
- 文本 ID 使用稳定类型前缀，至少区分 `fq_`、`pa_`、`ac_`、`cr_`、`cp_`，禁止无类型裸 hex 在日志和通用数据库索引中静默互换；
- 文本编码只属于 SDK/存储便利层，wire 中继续编码原始 32 字节 bstr；
- satoshi、区块高度、付款序号和 Unix 秒不能继续在角色 API 中以含义不明的裸整数出现；领域底层在不改变编码的前提下逐步统一到 named type；
- 不为同一概念在 `content`、`pool` 中再定义第二份不兼容类型。

### 3.2 显式外部事实

```go
// package protocol
type Facts struct {
    Now         time.Time
    BlockHeight BlockHeight
}
```

最终规则：

- 需要过期、deadline 或 refund lock 判断的角色方法必须显式接收 `Facts`；
- 时间无关的证据恢复、exact replay 和 Kind 10/11 事后取回验证不得接收或读取时间；
- `Facts.Now` 在操作需要时间判断时必须非零并规范为 UTC；同一次操作只使用传入的同一个值；
- SDK 只校验当前操作实际需要的 Facts 字段：仅验证 Quote 的操作不应强迫应用查询区块高度；需要高度的操作使用调用方明确给出的 `BlockHeight`。SDK 不读取节点，也不验证高度来源真实性；
- 应用负责同时读取并记录 `Now`、`BlockHeight`、来源和观测时刻；SDK 不接受 `bool Checked` 一类无法证明任何事实的参数；
- 删除 `internal/protoclock`，生产代码中不得再直接调用 `time.Now()`；允许测试代码构造固定事实；
- 不提供隐藏系统时钟的 convenience overload，以免形成两条语义不同的主 API。

### 3.3 受约束签名能力

建议最终接口：

```go
type SigningPurpose uint8

type SigningRequest struct {
    Purpose  SigningPurpose
    WireKind uint16       // 普通 wire 签名使用；交易签名为 0
    Digest   Digest32
}

type Signer interface {
    PublicKey() PublicKey
    Sign(ctx context.Context, request SigningRequest) ([]byte, error)
}
```

必须同时提供软件私钥适配器，例如：

```go
signer, err := protocol.NewPrivateKeySigner(privateKey)
buyerWorkflow, err := buyer.NewWorkflow(signer)
```

Signer 契约：

- SDK 唯一负责构造 wire signature input、SHA-256 digest、交易 preimage 和固定 sighash；
- Signer 只对 SDK 给出的 32 字节 digest 执行 secp256k1 签名，返回不带交易 sighash flag 的 DER；
- `Purpose`/`WireKind` 只供 HSM/KMS 策略审计，不进入或替代既定签名预映像；
- SDK 固定拒绝空签名、畸形 DER、high-S、错误公钥和验签失败；不得提供自定义 Verifier；
- Workflow 构造时固定并验证 `PublicKey()`，任何后续返回签名都必须针对该固定角色公钥自验；Signer 公钥不得在 Workflow 生命周期内变化；
- 交易 sighash flag 的添加、规范化和脚本装配仍由 `pool` 完成，Signer 不能选择 flag；
- context 只用于取消远程签名或长计算；nil context 不得被悄悄换成 `context.Background()`，公开 API 统一拒绝 nil context 或明确约定无 context 的纯函数；
- 不允许遇到 HSM/KMS 故障时自动降级为本地私钥；
- 私钥、seed、WIF、助记词和签名请求原文不得进入错误、日志、wire 或 checkpoint。

### 3.4 统一错误模型

`protocol` 建立仓库唯一稳定错误分类：

```go
type ErrorCode string

const (
    CodeMalformedWire       ErrorCode = "malformed_wire"
    CodeNonCanonical        ErrorCode = "non_canonical"
    CodeUnsupportedVersion  ErrorCode = "unsupported_version"
    CodeUnsupportedKind     ErrorCode = "unsupported_kind"
    CodeInvalidSignature    ErrorCode = "invalid_signature"
    CodeInvalidEvidence     ErrorCode = "invalid_evidence"
    CodeUnauthorized        ErrorCode = "unauthorized"
    CodeExpired             ErrorCode = "expired"
    CodeNotMatured          ErrorCode = "not_matured"
    CodeStateConflict       ErrorCode = "state_conflict"
    CodeInsufficientBalance ErrorCode = "insufficient_balance"
    CodeCanceled            ErrorCode = "canceled"
    CodeSignerUnavailable   ErrorCode = "signer_unavailable"
)

type Error struct {
    Op    string
    Code  ErrorCode
    Kind  uint16
    Field string
    Cause error
}
```

要求：

- 支持 `errors.Is` / `errors.As`，但不再保留 `content.ErrInvalidEvidence`、`pool.ErrInvalidEvidence` 等同义真值；
- parser、signature、evidence、business precondition 和 state conflict 必须可区分；
- 错误字段只能包含安全的路径名和类别，不回显私钥、完整 payload、签名 preimage、raw transaction 或多租户存在性信息；
- 错误字符串用于开发诊断，应用只能依据 code/type 做分支，不能匹配英文或中文文本；
- 一个结构合法且签名有效的 Kind 11 unavailable 是协议结果，不是 transport/parser error；
- 不在 SDK error 中声称某交易“已广播”“已确认”或某状态是数据库最新状态。

## 4. Exact Artifact、解析与验证状态

### 4.1 `wire.Artifact`

最终 `wire` 主入口必须围绕不可变 exact bytes：

```go
type Artifact struct {
    // 字段私有
}

func Parse(raw []byte) (Artifact, error)
func ParseAs(expected Kind, raw []byte) (Artifact, error)
func (a Artifact) Kind() Kind
func (a Artifact) Bytes() []byte
```

`Parse` 必须从 outer `[1, kind, ...]` 自己读取 version/kind，分派到对应严格 decoder，验证完整数组长度、canonical CBOR、attachment 分支和 trailing fields；`ParseAs` 额外验证传输路由声明的 Kind 与报文自描述 Kind 一致。

要求：

- `Artifact` 不能持有调用方可修改的 slice；`Bytes()` 返回副本；
- `Artifact` 只证明 complete wire 的规范结构，不代表签名、金额、身份或业务状态已经验证；
- typed decoder 改为接收 `Artifact` 或由角色 API 内部调用；
- typed encoder 返回 `Artifact`，不再让普通调用方自己组合 Kind 与 `any`；
- 删除 `Marshal(kind, any)` / `Unmarshal(kind, raw) any` 公开主入口，不保留 deprecated wrapper；
- 不通过 Go 反射、全局注册表或 init side effect 实现分派，固定 Kind 使用显式 switch；
- transport route 可以声明期望 Kind，但不能成为唯一 Kind 真值，必须与 outer header 交叉验证。

### 4.2 状态术语

全仓统一以下词义：

```text
Parsed    = outer header、结构与 canonical CBOR 正确
Verified  = 身份、签名、ID、证据链和相关业务约束正确
Prepared  = 已计算出签名/发送候选，但要求应用先持久化
Signed    = 密码学签名已完成并经 SDK 自验
Complete  = 协议所需签名或交易材料完整
Broadcast / Confirmed / Latest = 只能由应用或节点事实声明
```

禁止把 Parse 成功命名为 Verified，禁止把完整签名交易命名成 Confirmed，禁止把调用方传入的 base state 命名成 SDK 认定的 latest state。

## 5. 不可变 verified value 与 checkpoint

### 5.1 原则

底层领域 DTO 继续用于严格编解码，但角色 API 不再把可任意拼装的裸 DTO 作为唯一主路径。角色 API 应返回字段私有、访问器防御性复制的 verified value / checkpoint：

- `content.VerifiedQuote`；
- `pool.VerifiedOpening`；
- `pool.VerifiedPaymentState`；
- `buyer.OpeningCheckpoint`；
- `buyer.PoolCheckpoint`；
- `seller.OpeningCheckpoint`；
- `seller.PoolCheckpoint`；
- `seller.DeliveryCheckpoint`；
- `arbiter.PreparedArbitration`；
- 008 所需的 verified custody/retrieval 结果。

checkpoint 的职责是把本地下一步必须共同使用的证据组合起来，减少 `quote, opening, previous, request, state...` 参数爆炸；它不拥有数据库、锁、租约或网络行为。

### 5.2 持久化与恢复

- 应用持久化 exact wire、raw transaction 和必要本地原始证据；
- SDK 不承诺直接 JSON/CBOR 序列化 checkpoint 私有内存布局；
- 每种跨进程 checkpoint 必须提供显式 `Restore...`，从 exact evidence 重新派生 ID、角色、sequence、金额和签名关系；
- Restore 不信任调用方保存的派生字段，不允许“反序列化后直接设为 verified”；
- checkpoint 不携带 WireVersion 字段，不形成第二套线上协议；
- checkpoint 所有 byte getter 返回副本，禁止验证后外部变异；
- 同一资金池的并发序列化、CAS/high-water、outbox 和 checkpoint 原子保存仍由应用负责。

### 5.3 统一 Result

每个角色公开操作只返回一个具体 Result 和一个 error：

```go
type PrepareOpeningResult struct {
    Outbound   wire.Artifact
    Checkpoint buyer.OpeningCheckpoint
}

type DeliverContentResult struct {
    Outbound   wire.Artifact
    Checkpoint seller.DeliveryCheckpoint
}

type CompletePaymentResult struct {
    Transaction pool.VerifiedSignedTransaction
    NextPool    seller.PoolCheckpoint
}
```

禁止继续返回多个同层结果，例如 `(*Delivery, *State, error)`、`(*UnsignedPayment, []byte, error)` 或 `([]byte, *PaymentState, error)`。Result 字段必须标明：哪些是待发送 exact artifact、哪些必须发送前持久化、哪些是本地 verified state、哪些 raw transaction 仅供应用决定是否广播。

## 6. 角色 API 最终语义

以下方法名是施工目标语义；实施时可以在不降低准确性的前提下微调 Go 名称，但不得保留同义双入口。

### 6.1 Buyer

构造器：

```go
func NewWorkflow(signer protocol.Signer) (*Workflow, error)
```

主流程至少包括：

| 操作 | 输入 | 输出与语义 |
|---|---|---|
| `AcceptQuote(ctx, facts, rawKind1)` | exact Kind 1 bytes | 严格解析、验签、过期判断，返回 `VerifiedQuote` |
| `PreparePoolOpening(ctx, facts, command)` | Quote/资金交易/角色公钥/退款条件 | Kind 2 `Artifact` + 必须先保存的 Buyer opening checkpoint |
| `CompletePoolOpening(ctx, checkpoint, rawKind3)` | 保存的 checkpoint + exact Kind 3 | 验证 Seller 预签，返回 verified opening + initial pool checkpoint |
| `PrepareFundingDelivery(ctx, poolCheckpoint)` | verified opening | Kind 4 `Artifact`；不广播 funding transaction |
| `RequestContent(ctx, facts, command)` | verified quote/pool + hashes/deadline/seed | Kind 5 `Artifact` + Authorization ID/checkpoint |
| `VerifyDeliveryAndPreparePayment(ctx, facts, command)` | pool/request + exact Kind 6 | verified payload + Kind 7 `Artifact` + next payment candidate；名称必须暴露会产生 Buyer 交易签名 |
| `PrepareClose(ctx, facts, command)` | 调用方选择的 base 和目标金额 | unsigned close + Buyer 签名材料；不声称目标是业务最新 |
| `VerifyCompletedClose(ctx, command)` | opening + Seller 完整关闭交易 | verified complete transaction；不声称已广播 |
| `BuildMaturedRefund(ctx, facts, poolCheckpoint)` | opening + 显式事实 | verified refund transaction；不广播 |
| `RequestArbitratedContent(ctx, command)` | opening + exact signed 003 | SDK 默认生成安全 32 字节 nonce，返回 Kind 10 Artifact；提供显式 nonce 的测试/恢复底层入口，但普通 API 不接受任意 `[]byte` |
| `VerifyArbitratedContent(ctx, command)` | 本地 exact Kind 10 + exact Kind 11 + quote/opening/auth | 时间无关地返回 unavailable union 或 verified payload；available 不生成 Kind 7 |

`AcceptQuote` 不再只接收已经 decode 的 DTO；正常应用不需要直接使用 `wire` typed decoder。网络超时重试必须重发已持久化的原 Kind 10，不能重新调用默认 nonce 生成入口。

### 6.2 Seller

构造器同样只接收 `protocol.Signer`。主流程至少包括：

| 操作 | 输入 | 输出与语义 |
|---|---|---|
| `CreateQuote(ctx, facts, QuoteDraft)` | 单一完整 draft | 已签 Kind 1 Artifact + 最终规范化 terms；filename 只能有一个来源 |
| `PreparePoolOpening(ctx, facts, rawKind2)` | exact Kind 2 | Kind 3 Artifact + 必须先保存的 Seller opening checkpoint |
| `VerifyFundingDelivery(ctx, checkpoint, rawKind4)` | 保存的 checkpoint + exact Kind 4 | verified opening/initial pool + 待应用广播的 funding raw；不叫 Accept/Broadcast |
| `DeliverContent(ctx, facts, command)` | verified quote/pool + exact Kind 5 + payload/seed | Kind 6 Artifact + DeliveryCheckpoint；先保存后发送 |
| `CompletePayment(ctx, facts, command)` | pool + exact Kind 5/7 + DeliveryCheckpoint | 验证 Buyer 签名、Seller 补签并合并，返回完整交易和 next pool checkpoint；不声称节点接受 |
| `CompleteClose(ctx, facts, command)` | opening + Buyer unsigned/signature | Seller 补签并返回 complete transaction |
| `PrepareArbitration(ctx, facts, command)` | opening + exact 003/004 | Kind 8 Artifact；不构造 Arbiter 响应 |
| `CompleteArbitratedPayment(ctx, facts, command)` | exact Kind 8/9 +本地证据 | Seller 补签并返回 complete transaction；不广播 |

`CreateQuote` 必须删除独立 `recommendedFilename` 参数。SDK 可以规范化文件名，但必须在返回的最终 terms 中清楚展示实际签署值；不能静默使用两个输入中的一个覆盖另一个。

### 6.3 Arbiter

新增 `arbiter/` 角色包，构造器接收 `protocol.Signer`。主流程至少包括：

| 操作 | 输入 | 输出与语义 |
|---|---|---|
| `PrepareArbitration(ctx, facts, rawKind8, fee)` | exact Kind 8、显式链/时间事实、正仲裁费 | 完整验证但不签名的 opaque `PreparedArbitration`；应用先保存 exact custody |
| `SignPreparedArbitration(ctx, facts, prepared)` | 已持久化 prepared evidence | Kind 9 Artifact；重新验证冻结证据、费用、deadline、角色与 digest 后签名 |
| `AuthenticateRetrieval(ctx, rawKind10, storedKind8)` | exact Kind 10 + stored exact Kind 8 | 仅完成 Buyer 鉴权，用于 not_ready/gone 分支；时间无关 |
| `VerifyRetrievableCustody(ctx, rawKind10, storedKind8, storedKind9)` | 完整托管证据 | verified custody/payload；时间无关 |
| `BuildUnavailableRetrieval(ctx, requestID, reason)` | 结构化 reason | 已签 Kind 11 unavailable Artifact |
| `BuildAvailableRetrieval(ctx, requestID, verifiedCustody)` | verified exact payload | 已签 Kind 11 available Artifact，直接附带 content payloads |

`PreparedArbitration` 字段私有，并提供防御性复制 getter 供应用保存证据；`SignPreparedArbitration` 必须从 frozen exact request 独立重建交易和 digest，不能信任缓存的 mutable candidate。

### 6.4 纯领域 API

`content`、`pool`、`arbitration` 继续提供高级用户和测试所需的 Encode/Decode/Validate/Verify/Build 能力，但统一遵循：

- Encode/Decode 只处理确定性数据格式；
- Verify 处理密码学和证据关系；
- Build 不隐含网络、持久化或业务最新状态；
- 所有签名都经 `protocol.Signer`，所有验签固定在 SDK 内；
- 纯验证方法不接受无用 context；只有可取消的大 payload 计算或远程签名路径接收 context；
- 不出现 `_ context.Context`、内部 `context.Background()` 或为统一外形而加入的无效参数。

## 7. 一次性施工顺序

这是一个原子迭代，以下顺序不能被解释为可分别发布的阶段：

1. 在修改生产代码前冻结 Kind 1–11、普通签名 digest、交易 sighash 和 raw transaction golden manifest；
2. 建立 `protocol` 强类型、Facts、Signer、软件私钥 signer 与统一错误模型；
3. 将 `bitfs/` 一次性迁移为 `content/`，更新全部生产 import，不创建转发包；
4. 将 Arbiter 角色 Workflow 从 `arbitration` 拆到 `arbiter`，保持 `arbitration` 为纯领域包；
5. 重写 `wire` 为 Artifact/Parse/ParseAs/typed codec，删除 `any` 主入口；
6. 把 `pool` 所有签名入口切换为受约束 Signer，把时间/高度判断改成显式 Facts 或显式纯 helper；
7. 定义 verified value、checkpoint、Restore 和统一 Result；
8. 硬切换 Buyer/Seller/Arbiter 全部公开角色 API、方法词义和 Result；
9. 一次性迁移 Demo、integration、CDDL 映射测试、文档测试和安全矩阵；
10. 更新当前 README、完整购买文档、网站 SDK 文档、中英文生成 API 和翻译表；
11. 增加旧 API/旧包/隐藏时间/直接私钥/`any` wire API 的静态禁止检查；
12. 运行全部 golden 差分、单测、race、fuzz smoke、Demo、文档构建和静态搜索，全部通过后才能作为一个提交合并。

施工分支中允许短暂无法编译；主分支、最终提交和任何可供他人依赖的 commit 不允许存在双 API 或半迁移状态。

## 9. 明确不能怎么做

1. 不保留 `bitfs` 转发包、旧 import alias、旧 Workflow 构造器、旧方法 wrapper、deprecated 双 API 或 runtime feature flag。
2. 不用一次性大接口 `Client.DoEverything` 隐藏报价、签名、持久化、发送、广播和确认边界。
3. 不把 Store、Repository、UnitOfWork、Locker、Transport、NodeClient、ContentStore、RetryPolicy 或 Logger 注入协议核心和角色 Workflow。
4. 不让 Signer 提供自定义 hash、preimage、sighash、Verifier、CBOR encoder、价格规则或角色判断；Signer 只执行固定 digest 的密钥操作。
5. 不因远程 Signer 难接入而让 Workflow 同时接受 `Signer` 和 `*ec.PrivateKey`；软件私钥必须通过唯一 local signer 适配器进入。
6. 不保留 `time.Now()` fallback、`Clock` 默认实现、零 Facts 自动补当前时间或高度；外部事实缺失时直接拒绝操作。
7. 不新增本地 checkpoint version 到 wire，不让 checkpoint 直接充当网络报文，不把数据库主键写进协议字段。
8. 不信任反序列化 checkpoint 的派生字段；必须从 exact evidence Restore 并重验。
9. 不把 `Artifact` Parse 成功当成 Verified；不让 `Artifact.Bytes()` 暴露内部 mutable slice。
10. 不保留 `Marshal(kind, any)`、反射分派或调用方自选 Kind + 类型组合的普通路径。
11. 不把 valid Kind 11 unavailable 变成 HTTP 404、普通 error 或 unsigned application response。
12. 不自动生成新 nonce 重试一个已发送 Kind 10；网络不确定时只能重放原 exact Artifact。
13. 不在发送超时后重新签名同一业务报文并覆盖原 outbox；不在广播超时后重建交易或推进本地 confirmed/latest 状态。
14. 不把 complete transaction 命名为 submitted/accepted/confirmed；节点状态只能由应用事实决定。
15. 不通过删除验证来降低参数数量；角色、公钥、ID、sequence、金额、deadline、locktime、payload hash 和 opening ownership 仍必须完整验证。
16. 不借包迁移顺便修改 Kind 1–11 字段、签名范围、价格公式、仲裁费规则、retention 规则或任何协议业务原意。
17. 不为了通用化立即实现 AppKit、数据库 schema 或生产 runtime；这些只有在至少两个真实应用出现相同需求后另立施工单。

## 10. 特殊情况与规定动作

| 特殊情况 | 必须怎么做 | 不能怎么做 |
|---|---|---|
| HSM/KMS 暂时不可用 | 返回 `signer_unavailable`；保持 prepared/checkpoint 不变，按应用策略重试同一操作 | 自动降级到本地私钥、换 key 或跳过自验签 |
| Signer 返回不同公钥对应签名 | 固定返回 `invalid_signature/unauthorized` 并报警 | 更新 Workflow 身份或相信 Signer 自报成功 |
| Signer 超时，不知道是否内部已签 | 若 SDK 未得到签名则没有 outbound；可对同一 prepared 输入重试。得到 Artifact 后必须先持久化再发送 | 假造空响应、推进 checkpoint 或认为对端已收到 |
| Artifact 已生成但持久化失败 | 保留内存中的同一 Artifact 并重试持久化；未持久化前不发送 | 再次签名生成另一份 bytes 后覆盖，或先发送后补库 |
| 发送超时/响应未收完 | 从 outbox 重发同一 exact Artifact | 重新 Build/Sign；Kind 10 不得生成新 nonce |
| 明确收到 Kind 11 not_ready | 应用生成新业务尝试，调用 SDK 创建新 nonce/Kind 10 | 重发旧请求期待结果升级 |
| valid Kind 11 unavailable | 作为已验签 union 返回，应用按 reason 决定新 nonce、等待或终止 | 转为 parser error、unsigned HTTP 404 或产生付款状态 |
| 广播超时/结果不确定 | 先按 canonical txid/outpoint 查询并对账，原 raw 可安全重播时重播 | 重新构造、重新签名、自动推进 confirmed/latest |
| Facts 获取失败或高度/时间过旧 | 不调用需要该事实的 SDK 操作；应用延迟、切换可信源或人工处理 | 填 0、猜高度、用本机时间静默替代 |
| deadline/locktime 恰在操作边界 | 整个调用只使用传入同一份 Facts；签名前重新进入的独立操作必须使用新 Facts | 一次调用中多次读钟得到自相矛盾结果 |
| context 取消 | 立即返回 `canceled`，不得返回部分 verified payload、部分签名 Result | 忽略取消继续调用远程 signer 或把部分结果当成功 |
| 大 payload 验证中失败 | 原子拒绝整批；不产生 Kind 7/11 available | 保存部分块并声称协议验收完成 |
| Restore 发现 checkpoint/evidence 不匹配 | 返回 state conflict/invalid evidence，保留原始证据供审计 | 自动修复 sequence、金额、ID 或选择“看起来更新”的一份 |
| 同一 pool 并发两个操作 | 应用按 RefundTemplateTxID 做事务/CAS/串行化；失败者重新加载后重新计算 | 在 SDK 中加全局 mutex/cache，或让两个 candidate 都变成 latest |
| 未知 Wire version/kind | 返回 unsupported，保留原 bytes供升级/审计 | 猜测旧 shape、fallback 到 v1 其他 Kind、presence guessing |
| 旧 API 调用仍存在 | 编译或 terminology lint 失败，完成全仓迁移后再合并 | 加 alias 让它暂时通过 |
| 文档示例与真实签名不一致 | 以编译测试和真实 Go 签名为准，同时修正文档 | 保留“近似伪代码”作为当前接入真值 |
| 固定 golden 与新实现不一致 | 立即阻断，定位是实现回归还是旧 golden 错误；若主张 golden 错误必须单独给出协议级证据并人工审查 | 在同一 SDK 重构中直接更新 golden 以让测试通过 |

## 11. 测试与审查要求

### 11.1 必须新增的测试层次

1. **Wire golden**：Kind 1–11 exact bytes、子文档 bytes、typed ID、signature digest；
2. **Transaction golden**：opening/refund/payment/close/arbitrated payment 的 preimage、sighash、DER、raw、txid；
3. **Differential**：旧基线 fixture 与新 API 对同一输入产生相同协议结果；
4. **Signer contract**：local signer、fake remote signer、超时、取消、错误 key、high-S、畸形 DER、空签名；
5. **Facts boundary**：过期前一秒、等于 deadline、过期后一秒；height lock 前/等于/后；同一调用单一事实；
6. **Artifact immutability**：修改输入 raw、getter 返回值或 decoded DTO 不得改变内部 exact bytes；
7. **Checkpoint Restore**：成功 round-trip、跨角色错配、ID 错配、sequence 倒退、金额变化、证据被替换；
8. **Error taxonomy**：所有主路径拒绝稳定映射到 code/type，不依赖字符串；
9. **Role end-to-end**：001→002→003/004/005 循环→006，007/009，008 unavailable/available；
10. **Concurrency model**：同 base 的两个候选都可以独立计算，但应用 CAS 只接受一个；SDK 不声称 latest；
11. **Fuzz**：所有 wire parser、独立 child CBOR decoder、ID parser、signature parser 不 panic、不超限分配；
12. **Documentation compile**：README 与网站主示例必须被 Go test 编译执行。

### 11.2 Review 必查点

- 是否存在任何 Wire/transaction byte diff；
- Signer 是否只能接触 SDK 已构造 digest，签名是否全部固定自验；
- 是否还有直接 `*ec.PrivateKey` Workflow、隐藏 `time.Now()` 或 `context.Background()`；
- Parsed/Verified/Prepared/Complete 是否被准确使用；
- Result 是否明确 persist-before-send 和 broadcast boundary；
- checkpoint 是否私有不可变、Restore 是否重验 exact evidence；
- Kind 11 valid unavailable 是否保持签名结果语义；
- `content`/`arbitration`/`arbiter` 依赖是否无循环；
- 当前文档是否只展示一条推荐 API；
- 是否为了迁移方便留下任何旧 alias、wrapper、双 decoder 或 stale generated API。
