# 005 · 累计支付规范

005 是对 003 最终付款授权的正常履行消息。交易模板、费用、序号、输出和签名由 MultisigPool 唯一决定；go-bitfs 只传递授权哈希、原始状态交易和 A 签名。

## 交易规则

所有状态交易花费同一 002 资金输出，固定为 `[server=卖方, A=买方, B=仲裁者]` 2-of-3：

- output[0] 只支付 server，金额为卖方绝对累计金额；
- output[1] 只支付 A，金额为池余额扣除卖方金额和库计算的矿工费；
- 不存在 B 输出、仲裁费输出或第三价值输出；
- 正常累计使用 `server+A`，签名顺序固定为卖方在前、买方在后；
- B 不参与正常 005。

交易构造、整数费率、`SIGHASH_ALL|FORKID`、输入和输出校验全部调用 MultisigPool。go-bitfs 不自行拼脚本、自算费用或重建 sighash。

节点确认交易后，如果本地持久化接受状态失败，服务必须持久化“外部状态待核对”门闩并停止该池的新授权、交付和仲裁提交。只有通过节点重新核对并以相同交易 ID 调用恢复接口后，池才可恢复使用；不能沿用旧本地状态猜测继续。

## 005 CBOR

```text
CumulativePaymentUpdateCBOR = deterministic CBOR([
  version,
  content_request_terms_hash,
  partial_spend_tx_raw
])
```

当前 major 为 `2`。`partial_spend_tx_raw` 必须是同一池的两输出状态交易，输入解锁脚本为空或只含 A 签名；CBOR 不再携带独立金额字段或另一份买方签名真值。卖方用 MultisigPool 验证 A 签名和交易严格匹配 003 后，以 server 签名并按 `server+A` 合并。

节点只有在接受更高序号的非最终状态后，卖方才保存新状态并释放门闩。提交失败、超时或 txid/序号不一致时，本地接受状态不得推进。

## 与仲裁的边界

买方已经签出的 003 授权可以在买方拒签本次 005 时直接进入 007。007 不得要求买方先提供本次 005，也不得把 005 的旧买方签名作为仲裁前提。卖方仲裁交易使用 `server+B`，且不产生仲裁服务费。
