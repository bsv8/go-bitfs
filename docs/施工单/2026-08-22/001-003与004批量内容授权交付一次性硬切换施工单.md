# 003 与 004 批量内容授权/交付一次性硬切换施工单

## 0. 施工性质与唯一目标态

本施工单把 go-bitfs 的 003 内容请求/最终付款授权和 004 内容交付一次性硬切换为“一个付款序号授权一组内容 hash、一个交付包原子交付同一组 payload”的最终结构。

这是上线前的破坏式协议切换：一次改完、一次验收、一次合并，不分阶段发布，不提供旧/新双写，不保留旧字段 alias、旧构造器、旧 decoder 或迁移适配层。协议外壳 major 继续为 `4`；旧 v4 003/004 与新 v4 不兼容，旧 bytes 必须明确拒绝。

本次只改变 003/004 及其直接消费链路，不改变：

- 001 报价的 wire 结构；
- 002 OpeningProof 和 `RefundTemplateTxID` 算法；
- 005、006、007 的外层 wire 数组形状；
- MultisigPool v4 的交易构造、费用算法、角色顺序和交易签名规则；
- `PaymentAuthorizationHash = SHA-256(003 TermsCBOR)` 的定义。

当前工作树已经存在覆盖协议核心、workflow、demo、spec 和 website 的未提交改动。施工开始时必须先保存 `git status --short` 与目标文件 diff 作为基线，逐文件在现状上修改；不得使用 `git reset --hard`、`git checkout --`、整文件回退或批量覆盖来“获得干净起点”，也不得把与本施工单无关的用户改动混入删除清单。

最终唯一 wire 真值如下。

```text
003 SignedContentRequest = [
  4,
  terms_cbor,
  buyer_signature
]

003 terms_cbor = [
  quote_terms_hash,
  refund_template_txid,
  payment_sequence,
  seller_amount_after_sat,
  content_hashes_cbor,
  delivery_deadline_unix
]

004 SignedContentDelivery = [
  4,
  payment_authorization_hash,
  seller_payment_authorization_hash_signature,
  content_payloads_cbor
]
```

`content_hashes_cbor` 和 `content_payloads_cbor` 都是先独立执行 deterministic CBOR 编码、再作为父数组 `bstr` 放入 wire 的子文档。不得把 Go 的嵌套 slice 直接嵌入父数组。

## 1. 缘由简述

旧 003 重复携带 Buyer、Seller、Arbiter 公钥和矿工费率，但这些值已由 `RefundTemplateTxID` 对应且不可修改的 OpeningProof 唯一确定；重复传值只会制造“不一致时相信谁”的第二真值。

旧 `ContentType` 也没有提供独立信息：hash 等于报价 `SeedHash` 时就是 seed，否则必须在该 seed 的 block hash 列表中出现。类型应从证据推导，不能让发送方声明。

旧 003 同时传 `BasePaymentSequence` 和强制等于 `base+1` 的 `PaymentSequenceAfter`。正确的业务含义是“这张授权对应哪一个新付款状态”，所以只传本次目标 `PaymentSequence`；接收方用当前已接受状态验证 `request.PaymentSequence == previous.PaymentSequence + 1`。

旧 003/004 每次只能处理一个内容块。新结构用有序 hash/payload 子文档支持一次购买多个内容，价格逐项计算后安全累加，一次授权、一次交付、一次付款，整个批次原子成功或原子失败。

旧 004 把大 payload 放进 Seller 的签名对象，导致签名预映像、CBOR 编码、复制和持久化都包含大块内容。新 004 只让 Seller 对 32 字节 `PaymentAuthorizationHash` 走固定消息签名路径；payload 放在签名字段之后，并通过 003 已提交的有序 hash 间接绑定。

## 2. 不能改变或误解的基础规则

### 2.1 外壳与内层版本

- 003 外壳 `[4, terms_cbor, buyer_signature]` 必须保留；不得把 `TermsCBOR` 拆平到外壳。
- 003 内层条款固定为 6 元数组，不再携带重复的版本 `4`。
- 004 不再存在单字段 `TermsCBOR` 或 `ContentDeliveryTerms`；外壳本身固定为 4 元数组。
- 004 的外壳版本 `4` 不进入 Seller 签名。当前 decoder 只能接受版本 4；未来版本若改变授权 hash 或交付语义，必须定义新签名规则，不能静默复用本施工单的 v4 裸 hash 签名。

### 2.2 “裸签 PaymentAuthorizationHash”的准确含义

004 Seller 签名固定为：

```text
seller_payment_authorization_hash_signature =
  SignMessage(seller_private_key, payment_authorization_hash)
```

这里的 `SignMessage` 是项目现有的普通消息签名入口：对传入的 32 字节 payload 再做一次 SHA-256，然后生成 low-S DER ECDSA 签名。不得改成交易 sighash 签名，不得签 hash 的 hex 文本，不得额外构造 `[4, hash]` CBOR，也不得对 hash 预先再哈希后又调用 `SignMessage` 造成非约定次数的哈希。

### 2.3 单一真值

- 003 的 `RefundTemplateTxID` 选择费用池，并从 OpeningProof 恢复 Buyer/Seller/Arbiter 公钥和矿工费率。
- 003 的 `QuoteTermsHash` 选择报价；费用池不能替代报价，因为同一个池可以购买同一组角色下不同报价的内容。
- 003 的 `PaymentSequence` 是本次目标付款状态序号，不是 base、内容块下标、请求编号或数据库自增 ID。
- 003 的 `SellerAmountAfterSat` 是付款后 Seller 的绝对累计金额，不是本批增量。批次价格必须等于它减去当前状态的 Seller 金额。
- `PaymentAuthorizationHash` 唯一等于规范 003 `TermsCBOR` 的 SHA-256；不得使用完整 003 外壳、BuyerSignature、004 或 payload 的 hash 替代。
- 004 只携带 `PaymentAuthorizationHash`，不重复携带 `RefundTemplateTxID` 或内容 hashes；接收方必须从保存的原始 003 恢复这些信息。

## 3. 子 CBOR 的唯一编码

### 3.1 ContentHashesCBOR

```text
content_hashes = [1*64 content_hash]
content_hash = bstr .size 32
content_hashes_cbor = bstr .cbor content_hashes
```

Go 公共 helper 固定为下列名称和职责，不得把编码责任推给应用：

```go
const MaxContentBatchItems = 64

func EncodeContentHashes(hashes [][]byte) ([]byte, error)
func DecodeContentHashes(raw []byte) ([][]byte, error)
```

规则：

- 数组长度必须为 1–64；超过 64 时调用方必须拆成多个连续付款序号的 003 批次。
- 每项必须恰好 32 字节。
- 不允许重复 hash；内容按地址购买一次即可复用到文件中所有相同块位置，重复条目不能重复计价。
- 顺序是授权的一部分，不能排序、去重后悄悄接受或按 map 顺序重排。
- nil 与空数组都非法。
- 禁止 indefinite-length、tag、map、非最短整数/长度编码和尾随 CBOR 数据。
- decode 后必须重新 deterministic encode，并与输入逐字节相等。
- 返回值必须深复制，调用方修改输入或返回 slice 不能改变已编码/已验证证据。

### 3.2 ContentPayloadsCBOR

```text
content_payloads = [1*64 content_payload]
content_payload = bstr
content_payloads_cbor = bstr .cbor content_payloads
```

对应 helper：

```go
func EncodeContentPayloads(payloads [][]byte) ([]byte, error)
func DecodeContentPayloads(raw []byte) ([][]byte, error)
```

规则：

- 数组长度必须为 1–64，并在业务验证时严格等于 003 的 hash 数量。
- 每项 payload 必须非空，且不得大于 `masterseed.BlockSize`。
- 顺序必须与 003 hashes 一一对应；不得按 hash 自动重排后接受。
- 子 CBOR 必须规范，decode/re-encode 后逐字节相等，并执行深复制。
- 为避免单个恶意 `bstr` 绕过数组数量限制，固定 `MaxContentPayloadsCBORBytes = MaxContentBatchItems*(masterseed.BlockSize+9)+9`；在解码子数组前先拒绝超过上限的输入。
- 应用/HTTP/MQ 层仍必须设置不高于其可承受能力的 body/message 上限；SDK 的协议上限不是部署层资源配额。

## 4. 003 最终数据模型与验证

### 4.1 Go 类型

`bitfs.ContentRequestTerms` 硬切换为：

```go
type ContentRequestTerms struct {
    QuoteTermsHash       []byte
    RefundTemplateTxID   []byte
    PaymentSequence      uint32
    SellerAmountAfterSat uint64
    ContentHashesCBOR    []byte
    DeliveryDeadlineUnix int64
}

type SignedContentRequest struct {
    TermsCBOR      []byte
    BuyerSignature []byte
}
```

删除且不得保留 deprecated 字段：

- `BasePaymentSequence`
- `PaymentSequenceAfter`
- `MinerFeeRateSatPerKB`
- `BuyerPubkey`
- `SellerPubkey`
- `SelectedArbiterPubkey`
- `ContentType`
- `ContentHash`

同时删除不再准确的 `ContentType`、`ContentSeed`、`ContentBlock` 和带 Type 的 `ContentRef` 公共模型。调用方请求 API 使用 `[][]byte` hashes，SDK 负责生成 `ContentHashesCBOR`。

### 4.2 编码、签名和 hash

```text
terms_cbor = deterministic-CBOR([
  quote_terms_hash,
  refund_template_txid,
  payment_sequence,
  seller_amount_after_sat,
  content_hashes_cbor,
  delivery_deadline_unix
])

buyer_signature = SignMessage(buyer_key, terms_cbor)
payment_authorization_hash = SHA256(terms_cbor)
```

`EncodeContentRequestTerms` 只编码 6 元数组；`DecodeContentRequestTerms` 只接受 6 元数组。旧 13 元、旧 12 元、内层带版本、缺字段、多字段、嵌套原始数组或旧单 hash 一律返回 `ErrInvalidEvidence`。

### 4.3 身份、池和序号验证

由于 003 不再自带 Buyer 公钥，任何密码学验签都必须同时拥有对应 OpeningProof：

1. 从条款取 `RefundTemplateTxID`。
2. 对调用方传入的 OpeningProof 重新派生 `RefundTemplateTxID` 并比较。
3. 验证 OpeningProof 完整性。
4. 用 `OpeningProof.BuyerPubKey` 验证 Buyer 对精确 `TermsCBOR` 的签名。
5. 验证报价 Buyer/Seller 与 OpeningProof Buyer/Seller 相同，OpeningProof Arbiter 在报价白名单内。
6. 验证报价 hash、截止时间和报价有效期。
7. 验证 `request.PaymentSequence == previous.PaymentSequence + 1`；目标不得超过 MultisigPool 当前允许的最大普通付款序号 `0xfffffffe`。
8. 验证 `SellerAmountAfterSat >= previous.SellerAmountSat`，并与聚合价格精确一致。

删除现有 `VerifySignedContentRequestStandalone`。新增 `VerifySignedContentRequestForOpening(request, opening)`，只负责 007 所需的池绑定与 Buyer 签名验证；完整报价/内容验证入口固定为 `VerifySignedContentRequest(request, quote, opening)`，需要 seed membership 时固定为 `VerifySignedContentRequestWithSeed(request, quote, opening, seed)`。007 已携带 OpeningProof，应走 `ForOpening` 路径；不得为了保留旧函数而把公钥重新塞回 003。

### 4.4 自动识别 seed/block 和聚合定价

对每个有序 hash：

- 等于报价 `SeedHash`：识别为 seed，价格为 `SeedPriceSat`。
- 否则：必须在规范 seed 的 block hash 列表中找到，价格按该 block 的协议期望长度计算；完整块用 `FullBlockPriceSat`，尾块沿用现有按比例上取整及 10% Seller 计算规则。
- 找不到：返回 `ErrContentNotInSeed`。

若请求包含任意 block，Buyer 构造 003 时必须提供已经验证且 hash 等于报价 `SeedHash` 的 seed，SDK 不能只相信调用方提供的块大小或类型。若 Buyer 尚未取得 seed，应先单独购买 seed，再构造 block 批次。混合 seed+block 批次仅在 Buyer 已经持有有效 seed 时允许。

同一 block hash 若在 seed 中出现多次，购买一次即可恢复所有相同内容位置，只计价一次。若同一 hash 的多个匹配位置推导出不同期望长度，视为不可消歧的证据冲突并拒绝，不能任选较高或较低价格。

聚合金额必须逐项 checked-add：任意单项计算失败、总价 uint64 溢出、`previous.SellerAmountSat + totalPrice` 溢出或费用池容量不足，都必须在 Buyer 签 003 前失败。不得饱和、截断、跳过异常项或只授权能够支付的前缀。

## 5. 004 最终数据模型与验证

### 5.1 Go 类型与 wire

删除 `ContentDeliveryTerms`、`EncodeContentDeliveryTerms`、`DecodeContentDeliveryTerms` 和 `ContentDeliveryTermsHash`。`SignedContentDelivery` 硬切换为：

```go
type SignedContentDelivery struct {
    PaymentAuthorizationHash                 []byte
    SellerPaymentAuthorizationHashSignature  []byte
    ContentPayloadsCBOR                      []byte
}
```

全仓唯一签名字段名固定为 `SellerPaymentAuthorizationHashSignature`；注释必须明确它签的是精确 32 字节 `PaymentAuthorizationHash`。不得增加短名 alias、兼容 getter 或第二字段。

确定性 CBOR 固定为：

```text
[4,
 payment_authorization_hash,
 seller_payment_authorization_hash_signature,
 content_payloads_cbor]
```

旧 `[4, terms_cbor, seller_signature]`、任何含 `RefundTemplateTxID` 的 004、任何把 payload 放入签名 TermsCBOR 的结构都必须拒绝。

### 5.2 构造与验收顺序

Seller 构造 004 前必须：

1. 完整验证原始 003、报价、OpeningProof 和调用方提供的当前 PaymentState。
2. 重新计算 `PaymentAuthorizationHash`。
3. 解码 003 `ContentHashesCBOR`。
4. 验证 payload 数量、顺序、每项 SHA-256、seed/block 归属、期望长度和聚合价格。
5. 验证 003 的目标序号和累计金额。
6. 用与 `OpeningProof.SellerPubKey` 匹配的 Seller 私钥对精确 32 字节 hash 调用 `SignMessage`。
7. 编码 4 元 004，并返回需要由应用持久化的本地 `ContentDeliveryState`。

Buyer 验收 004 必须：

1. 先按 `PaymentAuthorizationHash` 找到自己保存的精确原始 003；找不到时不得扫描 payload 猜测订单或费用池。
2. 重新计算 003 hash 并逐字节比较。
3. 从 003 取得 `RefundTemplateTxID`，由应用加载 OpeningProof 和当前 PaymentState，再由 SDK 重新派生并验证池归属。
4. 用 `OpeningProof.SellerPubKey` 对精确 32 字节 `PaymentAuthorizationHash` 验证 Seller 签名。
5. 严格解码 `ContentPayloadsCBOR`，逐项验证数量、顺序、hash、seed/block 归属和长度。
6. 重新计算聚合价格、目标序号和绝对累计 Seller 金额。
7. 只有所有项成功，才构造并签署一个 005。

Payload 不直接进入 Seller 签名，但有以下完整绑定链：

```text
BuyerSignature -> 003 TermsCBOR
003 TermsCBOR -> ordered ContentHashesCBOR + pool + sequence + amount
PaymentAuthorizationHash = SHA256(003 TermsCBOR)
SellerSignature -> PaymentAuthorizationHash
ContentPayloadsCBOR[i] -> SHA256 -> ContentHashesCBOR[i]
```

因此不能把“payload 未直接签名”实现成“不校验 payload hash”，也不能只验证其中一项后接受整个批次。

### 5.3 本地状态与 005

`seller.ContentDeliveryState` 固定改为记录目标而不是重复 base/after 词义：

```go
type ContentDeliveryState struct {
    RefundTemplateTxID          pool.RefundTemplateTxID
    PaymentAuthorizationHash   pool.Hash32
    PaymentSequence            uint32
    SellerAmountAfterSat       uint64
}
```

Seller 接收 005 时继续显式接收并验证调用方传入的 previous PaymentState，因此 DeliveryState 不重复保存前态序号或前态 Seller 金额。它必须同时比较：池 ID、授权 hash、目标序号、交易解析出的累计金额、当前前态和买方交易签名。

005 wire 继续携带自己的 `RefundTemplateTxID`，因为 005 是可独立路由的付款更新；本施工单删除的是 004 中可由授权 hash 恢复的重复池 ID，不能顺手删除 005 的字段。

## 6. 特殊情况与固定处理

| 情况 | 必须处理方式 | 禁止行为 |
|---|---|---|
| 004 到达但本地没有原始 003 | 以 `PaymentAuthorizationHash` 暂存/死信，或请求对端重发 003；不进入 SDK 验收/005 | 从 payload、连接或 Seller 自称字段猜池 |
| 003 引用未知池 | 拒绝或等待应用加载对应 OpeningProof | 相信 003 自报公钥/费率；这些字段已删除 |
| 003 `PaymentSequence` 等于当前序号 | 返回 stale sequence | 当成幂等成功并再次交付 |
| 003 `PaymentSequence` 大于当前序号+1 | 返回 stale/out-of-order | 跳号构造付款交易 |
| 同池同目标序号并发收到两个 003 | 应用按 `RefundTemplateTxID` 串行化，只允许一个进入交付；SDK分别验证显式输入 | SDK 内加全局 mutex，或先交付两批再择一付款 |
| hashes 为空、超过 64 或重复 | 整个 003 拒绝 | 自动去重、截断或拆分后继续使用原签名 |
| payload 数量少于/多于 hashes | 整个 004 拒绝，不产生部分付款 | 接受前缀、给缺失项计零价或为多余项付费 |
| 某一 payload hash/长度错误 | 整批拒绝 | 仅丢弃坏项并支付好项 |
| hashes/payloads 顺序不同 | 拒绝 | 接收方自动排序后接受 |
| 只请求 seed | 不要求调用方已有 seed；Seller 交付 payload 的 hash 必须等于报价 SeedHash | 要求显式 ContentType |
| 只请求 blocks | Buyer/Seller/Buyer验收均需可验证 seed | 只凭调用方声明的大小定价 |
| 同批 seed+blocks | Buyer 构造时必须已有有效 seed；交付/验收可复用批次内与 SeedHash 对应的 seed payload，但仍验证其 hash 后才用于 block membership | 先信任未验证 seed 再接受其余块 |
| seed 中同 hash 多次出现 | 请求一次、交付一次、计价一次；文件重建时复用 | 为相同内容地址重复收费 |
| 同 hash 匹配不同期望长度 | 作为证据冲突拒绝 | 任意选择 full/tail 价格 |
| 聚合价格或累计金额溢出 | 返回余额/证据错误，签名前失败 | uint64 回绕、饱和或浮点计算 |
| 报价/交付截止时间已过 | 按一次读取的本地 UTC 拒绝；004 不自带时间 | Seller 自报送达时间覆盖本地验收时间 |
| payload 被篡改但 Seller 签名仍有效 | payload hash 校验失败，整批拒绝 | 因签名有效而忽略内容校验 |
| 同一 004 重发 | 应用按授权 hash 保存并重放同一 wire bytes；Buyer 幂等识别已处理授权 | 重复生成 005 或重复推进付款序号 |
| 进入 007 仲裁 | Arbiter 用 OpeningProof 恢复角色/费率，用 003 验 Buyer 签名和候选序号/金额；不读取 004 payload | 要求 003 再携带公钥、费率或让 Arbiter 重算内容价格 |

004 不能证明 Buyer 在截止时间前实际收到内容；它只证明 Seller 对该付款授权给出了可验证 payload。除非未来增加独立可证明接收机制，007 不裁定网络送达时间或重新计算内容履约事实。

## 7. 一次性实施顺序

以下顺序用于降低施工风险，不代表允许分步发布或合并中间态。

1. 先更新本施工单对应的 CDDL 和新的 golden 向量测试骨架，冻结最终 003/004 shape。
2. 在 `bitfs` 增加 hashes/payloads 子 CBOR helper、批量分类和 checked-add 定价 helper。
3. 破坏式重写 003 类型、编解码、签名和验证；删除所有旧字段、类型和 standalone 自验假设。
4. 破坏式重写 004 类型、编解码和裸授权 hash 签名；删除 DeliveryTerms 层。
5. 同一次变更中重写 Buyer/Seller/Arbitration workflow，使身份、费率全部来自 OpeningProof，序号只使用目标 `PaymentSequence`。
6. 调整 005 接收、本地 DeliveryState 和 007 候选验证，保持 005/007 wire shape 不变。
7. 重写 unit、wire golden、integration、race 和 documented API tests；添加所有旧 shape 拒绝用例。

## 9. 明确禁止的实现

- 禁止同时接受旧 13 元和新 6 元 003 条款。
- 禁止同时接受旧 3 元和新 4 元 004。
- 禁止保留 `ContentType` 并仅在 wire 中忽略它。
- 禁止保留 base 与 after 两套 sequence 字段或用 alias 掩盖语义。
- 禁止让 003 再携带 Buyer/Seller/Arbiter 公钥或 fee rate。
- 禁止让 004 再携带 `RefundTemplateTxID`、`ContentHashesCBOR` 或单独 `ContentHash`。
- 禁止恢复 004 `TermsCBOR`，也禁止签 `[4, payment_authorization_hash]`；Seller 只对精确 32 字节 hash 调用既有 `SignMessage`。
- 禁止签整个 004、`ContentPayloadsCBOR`、payload bytes 或其 hex/JSON 表示。
- 禁止因 payload 不直接入签名而省略逐项 hash/长度/顺序验证。
- 禁止把 hashes/payloads 作为父 CBOR 的原生嵌套数组；必须先规范编码为子 CBOR bstr。
- 禁止应用自行用第三方 CBOR 库生成签名字节；SDK helper 是唯一编码入口。
- 禁止 map/set 导致顺序丢失，禁止隐式排序或自动容错重排。
- 禁止部分交付、部分付款、按前缀接受或单项失败后继续。
- 禁止浮点价格、未检查的 uint64 加法或重复 hash 重复收费。
- 禁止在 SDK 内为并发批次新增 Store、mutex 或 lease；同池串行化仍由应用负责。
- 禁止把 `PaymentAuthorizationHash` 当作访问授权令牌；它只是内容寻址和证据关联 ID。
- 禁止手改生成 API/build 产物来掩盖源码注释或翻译目录不完整。
