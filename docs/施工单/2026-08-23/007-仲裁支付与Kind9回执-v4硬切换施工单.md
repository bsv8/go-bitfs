# 007 仲裁支付与 Kind 9 回执 v4 硬切换施工单

## 1. 施工结论

本次迭代一次性把 go-bitfs 的 007 仲裁路径切换到“仲裁方获得非零费用”的三资金输出交易，并把 Kind 9 从旧的五元 Result 三哈希响应硬切换为四元回执响应。

本次不做分阶段发布、不保留双 decoder、不提供旧字段别名，也不允许调用方在新旧结构之间按长度、字段是否为空或 feature flag 猜测协议版本。代码、CBOR、CDDL、测试向量、集成测试、demo 和中英文当前协议文档必须在同一个变更中同时落地并同时通过验收。

最终 wire 真值如下。

Kind 8 保持不变：

```text
ArbitrationRequest = [
  4,
  8,
  arbitration_claim_cbor,
  seller_claim_signature,
  content_payloads_cbor
]
```

Kind 9 硬切换为：

```text
ArbitrationResponse = [
  4,
  9,
  arbitration_receipt_cbor,
  arbiter_receipt_signature
]
```

内层回执固定为：

```text
ArbitrationReceipt = [
  arbitration_claim_id,
  arbiter_amount_sat,
  arbiter_transaction_signature
]
```

交易资金输出固定为：

```text
output[0] = Buyer P2PKH，金额为扣除 Seller、Arbiter 和既定矿工费后的余额
output[1] = Seller P2PKH，金额为 Buyer 已授权的 SellerAmountAfterSat
output[2] = Arbiter P2PKH，金额为本次回执中的 ArbiterAmountSat
```

本次 007 候选交易仍然必须恰好三个输出；不得为了绑定 Claim 再增加 OP_RETURN，也不得在线上传输 unsigned transaction raw。

## 2. 简述缘由

MultisigPool v4 已经把仲裁池状态升级为 Buyer、Seller、Arbiter 三个固定资金输出，但 go-bitfs 当前 007 builder 和 verifier 仍把第三个输出硬编码为零，因此底层交易具备付费能力，业务协议却无法实际向仲裁方付款。

旧 Kind 9 的 `ArbitrationResult` 同时传输 `request_commitment`、`content_payloads_hash` 和 `unsigned_state_tx_hash`，再附加 Result 消息签名和交易签名。现在已经确认：

- `arbitration_claim_cbor` 内含 Buyer 签名的 `terms_cbor`；
- `terms_cbor` 内含有序 `content_hashes_cbor`；
- 仲裁方在签名前必须逐项验证 exact payload 与这些 hash 匹配；
- Seller 能根据 Claim primitives 和回执金额独立重建同一笔未签名交易；
- `ForkID | All` 交易签名直接绑定三个输出及其金额。

因此不再需要把 payload bundle hash 和 unsigned transaction hash 作为 wire 字段重复发送。新的 Receipt 普通消息签名负责把 Claim、仲裁金额和交易签名绑定在一起；交易签名继续负责授权真实池交易。两种签名职责清晰且不可互换。

## 3. 协议最终真值

### 3.1 Claim ID

协议字段统一命名为 `ArbitrationClaimID`，长度固定为 32 字节。它不是完整 Kind 8 外壳的 hash，也不是 `TermsCBOR` hash。

唯一计算方式为：

```text
seller_claim_signing_cbor = deterministic-CBOR([
  4,
  8,
  exact_arbitration_claim_cbor
])

arbitration_claim_id = SHA-256(seller_claim_signing_cbor)
```

这与当前 `RequestCommitment` 的密码学输入相同，但本次硬切换后必须统一改名为 Claim ID，旧 `RequestCommitment` 命名和公开 getter 不保留兼容别名。

Claim ID 间接绑定：

```text
Claim ID
  -> exact arbitration_claim_cbor
     -> exact terms_cbor
        -> ordered content_hashes_cbor
```

仲裁方仍必须实际接收并验证 `content_payloads_cbor`；“hash 已经存在”不能作为跳过 payload 解码、数量、顺序、大小和逐项 SHA-256 验证的理由。

### 3.2 Receipt 与签名域

`arbitration_receipt_cbor` 是无 version、无 kind 的 deterministic-CBOR 三元子文档：

```text
[
  arbitration_claim_id,          // bstr .size 32
  arbiter_amount_sat,             // uint，成功响应必须 > 0
  arbiter_transaction_signature   // bstr，ForkID | All
]
```

仲裁回执签名域固定为：

```text
arbiter_receipt_signing_cbor = deterministic-CBOR([
  4,
  9,
  exact_arbitration_receipt_cbor
])

arbiter_receipt_signature =
  SignMessage(ArbiterKey, arbiter_receipt_signing_cbor)
```

签名生成顺序必须是：先确定费用并重建 candidate，再生成 `arbiter_transaction_signature`，然后编码 Receipt，最后生成 `arbiter_receipt_signature`。不得先对一个缺少交易签名的半成品 Receipt 签名，也不得签名后修改金额或替换交易签名。

Seller 必须从 Claim 的 role-ordered pool script 恢复 Arbiter 公钥，验证 Receipt 普通消息签名；不得信任传输层声称的发送者身份代替协议验签。

### 3.3 两种签名的职责

`arbiter_receipt_signature` 证明仲裁方认可以下三者的组合：

- 精确 Claim ID；
- 精确仲裁金额；
- 精确的仲裁交易签名字节。

`arbiter_transaction_signature` 是对 Seller 本地重建 candidate 的 `SIGHASH_ALL | SIGHASH_FORKID` 交易签名，绑定 input、sequence、locktime、三个输出脚本和三个输出金额。

不能用 Receipt 签名直接填入 2-of-3 unlocking script，也不能用交易签名冒充对 `[4, 9, receipt_cbor]` 的普通消息签名。

### 3.4 仲裁金额和余额公式

`ArbiterAmountSat` 是本次状态交易分配给 Arbiter 的绝对金额，不是相对上一状态的增量。成功的 Kind 9 必须使用正数；零不能代表免费、拒绝、未报价或“稍后决定”。如将来需要免费仲裁，应另行修改协议，不得在本次实现中留下零值双重语义。

候选交易继续从 Claim 的 refund template 独立构造。退款模板本身仍要求 Seller、Arbiter 输出金额均为零；该约束不能因为 007 支持付费而放宽。

计算必须按无溢出的减法顺序执行：

```text
refund_outputs = refund.output[0] + refund.output[1] + refund.output[2]
refund_fee_sat = pool_output_satoshis - refund_outputs
spendable_sat  = pool_output_satoshis - refund_fee_sat

require seller_amount_after_sat <= spendable_sat
remaining_after_seller = spendable_sat - seller_amount_after_sat

require arbiter_amount_sat > 0
require arbiter_amount_sat <= remaining_after_seller

buyer_amount_sat = remaining_after_seller - arbiter_amount_sat
```

最终必须满足：

```text
BuyerAmountSat
+ SellerAmountAfterSat
+ ArbiterAmountSat
+ RefundFeeSat
= PoolOutputSatoshis
```

当前业务语义是保持 Buyer 已授权的 `SellerAmountAfterSat` 不变，仲裁费作为第三份绝对分配从 Buyer 剩余池余额中扣除。不得在 builder 内暗中把仲裁费从 Seller 金额中相减。若产品以后决定“Seller 承担仲裁费”，必须单独定义 Buyer 授权语义和金额公式，不能复用本次字段后静默改变含义。

### 3.5 收费策略边界

仲裁服务价格属于应用策略，不属于 `pool` 或 `arbitration` SDK 的商业定价逻辑。调用方按精确收到并通过 canonical 校验的：

```text
len(request.ContentPayloadsCBOR)
```

计算 `arbiter_amount_sat`。如果采用阶梯计费，必须使用整数公式，例如：

```text
fee = base_fee_sat + ceil(payload_cbor_bytes / 1024) * sat_per_kib
```

不得使用浮点数；不得一端按 decoded payload 原文总长、另一端按 CBOR 子文档总长；不得按整个 Kind 8 外壳长度或 transport 压缩后的长度计费。

建议的硬切换 API 为：

```go
func (workflow *Workflow) PreparePayment(
    ctx context.Context,
    request *ArbitrationRequest,
    blockHeight uint32,
    arbiterAmountSat uint64,
) (*PreparedPayment, error)
```

由 Arbiter 应用先执行自己的费用策略，再把明确金额传给 SDK。SDK 负责验证金额、余额、证据和交易确定性，不注入 FeePolicy interface，不读取环境变量，不访问报价服务，也不根据 payload 长度自行选择费率。

本次不修改 001、003 或 Kind 8 来携带费率、费用上限或报价单。如果后续产品要求 Buyer 预先签署 `max_arbiter_amount_sat` 或仲裁费率策略 hash，那是另一项签名域和 wire 语义变更，必须另开硬切换施工，不得偷偷塞入现有 `terms_cbor`。

### 3.6 持久化与幂等边界

正确顺序固定为：

```text
接收并严格解码 exact Kind 8
  -> 应用计算 arbiter_amount_sat
  -> PreparePayment(request, blockHeight, arbiter_amount_sat)
  -> 原子持久化 exact Kind 8、Claim ID、费用、payload 与 prepared 审计材料
  -> SignPreparedPayment
  -> 原子持久化 exact canonical Kind 9 bytes
  -> 发送 Kind 9
```

`PreparePayment` 不得产生任何交易签名或 Receipt 签名。`SignPreparedPayment` 必须仅从持久化前已经冻结的 exact request 和 amount 重新验证、重建，不能信任可变缓存里的 decoded Claim、unsigned raw 或金额。

应用以 Claim ID 作为 007 幂等索引，但必须同时保存 exact Kind 8。相同 Claim ID 再次到达时：

- 已经生成并保存 Kind 9：重发完全相同的 canonical response bytes，不重新计价、不重签；
- 只完成 custody 保存而未签名：从保存的 exact Kind 8 和保存的金额重新运行 `PreparePayment`，不得构造 `PreparedPayment` 私有字段；
- 相同 Claim ID 却出现不同 exact Claim bytes：作为冲突或不可实现的 hash collision 处理，停止自动流程并报警，不覆盖原记录；
- 相同 Claim、不同外层 Seller signature 或 payload bundle：重新执行完整验签和 payload 校验；若 exact request 与已保存记录不同，作为重复冲突处理，不静默替换托管证据。

## 4. 必须删除的旧协议面

本次必须彻底删除：

- `ArbitrationResult` 类型；
- `ResultCBOR`；
- `ArbiterResultSignature`；
- `RequestCommitment` 命名；
- `ContentPayloadsHash` getter 和 prepared 缓存；
- `UnsignedStateTxHash` wire/result 绑定与 getter；
- `ValidateResult`、`MarshalResult`、`UnmarshalResult`；
- `ArbiterResultSigningCBOR`；
- 五元 Kind 9 编解码；
- 旧 Result 三哈希 golden bytes；
- 所有声称 Seller 需要验证“三个 Result hash”的当前文档。

可以在 `PreparedPayment` 内部保留仅用于防篡改比较的私有 `preparedEvidenceCommitment`，但不得继续以旧 `UnsignedStateTxHash` 公共协议字段或公共 getter 的形式暴露。这个私有 commitment 必须同时绑定 exact canonical Kind 8 bytes、Claim ID、明确仲裁金额和重建 candidate raw，不能成为第二套 wire 真值。

## 5. 明确不能怎么做

- 不改 Kind 8 的五元外壳、Claim 五元结构或 Seller Claim 签名域。
- 不把 `arbiter_amount_sat` 放进 Kind 8；费用只有 Arbiter 收到并验证 payload 后才确定。
- 不在 Kind 9 继续携带 payload hash、unsigned tx hash、candidate raw、FundingTx raw、OpeningProof 或 previous state。
- 不把 `arbiter_transaction_signature` 命名为 FundingTx signature；它签的是花费 pool output 的仲裁状态交易，不是 FundingTx。
- 不接受 `ArbiterAmountSat == 0` 的成功 007；也不用零作拒绝哨兵。
- 不放宽普通 005 对 Arbiter 金额为零的要求；这次只改变 007。
- 不修改 refund template 的 Seller/Arbiter 初始零金额不变量。
- 不让 Seller 采用 Response 提供的 raw transaction；Response 根本不携带 raw，Seller 必须独立重建。
- 不先生成 Seller transaction signature 再验证 Receipt 和 Arbiter transaction signature。
- 不在 decoder 中尝试旧五元 Kind 9；旧 bytes 必须确定性失败。
- 不保留 `Result` 到 `Receipt` 的兼容 alias、deprecated wrapper 或按字段为空回退。
- 不让 SDK 查询节点、计算商业费率、写数据库、广播交易或暗示交易已上链。
- 不通过修改 `vendor/` 或本地 module cache 修补 MultisigPool；go-bitfs 必须只调用已经发布的 MultisigPool v4 三输出 API。

## 6. 特殊情况与既定处理

| 特殊情况 | 必须处理方式 |
|---|---|
| `arbiter_amount_sat == 0` | `PreparePayment` 立即返回 invalid evidence；不持久化成功 prepared，不产生任何签名，不发送 Kind 9。 |
| Seller 金额本身已超过 spendable | 返回 `pool.ErrInsufficientBalance`；不能通过削减 Seller 金额自动修复。 |
| Seller 金额合法但剩余余额不足以支付仲裁费 | 返回 `pool.ErrInsufficientBalance`；不产生免费或部分收费响应。 |
| 金额加法可能溢出 | 使用先比较后减法；任何溢出风险按 invalid evidence 拒绝，禁止 `uint64` 回绕。 |
| Buyer 输出恰好为零 | 只要三个固定输出仍存在、金额公式成立且底层 MultisigPool 接受，就视为合法边界；不得删除 Buyer 输出。 |
| 费用策略计算溢出、服务不可用或不能报价 | 应用在调用 `PreparePayment` 前失败；SDK 不猜默认费率。 |
| payload 任一项 hash、数量、顺序、大小或 canonical CBOR 不符 | 在计入 custody 成功和签名前拒绝整个请求；不能只删掉坏项继续仲裁。 |
| delivery deadline 在 Prepare 前已到 | Prepare 拒绝。 |
| deadline 在持久化间隙内到期 | `SignPreparedPayment` 重新检查并拒绝；已持久化证据保留为失败审计记录。 |
| refund 已达到不可仲裁高度 | Prepare 和 Seller completion 都拒绝，不签名、不广播。 |
| Claim 指定了另一个 Arbiter 公钥 | 在生成任何签名前拒绝。 |
| Claim 的 source amount/script 与真实链上 UTXO 不一致 | SDK 只能按离线 Claim 算术拒绝或构造；生产应用必须在签名前自行查节点核对 outpoint、金额、script、确认和 unspent。查不到或不一致时停止签名并进入人工/重试对账。 |
| UTXO 查询超时或结果不确定 | 不把“不确定”当作可花费；不产生新签名。保存状态后重试查询。 |
| Kind 9 Receipt 签名损坏 | Seller 拒绝，绝不继续验签合并或补签。 |
| Receipt 金额被篡改 | Receipt 普通消息签名失败；Seller 拒绝。 |
| Receipt 内交易签名被替换 | Receipt 签名或交易验签失败；Seller 拒绝。 |
| Claim ID 被替换 | Receipt 签名或 Seller 本地 Claim ID 比对失败；Seller 拒绝。 |
| 收到旧五元 Kind 9 | strict decoder 返回 unsupported shape/invalid evidence；不得迁移、猜测或降级。 |
| Kind 9 已保存但发送失败 | 重发 exact saved bytes；不得因当前费率变化重新计价或重签。 |
| Seller 已合并但广播结果未知 | 先保存 signed raw 和 canonical txid，再按 outpoint/txid 对账；不得生成另一金额的竞争响应作为普通重试。 |
| 链上 outpoint 已花费 | 不广播或停止重播，记录冲突交易并进入应用对账；SDK 不宣称可恢复。 |
| hash collision 或同 Claim ID 不同 exact Claim | 停止自动处理并报警；绝不覆盖已经托管和签署的记录。 |

Kind 9 只表达成功响应。本次不为拒绝新增 Kind 9 union/status 字段。余额不足、过期、证据错误、无法报价和链上异常均通过应用错误通道返回；不得发送结构合法但不可执行的“拒绝 Kind 9”。如果将来需要可转交验证的已签名拒绝回执，应设计独立 kind 或独立固定结构。

## 7. 文件级施工清单

以下项目属于一个不可拆分的提交面。顺序是实现依赖顺序，不是允许分批发布的阶段。

### 7.1 资金池构造与验证

#### `pool/arbitration.go`

- 把 `BuildArbitrationPaymentFromClaim` 改为显式接收 `arbiterAmountSat uint64`。
- 保持 source、refund template、role script、sequence、locktime 和三个固定输出验证。
- 保持 refund template 的 `output[1] == 0`、`output[2] == 0`。
- 按第 3.4 节公式计算 Buyer 余额，设置 candidate `output[2] = arbiterAmountSat`。
- 返回的 `UnsignedPayment.ArbiterAmountSat` 必须等于 caller 明确传入的金额。
- `validateArbitrationUnsignedPayment` 删除“Arbiter 金额必须为零”，改为成功 007 必须为正，并继续逐字段核对 raw transaction 与 metadata。
- `arbitrationCandidateCommitment` 继续绑定 `ArbiterAmountSat`；确认 clone/rebuild 时该字段不会丢失。
- 为 Claim 的纯结构验证拆出不依赖成功仲裁费的结构验证入口；因 `arbitration` 包需要跨包复用该验证，它以公开纯函数 `pool.ValidateArbitrationClaimStructure(poolOutputSatoshis, poolOutputLockingScript, refundTemplateRaw, paymentSequence, sellerAmountAfterSat) error` 交付（2026-08-23 验收修订：本条原写"内部 helper"，实施时确认跨包复用必须导出；该函数只做结构校验、无签名无副作用，作为公开 API 承担后续兼容性责任，并已登记进 SDK 文档与翻译目录）。不得为了复用 builder 而传入假的 `1 sat`，也不得让公开成功 builder 接受零金额。

#### `pool/types.go`

- 更新 `UnsignedPayment`、`PaymentState` 中 `ArbiterAmountSat` 的注释，明确普通 005 为零、007 为正且都是绝对金额。
- 不新增重复的 arbitration fee 字段；交易真值继续只有 `ArbiterAmountSat`。

#### `pool/errors.go`

- 余额不足继续统一使用 `pool.ErrInsufficientBalance`，确保 `errors.Is` 可匹配。
- 零金额、错误 output/metadata、非 canonical evidence 继续归入 `pool.ErrInvalidEvidence`；除非调用方确有分支需求，否则不新增同义 sentinel。

#### `pool/multisigpool_test.go`

- 更新所有 `BuildArbitrationPaymentFromClaim` 调用。
- 新增正费用 candidate，断言三个 output 的脚本、金额、metadata 和公式。
- 覆盖 `1 sat`、恰好耗尽 Buyer 余额、余额差 `1 sat` 不足、零费用、超大费用、错误第三输出 metadata、篡改第三输出 raw 等边界。
- 证明 Seller/Arbiter 两个 detached signature 都绑定第三输出金额；金额加一或减一后旧签名必须失败。
- 保持并证明普通 005 仍拒绝非零 Arbiter 金额。

#### `pool/shared_fixture_test.go`、`pool/testdata/arbitrated_pool_v4_fixture.json`

- 底层官方 fixture 若已覆盖非零 Arbiter 输出则保留并确认通过；只有 go-bitfs 007 golden 改变时不得无理由重写官方共享 fixture。
- 若当前 fixture 的断言被 007 helper API 变化影响，只改调用和断言，不改第三方协议既有真值。

### 7.2 Arbitration wire、Receipt 与两段式签名

#### `arbitration/workflow.go`

- 删除旧 `ArbitrationResult` 及其全部 marshal/validate/signing API。
- 新增：

```go
type ArbitrationReceipt struct {
    ClaimID                     []byte
    ArbiterAmountSat            uint64
    ArbiterTransactionSignature []byte
}

type ArbitrationResponse struct {
    Version                 uint64
    ReceiptCBOR             []byte
    ArbiterReceiptSignature []byte
}
```

- 新增并只保留以下协议函数：

```go
func ArbitrationClaimID(claimCBOR []byte) ([]byte, error)
func ValidateReceipt(receipt *ArbitrationReceipt) error
func MarshalReceipt(receipt *ArbitrationReceipt) ([]byte, error)
func UnmarshalReceipt(raw []byte) (*ArbitrationReceipt, error)
func ArbiterReceiptSigningCBOR(receiptCBOR []byte) ([]byte, error)
```

- `ArbitrationClaimID` 必须复用精确 Seller Claim signing domain `[4,8,claim_cbor]` 后做 SHA-256，不直接 hash Go struct，不 hash完整 Kind 8。

## 10. 完成定义

只有当代码、规范、wire、golden、集成、demo、中英文当前文档和生成检查在同一提交状态下全部满足第 9 节，才算本次硬切换完成。

- 新 Kind 9 能编码但 Seller 仍按旧 Result 验证；
- 交易第三输出已付费但 Receipt 没有绑定该交易签名；

本施工单本身不是分阶段迁移计划；实施时可以按文件依赖顺序开发，但最终只能以完整硬切换结果交付。
