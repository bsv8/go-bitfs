# 007 仲裁托管与独立交易重建一次性硬切换施工单

## 0. 施工性质、覆盖关系与唯一目标态

本施工单把 Kind 8 / Kind 9 / 007 一次性硬切换为“Seller 提交签名证据与内容、Arbiter 验证并托管内容、Arbiter 从证据独立确定性构造付款交易、Seller 收到结果后独立重建并补签”的最终协议。

这是上线前的破坏式协议切换：一次改完、一次验收、一次合并，不分阶段发布，不提供旧/新双写，不保留旧字段 alias、兼容 decoder、自动探测、运行时转换或迁移适配层。协议 major 暂时继续使用 `4`，但旧六元 v4 007 request、旧五元 v4 007 response 必须严格拒绝。

本施工单覆盖以下既有结论中所有与新 007 冲突的内容：

- `.david/施工单/2026-08-22/002-005最小付款凭证与确定性交易重建一次性硬切换施工单.md` 中“007 必须携带 OpeningProof、unsigned candidate 和 Seller transaction signature”“不能从 007 删除 candidate raw”的条款；
- `docs/protocol/wire-messages.zh.md` 与 website 007 文档中“Arbiter 只验证 Seller 构造的候选交易，不构造交易”“007 不读取 payload”“007 请求携带完整 OpeningProof”的条款；
- 当前 `spec/v4/arbitration.cddl`、`arbitration/workflow.go` 与所有测试中冻结的旧 v4 007 数组结构。

本施工单不回退已经确定的 003/004/005 规则：

- `terms_cbor` 仍是 Buyer 签名的六元 003 条款；
- `PaymentAuthorizationHash = SHA-256(terms_cbor)`；
- `content_hashes_cbor` 与 `content_payloads_cbor` 仍是规范、有序、1–64 项的 deterministic CBOR 子文档；
- 004 正常直连交付仍是 `[4, payment_authorization_hash, seller_payment_authorization_hash_signature, content_payloads_cbor]`；
- 005 正常付款仍是 `[4, payment_authorization_hash, buyer_transaction_signature]`；
- MultisigPool 仍使用 `[Buyer, Seller, Arbiter]` 固定角色顺序、三输出、`ArbiterAmount = 0` 和 `ForkID|All` 交易签名。

如果施工时发现旧 v4 007 已被独立外部客户端、生产服务、持久化队列或不可同步升级的节点实际使用，必须停止同 major 硬切换，改定新 major/transport family 并制定显式迁移方案；不得让两套互不兼容的 007 都自称 v4。

施工开始前必须记录 `git status --short` 与目标文件 diff 基线，在当前工作树上逐文件修改。不得使用 `git reset --hard`、`git checkout --`、整文件回退、清理未跟踪文件或覆盖用户现有改动来获得“干净起点”。

### 0.1 最终 Kind 8 唯一 wire 真值

```text
ArbitrationRequest = [
  4,
  8,
  arbitration_claim_cbor,
  seller_claim_signature,
  content_payloads_cbor
]
```

`arbitration_claim_cbor` 是独立 deterministic CBOR 子文档，作为 `bstr` 嵌入外壳：

```text
ArbitrationClaim = [
  pool_output_satoshis,
  pool_output_locking_script,
  refund_template_raw,
  terms_cbor,
  buyer_signature
]
```

内层 Claim 不携带版本和类型；版本 `4` 与类型 `8` 只在外层出现一次。Seller 的消息签名必须绑定外层版本、类型和精确 Claim bytes：

```text
seller_claim_signing_cbor = deterministic-CBOR([
  4,
  8,
  arbitration_claim_cbor
])

seller_claim_signature =
  SignMessage(seller_private_key, seller_claim_signing_cbor)
```

`SignMessage` 沿用项目固定语义：对精确 payload 做一次 SHA-256，再输出 low-S DER ECDSA 签名。不得签 Claim hash、hex、JSON、完整 request、payload 原文或交易 sighash来替代上述签名域。

### 0.2 最终 Kind 9 唯一 wire 真值

为使“Arbiter 已接收并托管精确 payload”与“Arbiter 已签署精确付款交易”都能被独立验证，Kind 9 对称硬切换为：

```text
ArbitrationResponse = [
  4,
  9,
  arbitration_result_cbor,
  arbiter_result_signature,
  arbiter_transaction_signature
]
```

```text
ArbitrationResult = [
  request_commitment,
  content_payloads_hash,
  unsigned_state_tx_hash
]
```

```text
request_commitment = SHA-256(seller_claim_signing_cbor)
content_payloads_hash = SHA-256(content_payloads_cbor)
unsigned_state_tx_hash = SHA-256(exact_unsigned_state_tx_raw)

arbiter_result_signing_cbor = deterministic-CBOR([
  4,
  9,
  arbitration_result_cbor
])

arbiter_result_signature =
  SignMessage(arbiter_private_key, arbiter_result_signing_cbor)
```

`arbiter_transaction_signature` 仍是 Arbiter 对精确 unsigned state transaction 的 `ForkID|All` 交易签名，格式为 `low-S DER || sighash byte`。它不能代替 `arbiter_result_signature`：交易签名不提交 payload custody hash；result 消息签名也不能代替可合并上链的交易签名。

## 1. 缘由简述

### 1.1 Arbiter 必须从证据构造交易，不能相信 Seller 提交的候选 raw

旧 007 让 Seller 发送 `UnsignedStateTxRaw`，Arbiter 解析、比对少量字段后在 Seller 提供的 bytes 上签名。新设计把 005 已确立的原则推广到仲裁：报文只提交原始证据与角色意愿，付款交易由角色按唯一算法独立重建。

```text
Seller：从本地完整 opening 恢复 source output，形成 Claim 并签名
Arbiter：只接收 Claim + payload，验证后独立构造 candidate
Seller：收到 Kind 9 后再次独立构造同一 candidate，再添加 transaction signature
```

只要 Seller 与 Arbiter 构造出的 transaction bytes 有一个字节不同，hash 或 Arbiter transaction signature 验证必然失败，不允许回退到“相信 Seller raw”。

### 1.2 完整 OpeningProof 对 Arbiter 是过度证据

Arbiter 构造和签署 candidate 真正需要的 pool source context 是：

```text
pool output satoshis
pool output locking script
```

Refund template 本身提供：

```text
funding outpoint（txid + output index）
refund locktime
基础 input/output 形状
RefundTemplateTxID 的原文来源
```

完整 OpeningProof 中的 FundingTx raw、Buyer/Seller refund detached signatures、重复角色字段和 fee rate 不再进入 007 wire。Seller 在 Claim 上签名，明确对其声明的 source-output context、RefundTx、Buyer 授权和本次仲裁提交负责。

这是一项明确的效率/信任边界取舍：标准 Bitcoin txid 提交整个 FundingTx，而不是单独提交某个 output；没有完整 FundingTx 或链查询时，Arbiter 无法密码学证明 Seller 声明的 `satoshis + locking_script` 确实属于 RefundTx input 指向的链上 output。错误 context 会让双方生成的 ForkID sighash与真实 UTXO 不符，最终交易无法花费真实资金，Seller 无法获款，Buyer 不会因此被错误扣款。协议必须把无效 context 的可用性风险归于 Seller，不得声称 Arbiter 已验证链上 UTXO 存在、确认或未花费。

### 1.3 007 的交付真值是 Arbiter 实际托管内容

旧文档把 007 描述为不读取 004/payload 的纯联合签名；这无法证明 Seller 已完成交付。新 007 的业务事实改为：

```text
Buyer 在 003 中签署了有序 content hashes、目标 sequence、绝对 Seller 金额和 deadline
+ 任意提交者向 Arbiter 提交了这些 hashes 的精确 payload preimages
+ Seller 对完整 Claim 明确签名发起仲裁
+ Arbiter 在 deadline 前验证并持久化精确 payload bundle
= 对 Buyer 可恢复的仲裁交付已完成
```

请求外壳不重复携带旧 004 的 `payment_authorization_hash` 和旧 004 Seller signature。`PaymentAuthorizationHash` 可从 Claim 中的 `terms_cbor` 唯一推导；新的 `seller_claim_signature` 比旧 004 裸 hash 签名覆盖更多仲裁事实。Payload 不直接进入 Seller 签名，但通过 Buyer/Seller 都签入的 `terms_cbor.content_hashes_cbor` 间接绑定；Arbiter 必须逐项验证 payload 数量、顺序和 SHA-256。

### 1.4 previous state 不进入 007

003 已由 Buyer 签署目标 `PaymentSequence` 和绝对累计 `SellerAmountAfterSat`。007 candidate 的输入仍花费 opening funding outpoint；候选 outputs、sequence 和金额由 Claim 与固定构造规则唯一决定。Arbiter 不声称知道 Seller/Buyer 数据库中的“全局最新 off-chain state”，也不靠 Seller 提交 previous state 证明不存在更高状态。

若 Seller 选择较旧或较低金额的 Buyer 授权，经济损失由 Seller 自己承担；Arbiter 只执行一张密码学有效的 Buyer 绝对授权。应用可维护本 Arbiter 已处理过的 per-pool high-water mark 以避免自身重复/倒退签署，但不得把它描述成全网最新状态证明。

## 2. 不能改变或误解的基础规则

### 2.1 外层 version/type 与签名域

- Kind 8 CBOR 本体固定五元 `[4, 8, claim_cbor, seller_claim_signature, payloads_cbor]`。
- Kind 9 CBOR 本体固定五元 `[4, 9, result_cbor, arbiter_result_signature, arbiter_transaction_signature]`。
- Claim 和 Result 内层都不带版本或类型。
- Seller 只签 deterministic CBOR `[4, 8, exact_claim_cbor_bstr]`。
- Arbiter result 只签 deterministic CBOR `[4, 9, exact_result_cbor_bstr]`。
- 若 transport `wire.Packet.Kind` 仍存在，接收方必须同时要求 Packet Kind 与本体 type 一致；Kind 8 payload 贴成 Kind 9 或反之必须失败。
- 不得因 transport 已知 Kind 而删除本体的 `8/9`；也不得在 Claim/Result 内再重复一份 `4/8/9`。

### 2.2 Claim 字段单一真值

```text
pool_output_satoshis       Seller 声明的 pool source output 金额
pool_output_locking_script Seller 声明的规范 [Buyer,Seller,Arbiter] 2-of-3 P2MS script
refund_template_raw        unsigned canonical RefundTx 原文
terms_cbor                 Buyer 签署的精确 003 条款原文
buyer_signature            Buyer 对 terms_cbor 的普通消息签名
```

字段名不得使用含糊的 `FundingTxSatoshis` 或 `FundingTxLockingScript`；它们描述的是 FundingTx 的某个 pool output，而不是整笔 FundingTx。

`RefundTemplateTxID` 不单独出现在 Kind 8：

```text
derived_refund_template_txid = TxID(refund_template_raw)
claimed_refund_template_txid = Decode(terms_cbor).RefundTemplateTxID
```

二者必须逐字节相等。Hash 比对证明 Seller 提交的 RefundTx 原文正是 Buyer 在 003 中引用的原文，不证明 FundingTx 上链或 UTXO 未花费。

### 2.3 Pool locking script 必须严格恢复角色

`pool_output_locking_script` 只能接受规范的：

```text
OP_2
PUSHDATA(33-byte compressed Buyer pubkey)
PUSHDATA(33-byte compressed Seller pubkey)
PUSHDATA(33-byte compressed Arbiter pubkey)
OP_3
OP_CHECKMULTISIG
```

要求：

- 三把公钥均为规范压缩 secp256k1，且两两不同；
- 顺序固定为 Buyer、Seller、Arbiter，不能排序或根据签名猜角色；
- 不接受 P2SH/P2WSH、非最短 push、额外 opcode、尾随 bytes、等价但非规范脚本；
- 解析后必须调用官方 `BuildArbitratedPoolLock` 重建并逐字节比较；
- Seller workflow 私钥必须匹配第二把 key；Arbiter workflow 私钥必须匹配第三把 key；
- Buyer `terms_cbor` 签名必须用第一把 key 验证。

### 2.4 Payload 的间接绑定

```text
BuyerSignature -> terms_cbor -> ordered content_hashes_cbor
SellerClaimSignature -> [4, 8, claim_cbor] -> terms_cbor
content_payloads_cbor[i] -> SHA-256 -> content_hashes_cbor[i]
```

因此 payload 可以位于 Seller Claim 签名外，但必须：

- 数量严格相等且在 1–64；
- 顺序严格相同；
- 每项非空且不超过 `masterseed.BlockSize`；
- 每项 SHA-256 与对应 hash 完全一致；
- 子 CBOR deterministic，decode/re-encode 逐字节一致；
- 任一项失败整批拒绝，不允许前缀接受、自动排序、部分保存后签名或缺失项计零价。

Arbiter 不读取 001 Quote、不重新定价、不判断 seed/block 类型或 membership；Buyer 已签署精确 hashes 和绝对 Seller 金额。007 验证“请求的精确 bytes 已托管”，不是重新审查报价经济学。

### 2.5 Source output 真实性边界

本次明确不做：

- 不在 007 请求中携带完整 FundingTx；
- 不要求 Arbiter 联网查询 FundingTx、UTXO、确认数或广播状态；
- 不把 OpeningProof 携带回 007；
- 不增加 BuyerRefundSignature 来证明 source context。

Arbiter 只验证 Seller 签名已绑定 source context、脚本/金额/RefundTx/candidate 在离线证据下内部一致。若 source context 与真实 FundingTx output 不同，最终链上签名无效；Seller 自负无法结算、仲裁服务费和重试成本。应用必须把该错误记录为 `seller_source_context_invalid_or_unspendable` 一类对账结果，不能让 SDK 猜测真实 context 或静默改值重签。

### 2.6 Seller Claim 签名与交易签名职责不同

Kind 8 只携带 `seller_claim_signature`，不携带 `seller_transaction_signature`。前者证明 Seller 主动提交完整仲裁证据；Arbiter 验证、持久化并签署 candidate 后，Seller 收到 Kind 9，再独立重建 candidate 并生成交易签名。

```text
seller_claim_signature       普通消息 low-S DER；签 [4,8,claim_cbor]
arbiter_result_signature     普通消息 low-S DER；签 [4,9,result_cbor]
arbiter_transaction_signature 交易签名 DER||ForkID|All
seller_transaction_signature  Kind 9 完成后本地生成的交易签名 DER||ForkID|All
```

任何混用、少/多一次 SHA-256、签 CBOR hex、签 txid 或把消息签名塞进 unlocking script 都必须失败。

## 3. 唯一确定性仲裁交易构造算法

### 3.1 输入

唯一公开构造核心只接受：

```text
pool_output_satoshis
pool_output_locking_script
refund_template_raw
payment_sequence          <- terms_cbor
seller_amount_after_sat   <- terms_cbor
```

它不得接受 Buyer amount、Arbiter amount、fee、fee rate、角色公钥、output scripts、locktime、funding outpoint 或 candidate raw 的第二份调用方声明。

### 3.2 Refund template 验证

构造前必须严格验证：

- RefundTx 是规范序列化、恰好一个 input、恰好三个 outputs；
- input unlocking script 为空；
- input outpoint 非空，output index 直接来自该 input；
- RefundTx sequence 不是最终关闭哨兵；
- outputs 顺序和脚本严格为 `[P2PKH(Buyer), P2PKH(Seller), P2PKH(Arbiter)]`；
- RefundTx Seller output 与 Arbiter output 均为 0；
- 三个输出金额 checked-add 后不超过 `pool_output_satoshis`；
- `refund_fee_sat = pool_output_satoshis - sum(refund_outputs)`，允许协议已有规则产生 0 fee，但不得下溢；
- `TxID(refund_template_raw)` 与 Buyer terms 中的 ID 相等。

### 3.3 Candidate 构造

```text
seller_amount = terms.SellerAmountAfterSat
arbiter_amount = 0
buyer_amount = pool_output_satoshis - refund_fee_sat - seller_amount
```

所有算术使用 checked subtraction/addition；余额不足、溢出、保留 final sequence、目标 sequence 不大于 RefundTx sequence 均拒绝。

从零构造或克隆后完全规范化为：

```text
Input[0]:
  outpoint          = RefundTx.Input[0].outpoint
  sequence          = terms.PaymentSequence
  unlocking_script  = empty
  source_output     = {pool_output_satoshis, pool_output_locking_script} // 内存 sighash context，不序列化

Output[0]: P2PKH(Buyer),  buyer_amount
Output[1]: P2PKH(Seller), seller_amount
Output[2]: P2PKH(Arbiter), 0

LockTime = RefundTx.LockTime
```

candidate 的 wire bytes 不携带 source output 元数据；签名/验签前必须把 Claim source context 注入 transaction input 的内存对象。不得从 payload 大小、Quote、previous PaymentState、当前数据库余额或 Seller 自报 fee 修改 candidate。

### 3.4 与 MultisigPool v4 的一致性

实现必须有 golden/property tests 证明，在相同合法 opening、任意普通目标 sequence 和任意容量内 Seller 绝对金额下：

```text
new BuildArbitrationPaymentFromClaim(...).RawTx
  == existing canonical MultisigPool BuildPaymentUpdate(...).RawTx
```

若出现不一致，必须停止施工，定位 fee size、locktime、sequence、output script 或底层 MultisigPool 规则差异；不得以修改 fixture、相信任一角色 raw、放松 byte equality 或给 007 单独发明非 MultisigPool 交易格式解决。

## 4. 最终角色 API 与状态边界

### 4.1 Seller 构建 Kind 8

Seller workflow 固定硬切换为：

```go
func (workflow *Workflow) BuildArbitrationRequest(
    ctx context.Context,
    opening *pool.OpeningProof,
    authorization *bitfs.SignedContentRequest,
    delivery *bitfs.SignedContentDelivery,
    blockHeight uint32,
) (*arbitration.ArbitrationRequest, error)
```

`OpeningProof` 仅是 Seller 本地可信输入，用于验证自己保存的 opening 并提取：

- `RefundTx`；
- FundingTx 固定 pool output 的 satoshis/locking script；
- Seller 角色归属。

它绝不进入新 Kind 8 wire。Seller 固定顺序：

1. clone 输入并验证 workflow 私钥属于 opening Seller；
2. 完整验证 opening，确保本地 source output 来自自己的 FundingTx；
3. 验证 003 Buyer 签名与 opening/RefundTemplateTxID 绑定；
4. 验证传入 004 的 `PaymentAuthorizationHash`、Seller 004 签名和 payload bundle；
5. 检查本地时间/区块高度仍允许 007；
6. 编码最终五元 Claim；
7. 编码 Seller 签名预映像 `[4,8,claim_cbor]`；
8. 用 Seller key 走固定 `SignMessage`，并在返回前自验；
9. 只把 Claim、Claim signature、004 中的 `ContentPayloadsCBOR` 放入 Kind 8。

删除旧参数 `base *pool.PaymentState`；删除 Seller 构造/签署 arbitration transaction 的旧步骤。不得保留旧 overload 或 `BuildArbitrationRequestFromCandidate`。

### 4.2 Arbiter 准备、应用持久化、再签名

SDK 继续无数据库副作用，但公开 API 必须让应用能在 Arbiter transaction signature 生成前持久化内容。公开接口固定硬切换为两段纯协议 API：

```go
func (workflow *Workflow) PreparePayment(
    ctx context.Context,
    request *ArbitrationRequest,
    blockHeight uint32,
) (*PreparedPayment, error)

func (workflow *Workflow) SignPreparedPayment(
    ctx context.Context,
    prepared *PreparedPayment,
) (*ArbitrationResponse, error)
```

删除旧 `SignPayment(ctx, request)` 直接验证并签名入口，避免公共 happy path 绕过 custody persistence 门禁。

`PreparedPayment` 只能由 `PreparePayment` 构造；内部字段不导出，公开 getter 必须返回深复制。它至少携带：

- 精确 request commitment；
- 派生 RefundTemplateTxID；
- PaymentAuthorizationHash；
- ContentPayloadsHash；
- 深复制 payloads；
- 独立构造的 exact unsigned candidate；
- Buyer/Seller/Arbiter 角色公钥；
- deadline 与准备时读取的 UTC 事实。

应用固定顺序：

```text
raw Kind 8 入站先持久化/限流
-> PreparePayment 完整验证
-> 在应用数据库/对象存储原子持久化 exact request + exact payload bundle + commitment
-> persistence commit 成功
-> SignPreparedPayment
-> 持久化 exact Kind 9 bytes 与状态
-> 发送 Kind 9
```

`SignPreparedPayment` 必须对 opaque prepared 内容重新做最小一致性检查、独立重算 candidate hash、生成并自验 result message signature 与 transaction signature。应用崩溃后没有内存 `PreparedPayment` 时，必须从已保存 exact Kind 8 bytes 重新调用 `PreparePayment`，不能反序列化或伪造 opaque token。

### 4.3 Buyer 内容取回属于应用服务

go-bitfs SDK 不增加数据库、HTTP 或对象存储。Arbiter 应用必须以至少以下键持久化索引：

```text
request_commitment -> exact request/result/status
payment_authorization_hash -> request_commitment
(refund_template_txid, payment_sequence) -> request_commitment/high-water state
```

Buyer 恢复后通过应用定义的已认证接口取回精确 `content_payloads_cbor`；应用用 Claim locking script 的 Buyer pubkey 验证调用者所有权。Retention、删除、配额、加密静态存储与服务收费属于部署策略，但不得在 Kind 9 签出后立即删除尚未被 Buyer 取回且未达到约定 retention 的内容。

### 4.4 Seller 完成仲裁交易

Seller API 硬切换为不再接收 OpeningProof/previous candidate state：

```go
func (workflow *Workflow) CompleteArbitratedPayment(
    ctx context.Context,
    request *arbitration.ArbitrationRequest,
    response *arbitration.ArbitrationResponse,
    blockHeight uint32,
) (*pool.SignedPayment, error)
```

固定顺序：

1. 严格编码/验证 request 与 response；
2. 从 Claim locking script 恢复角色，绑定当前 Seller key；
3. 验 Seller Claim signature、Buyer terms signature、RefundTemplateTxID 与 payload hashes；
4. 重新计算 request commitment、payload hash；
5. 独立构造 exact candidate 并计算 unsigned tx hash；
6. 与 ArbiterResult 三个 hash 全部逐字节比较；
7. 验 Arbiter result message signature；
8. 验 Arbiter transaction signature覆盖 Seller 本地重建的 exact candidate；
9. Seller 现在才生成自己的 transaction signature；
10. 通过唯一 `MergeArbitratedPoolSellerArbiterSignatures` 合并；
11. 返回完整 `SignedPayment`，记录派生 RefundTemplateTxID、sequence、金额、授权 hash 与两份 detached signatures；
12. 广播、对账、accepted 状态推进仍由应用负责。

## 5. 明确禁止的实现

- 禁止同时接受旧六元和新五元 v4 Kind 8；禁止按数组长度试探 decoder。
- 禁止同时接受旧五元和新五元但不同字段语义的 v4 Kind 9；外层 type `9` 和 Result 子文档必须严格存在。
- 禁止在 `ArbitrationRequest` 保留 `RefundTemplateTxID`、`PoolOpeningProofCBOR`、`PaymentAuthorizationCBOR`、`UnsignedStateTxRaw`、`SellerTransactionSignature` 作为 deprecated/omitempty/内部字段。
- 禁止在 Claim 内重复版本、Kind、RefundTemplateTxID、PaymentAuthorizationHash、角色公钥、fee rate、previous state、candidate raw 或 Seller amount/sequence副本。
- 禁止携带完整 FundingTx 或要求 Arbiter 联网查询 FundingTx/UTXO；本单选择 Seller-signed source-output context。
- 禁止文档声称 Seller source output 已被链上证明、已确认或未花费。
- 禁止 Arbiter 接收 Seller 构造的 candidate raw、patch Seller raw 后签名，或在本地构造失败时回退相信 Seller。
- 禁止 Seller 在 Kind 8 发送 transaction signature；Seller transaction signature 只能在验证 Kind 9 后针对本地重建 candidate 生成。
- 禁止 Seller Claim signature 只签 `arbitration_claim_cbor`；必须签 deterministic `[4,8,claim_cbor]`。
- 禁止把完整 outer request、payload bytes、Claim hash、hex/JSON 或 `[claim,payload]` 当成 Seller 约定签名对象。
- 禁止 Arbiter result signature 只签 Result bytes；必须签 deterministic `[4,9,result_cbor]`。
- 禁止用 result message signature 合并交易，或用 transaction signature冒充 payload custody receipt。
- 禁止把 content payloads 直接塞入 Seller Claim 签名预映像；只通过 terms hashes 绑定，避免大 payload 签名复制。
- 禁止跳过 payload 数量、顺序、hash、大小和 canonical CBOR 验证。
- 禁止 007 读取 Quote、重新定价、按 payload 类型改金额，或从 Seller 数据库金额覆盖 Buyer 签署的绝对金额。
- 禁止把 `PaymentAuthorizationHash` 定义为完整 003 外壳、Claim、Request 或 BuyerSignature 的 hash。
- 禁止从 seller source context 猜测/修复真实链上 output；失败只能拒绝或后续广播对账暴露。
- 禁止 `PreparePayment` 在内容持久化前产生任何 Arbiter transaction signature。
- 禁止 SDK 自己写数据库、对象存储、发网络请求、广播交易或声明 UTXO 可花费。
- 禁止应用在 payload 保存失败、部分保存或 result 保存失败时仍向 Seller 返回 Arbiter transaction signature。
- 禁止手改生成 API 文档或中文 API 页面来掩盖源码、spec、英文/中文文档未同步。
- 禁止修改 `spec/v1`、`spec/v3` 历史结构来伪造全仓一致；它们保持历史真值，当前 v4 decoder 只拒绝旧形状。

## 6. 特殊情况与固定处理

| 特殊情况 | 必须怎么做 | 不能怎么做 |
|---|---|---|
| Kind 8 version 不是 4 或内嵌 type 不是 8 | 严格拒绝 | 依赖 transport Kind 覆盖错误本体 |
| Packet Kind 与本体 type 不一致 | 拒绝并记录跨类/错误路由 | 只按其中一个继续 |
| 旧六元 v4 request 到达 | decoder 明确拒绝并要求整体升级 | 运行时转换、双 decoder、静默抽字段 |
| Claim 非 canonical、缺/多字段或尾随 bytes | 拒绝 | 解码后重新编码替发送方“修复”再验签 |
| Pool locking script 不是精确角色顺序 P2MS | 拒绝 | 猜角色、排序公钥、接受等价非规范 script |
| Claim Arbiter key 不是当前 workflow key | 拒绝错仲裁方 | 仍用当前私钥签，或把第三把 key 覆盖成自己 |
| Seller Claim signature 无效 | 拒绝，不保存为有效仲裁 | 因资金流向 Seller 就忽略提交意愿签名 |
| Buyer terms signature 无效 | 拒绝 | 只因 RefundTemplateTxID 相等就接受 |
| RefundTx txid 与 terms pool ID 不同 | 拒绝错池/换模板 | 用任一边覆盖另一边 |
| Seller source sats 小于 RefundTx outputs 总额 | 算术错误，签名前拒绝 | uint64 下溢或把差额当负 fee |
| Seller source script/amount 与真实 UTXO 不同 | SDK 离线阶段可能无法发现；最终不可花费由 Seller 承担，应用对账记录并停止重签 | SDK 猜值、联网补证据、改 candidate 反复试签 |
| PaymentSequence 不大于 RefundTx sequence、为 final sentinel 或越界 | 拒绝 | 自动加一或改写 Buyer terms |
| SellerAmountAfterSat 超容量 | 拒绝余额不足 | 截断金额、减少 fee 或修改 Buyer amount 掩盖 |
| payload 数量/顺序/hash/大小错误 | 整批拒绝且不签 | 部分托管、接受前缀、排序或跳过坏项 |
| Seller 提交正确 hash 的相同内容副本 | 内容地址相同即可接受；exact canonical bundle hash 用于幂等 | 以网络来源不是原 004 连接为由拒绝 |
| 当前时间晚于 DeliveryDeadline，且 Arbiter 尚未完整持久化 | 拒绝无可证明的及时托管 | 相信 Seller 自报早先发送时间或文件 mtime |
| Prepare 在 deadline 前完成、持久化 commit 在 deadline 后 | 以持久化 commit 时间为准，拒绝签名 | 以开始处理或收到第一字节时间冒充完成托管 |
| payload 部分保存后存储失败 | 回滚/标记不完整，绝不调用 SignPreparedPayment | 对已有部分内容签 Kind 9 |
| payload 保存成功、签名失败 | 保留已验证 custody 记录，可从 exact request 重新 Prepare 后重试 | 删除内容或改写 request 后继续 |
| Arbiter 已签但 Kind 9 保存失败 | 不发送；从内存或 exact prepared 结果先持久化完整 response bytes，再发送 | 只发送裸 transaction signature，或重新构造不同 Result |
| Kind 9 保存成功但网络发送失败 | 重发同一 exact canonical bytes | 重签、改变 result hash 或生成另一 response |
| 完全相同 Kind 8 重放 | 按 request commitment 幂等返回已保存状态/response；若仍 prepared 则继续同一状态机 | 重复存 payload、重复收费、生成冲突记录 |
| 同 request commitment 但 payload hash 不同 | 视为哈希/数据库安全事件并拒绝 | 任取一份或覆盖旧 bundle |
| 同 `(pool, sequence)` 不同有效 Claim | 应用标记冲突并人工/策略处理；默认不为第二份签名 | 因两份都由 Buyer 签过就无记录地双签 |
| sequence 低于本 Arbiter 已签 high-water | 默认拒绝 stale 仲裁；若产品允许，必须有显式审计策略 | 静默倒退 high-water |
| Seller 收到 response 但找不到 exact request | 请求重发/从本地 journal 恢复；不能完成 | 扫描所有 claim 尝试 Arbiter signature |
| response request/payload/tx hash 任一错配 | 拒绝，不生成 Seller tx signature | 只验证 Arbiter transaction signature 就继续 |
| Arbiter result sig 有效但 transaction sig 无效 | 拒绝交易完成，保留 custody 审计并告警 | 把 message signature 塞进交易 |
| transaction sig 有效但 result sig 无效 | 拒绝，因为 custody/result 未被 Arbiter 认证 | 仅因钱能花就忽略 result |
| Seller 合并成功但广播失败/超时 | 先持久化 raw/txid，再按应用节点策略对账 | 重新要求 Arbiter 签另一 candidate |
| Buyer 恢复取件 | 验 Buyer key 归属后返回 exact payload bundle，并保留审计 | 仅凭 auth hash 作为 bearer token 公开内容 |
| retention 到期但付款仍未决/Buyer 未取回 | 按产品合约延长或进入人工处置，先保全已签 custody 证据 | Kind 9 签出后立即无痕删除 |
| 已存在外部旧 v4 客户端 | 停止同 major 施工并升级版本 | 同 v4 双栈探测 |

## 7. 一次性实施顺序与切换门禁

以下顺序只用于同一原子迭代内降低施工风险，不表示允许分步发布、合并或双栈运行。

1. 冻结同一 fixture 的 OpeningProof、RefundTx、pool source output、003、004、旧 007 candidate、旧 Seller/Arbiter transaction sighash 和最终 merged raw，作为“只改证据传输与构造责任、不改最终交易”的对照。
2. 更新 `spec/v4/arbitration.cddl` 与新的 request/result signing-domain golden，先固定最终 wire、Claim、Result、hash 和签名预映像。
3. 在 `pool` 增加严格 P2MS role parser 与唯一 `BuildArbitrationPaymentFromClaim` 核心；用旧 canonical `BuildPaymentUpdate` fixture 证明 candidate bytes 完全一致。
4. 破坏式替换 `arbitration` request/response 类型、CBOR、validator、clone、Prepare/SignPrepared workflow；删除旧字段和旧 `SignPayment`。
5. 修改 Seller Build/Complete API：Build 只形成 Claim + Claim signature + payload；Complete 从 request 重建 candidate、验 response 后才签交易。
6. 同一次修改全部 wire 分派测试、unit/integration/golden/negative/cross-language tests、demo、CDDL、中英文规范和 SDK API 文档。
7. 增加旧 v4 request/response exact reject tests；静态搜索确保旧字段、旧注释和旧 API 不再出现在当前代码/当前 v4 文档中。
8. 跑格式化、Go 单测、race、vet、website 文档构建与跨语言向量；任何失败先修复，不允许带红项合并。
9. 合并/部署时全体 Seller/Arbiter 同时替换；排空旧 007 队列。运行时只存在新 shape。

## 9. 测试与安全验收矩阵

### 9.1 CBOR / signature golden

- Request exact 五元、outer `4,8`；Response exact 五元、outer `4,9`。
- Claim exact 五元且无内层版本/kind；Result exact三元且无内层版本/kind。
- `seller_claim_signing_cbor` exact bytes 固定；签 Claim alone、Claim hash、完整 request、hex、payload 都验证失败。
- `arbiter_result_signing_cbor` exact bytes 固定；签 Result alone/hash/完整 response 都验证失败。
- 非最短整数/长度、indefinite array/bstr、tag、多/少字段、尾随 bytes、错误 bstr/嵌套 array 全拒绝。
- request/result/signing bytes/hash/signature 全部由 Go golden 测试冻结（`wire/golden_messages_test.go`），不以跨语言双向一致作为验收口径。

### 9.2 角色与证据

- 精确解析规范 P2MS，Buyer/Seller/Arbiter顺序正确。
- 错 key、重复 key、非压缩 key、非最短 push、额外 opcode 全拒绝。
- Seller workflow key 不匹配第二角色、Arbiter key不匹配第三角色全拒绝。
- Buyer signature错 terms、Seller signature错 Claim/preimage 全拒绝。
- RefundTx txid错 terms pool ID、错 input/output shape、错 role output script、Seller/Arbiter refund输出非0全拒绝。
- source sats不足、溢出、异常 fee、sequence非法、Seller amount超容量全拒绝且不触发签名。

### 9.3 Payload custody

- 1项与64项边界通过；0项、65项拒绝。
- 任一 payload 空、过大、hash错、顺序错、数量错、非canonical拒绝。
- Prepare返回 payload深复制；修改 request/input/getter返回值不改变 prepared内部证据。
- 内容持久化失败时测试应用断言没有调用 SignPreparedPayment/没有任何 Arbiter tx sig。
- 完整重放按 commitment幂等；同 commitment不同bundle视为冲突。
- deadline前 commit通过；deadline后完整托管拒绝。
- Arbiter result signature精确绑定 request、payload、candidate三个hash。

### 9.4 交易构造与签名

- Seller与Arbiter从同一Claim重建candidate逐字节一致。
- 新builder与旧canonical MultisigPool fixture candidate逐字节一致。
- source output只作为内存sighash context，不泄漏进标准raw tx。
- Buyer/Seller/Arbiter outputs、金额、fee、sequence、locktime与规则一致。
- Arbiter transaction signature只对exact candidate有效；任一输入/output/sequence/locktime变更失败。
- Seller必须在Kind9全验后才签；merge后的完整raw通过 `VerifyArbitratedPayment`。
- final signed raw/txid与切换前相同业务fixture保持一致；变化只允许来自确定性签名本身已知规则，不允许交易结构漂移。

### 9.5 兼容与静态门禁

- 旧 request `[4, refund_id, opening, authorization, unsigned_tx, seller_tx_sig]` 严格拒绝。
- 旧 response `[4, refund_id, auth_hash, tx_hash, arbiter_tx_sig]` 严格拒绝。
- 当前非legacy代码静态搜索不再出现 request旧字段或旧 `SignPayment(ctx, request)` 调用。
- 当前文档不再出现“007 不读payload”“Arbiter不构造交易”“007携带OpeningProof/candidate raw”等旧结论。
- `spec/v1`/`spec/v3` 历史仍原样存在但不会被v4 decoder接受。
