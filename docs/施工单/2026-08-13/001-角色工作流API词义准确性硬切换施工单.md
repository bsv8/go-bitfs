# 角色工作流 API 词义准确性硬切换施工单

## 1. 背景

`go-bitfs` 是 BitFS v3 的协议真值库与进程内角色工作流 SDK，不是网络客户端，也不是可独立部署的服务器。目前三个角色入口分别叫作 `buyer.Client`、`seller.Service`、`arbiter.Service`，同一层抽象使用了不同名词；其中 `Client` 容易被理解为网络客户端，`Service` 容易被理解为常驻服务。

同时，根包 `arbiter` 实际承载的是 007 仲裁业务流程、请求响应编解码与证据验证，而不是一个“仲裁者对象”。包名应描述业务能力，而不是参与者实体。

## 2. 目标

对公开 Go API 做一次无兼容别名的词义硬切换：

| 当前 API | 新 API |
|---|---|
| `buyer.ClientConfig` | `buyer.WorkflowConfig` |
| `buyer.Client` | `buyer.Workflow` |
| `buyer.NewClient` | `buyer.NewWorkflow` |
| `seller.ServiceConfig` | `seller.WorkflowConfig` |
| `seller.Service` | `seller.Workflow` |
| `seller.NewService` | `seller.NewWorkflow` |
| `arbiter` 包 | `arbitration` 包 |
| `arbiter.ServiceConfig` | `arbitration.WorkflowConfig` |
| `arbiter.Service` | `arbitration.Workflow` |
| `arbiter.NewService` | `arbitration.NewWorkflow` |
| `arbiter.PaymentSignatureRequest` | `arbitration.ArbitrationRequest` |
| `arbiter.PaymentSignatureResponse` | `arbitration.ArbitrationResponse` |
| `arbiter.PoolVerifier` | `arbitration.PoolPort` |

`Workflow` 的统一含义是：一个通过端口注入外部能力、在当前进程内编排某个协议角色行为的对象。它不暗示 HTTP、RPC、消息队列、后台进程或部署形态。

## 3. 实施范围

1. 硬切换上述公开类型、构造器、包路径及所有仓库内调用点。
2. 将 `buyer/client.go`、`seller/service.go` 等明显携带旧抽象名称的文件改成与 `Workflow` 一致的文件名；测试文件同理。
3. 将接收者、局部变量、注释和错误消息中用于描述这三个工作流对象的 `client`、`service` 改成 `workflow`，避免代码内部继续表达错误概念。
4. 将 `arbiter/` 目录迁移为 `arbitration/`，更新 `seller`、`wire`、集成测试和其他生产调用点的 import 与限定名。
5. 更新 README、当前 SDK 文档和当前协议文档里的 Go API 引用。历史文档只在仍被当前 README/SDK 当作有效入口引用时修改。
6. 保持 `Arbiter` 作为费用池角色名，保持 `ArbitrationRequest`、`ArbitrationResponse` 等仲裁领域名；这些词义准确，不随包目录改名而改变。
7. 删除泛化且重复的 `PaymentSignatureRequest`、`PaymentSignatureResponse` 类型别名，仓库内统一直接使用 `ArbitrationRequest`、`ArbitrationResponse`。
8. 将同时提供费用池验证和 Arbiter 签名的接口命名为 `PoolPort`；不得继续使用只表达验证能力的 `PoolVerifier`。
9. 保持现有测试语义，并增加或调整编译期覆盖，确保仓库只使用新 API。

## 4. 明确不做

1. 不保留 `Client`、`Service`、`ClientConfig`、`ServiceConfig`、`NewClient`、`NewService`、`PaymentSignatureRequest`、`PaymentSignatureResponse`、`PoolVerifier` 或旧 `arbiter` 包的兼容别名、包装器、转发包。
2. 不修改 BitFS 协议 major、消息 kind、CBOR 数组结构、CDDL 数据结构、签名域或哈希计算。
3. 不修改 MultisigPool v4 的角色、脚本、输出、手续费、签名和交易构造语义。
4. 不把 `arbitration` 合并进 `pool`：`pool` 负责通用费用池交易能力，`arbitration` 负责 BitFS 007 证据验证与仲裁签名编排。
5. 不新增 HTTP、RPC、队列、数据库、钱包或节点运行时代码。
6. 不顺带重构 buyer、seller、arbitration 的业务流程，不改变公开方法的业务参数和返回值；仅做这次命名硬切换必需的修改。
7. 不改费用池角色术语 `Buyer`、`Seller`、`Arbiter`，也不把真正表示传输客户端的通用概念机械改名。

## 5. 验收标准

1. `buyer.NewWorkflow(buyer.WorkflowConfig{...})`、`seller.NewWorkflow(seller.WorkflowConfig{...})`、`arbitration.NewWorkflow(arbitration.WorkflowConfig{...})` 是三个唯一公开角色工作流入口。
2. 非历史代码和当前文档中不存在旧包路径 `github.com/bsv8/go-bitfs/arbiter`，不存在三个入口的旧公开名称。
3. `wire` 继续编解码同样的仲裁请求响应字节，只是 Go 类型来自 `arbitration` 包。
4. 所有现有协议、费用池、仲裁和端到端测试通过。
5. `go vet ./...`、`go test ./...`、`go test -race ./...`、`git diff --check` 全部通过。
6. 通过改名前后的 fixture/测试证明：本次修改不改变任何协议编码和交易字节。

## 6. Review 重点

1. 搜索旧符号，防止通过 type alias 或旧目录残留形成双 API。
2. 检查 `seller -> arbitration -> pool` 的依赖方向没有反转或循环。
3. 检查错误消息和注释没有继续把进程内工作流称为网络 client/server service。
4. 检查改名没有误伤领域中的 Arbiter 角色、arbitrated payment 或真正的外部传输概念。
5. 检查 `wire` 的编码测试与端到端仲裁测试，确认纯命名修改没有影响协议结果。
