# 008 买方仲裁托管内容取回 v4 一次性硬切换施工单

## 0. 施工结论、范围和唯一目标态

本次在一个不可拆分的迭代中，为现有 007 Seller 仲裁托管补齐 Buyer 取件路径：Seller 与 Buyer 无法直连时，Seller 继续通过 Kind 8 把精确 payload 托管给 Arbiter，Arbiter 按现有 Kind 9 完成付费仲裁回执；Buyer 使用自己可独立计算的 `ArbitrationClaimID` 定位这份托管记录，经 Buyer 公钥签名鉴权后，从 Arbiter 取回 exact Kind 8/9 证据和其中的精确 payload bundle。

本次同时把一条边界写死：**不设计、不实现 Buyer 仲裁关闭费用池**。Seller 失联或拒绝协商关池时，Buyer 使用 002 已获得的预签名 RefundTx，等到 `nLockTime` 成熟后退款。不新增 Buyer+Arbiter 关池 candidate、挑战期、Seller 反证流程或关池仲裁状态机。

这是上线前的 v4 一次性硬切换：代码、wire kind、CBOR、CDDL、测试向量、集成测试、demo、中英文当前文档和静态一致性门禁必须在同一次变更中同时落地。不做分步上线，不先发布只能编解码但不能完整鉴权的中间状态，不保留另一套取件字段、旧 kind、兼容 decoder、feature flag 或按字段是否为空自动猜测。

本次对现有 001–007 的不可变结论是：

- Kind 8 Seller Arbitration Request 的数组形状、Claim 字节、Seller Claim 签名域和 golden bytes 不变；
- Kind 9 Arbiter Receipt Response 的四元形状、Receipt 字节、正仲裁费、Receipt 签名域和 golden bytes 不变；
- `ArbitrationClaimID = SHA-256(deterministic-CBOR([4, 8, exact_claim_cbor]))` 的唯一算法不变；
- 004 仍是 Seller 直连交付，005 仍是 Buyer 验货后的付款凭证；
- 008 取回的内容已经进入 007 Seller+Arbiter 结算路径，Buyer 验收时不得再生成 005；
- SDK 继续无状态；网络、数据库、nonce 去重、留存期、限流、TLS、节点查询和广播仍由应用负责。

若施工时发现 Kind 10/11 已被其他未同步升级的客户端占用，或 v4 已有不可一次同步升级的生产节点，必须停止同 major 硬切换，改定新 major/transport family 并单独制定迁移方案；不得让两套不兼容的报文都自称 v4。

施工开始前必须记录 `git status --short` 和目标文件 diff 基线。不得使用 `git reset --hard`、`git checkout --`、整文件回退、清理未跟踪文件或覆盖用户现有改动来获得“干净起点”。

## 1. 缘由简述

### 1.1 现有 007 已托管内容，但 Buyer 没有标准取件路径

当 Seller 已按 Kind 8 提交 Claim 和 exact payload bundle，Arbiter 也已验证、持久化并按 Kind 9 签署 Receipt 时，“Arbiter 持有 Buyer 已授权内容的精确 preimage”已是现有协议事实。但当前只把 Buyer retrieval 写成应用责任，没有固定关联 ID、Buyer 签名域、严格 wire 结构和 Buyer workflow 验收入口。结果是每个 Arbiter 应用都会自定一套不可互验的下载 token 或 HTTP 字段。

本次把它收敛为一条简单的、可离线验证的链：

```text
Buyer 原始 OpeningProof + Buyer 原始 signed 003
  -> 独立构造与 Seller 相同的 exact ClaimCBOR
  -> ArbitrationClaimID
  -> [ClaimID + random nonce] Buyer 签名
  -> Arbiter 按 ClaimID 取回已保存 exact Kind 8/9
  -> Buyer 独立验证 Claim、Receipt、交易签名和 payload
```

### 1.2 Claim ID 比数据库随机 ID 或单独 PaymentAuthorizationHash 更适合

Claim ID 已是 007 的内容派生稳定 ID，它绑定 exact ClaimCBOR，间接绑定 pool source context、RefundTx、Buyer 签名的 exact TermsCBOR 和其中的有序 content hashes。Buyer 和 Seller 不需要直连，也不需要拿到 Seller Claim signature、payload 或 Kind 9，就能从各自已有的 opening + signed 003 得到相同 ID。

因此：

- 不新增数据库自增 ID、UUID 或可变 session ID；
- 不同时保留 `claim_hash`、`claim_id`、`request_commitment` 三个同义字段；
- 不用 `PaymentAuthorizationHash` 代替 Claim ID 路由 008；
- Go 和 wire 中唯一命名继续是 `ArbitrationClaimID` / `ClaimID`。

### 1.3 Buyer 关池仲裁不做，到期 RefundTx 就是关池保障

Buyer 仲裁关池会引入无法靠一个请求解决的竞态：Buyer 可能已签 003，Seller 也可能已交付或正在提交 007，Arbiter 不能因为当下没查到 Claim 就立即帮 Buyer 花费池输出。要安全实现必然需要 Seller 通知、挑战期、最新状态选择和 Buyer+Arbiter 合签状态机，这会把“取回已托管文件”变成另一个结算协议。

002 已要求 Buyer 在公开 FundingTx 前持有 Buyer+Seller 预签名的 RefundTx。因此本次保持简单且可证明的边界：

```text
Seller 仲裁交付：Kind 8/9 + 008 Buyer 取件
Buyer 关池：协商 006，或等 nLockTime 后广播 002 RefundTx
```

Arbiter 不提供“快速退款”、“提前关池”或“判定 Seller 没有交付”服务。

## 2. 最终 wire 真值

### 2.1 Kind 10·Buyer 托管内容取回请求

方向固定为 Buyer → Arbiter。报文是五元 deterministic CBOR：

```text
ArbitrationContentRequest = [
  4,
  10,
  arbitration_claim_id,
  retrieval_nonce,
  buyer_retrieval_signature
]
```

字段约束：

```text
arbitration_claim_id      = bstr .size 32
retrieval_nonce           = bstr .size 32，禁止全零
buyer_retrieval_signature = bstr .size (1..256)
```

Buyer 签名域固定为：

```text
buyer_retrieval_signing_cbor = deterministic-CBOR([
  4,
  10,
  arbitration_claim_id,
  retrieval_nonce
])

buyer_retrieval_signature =
  SignMessage(BuyerKey, buyer_retrieval_signing_cbor)
```

`SignMessage` 继续使用项目固定语义：对 exact signing CBOR 内部做一次 SHA-256，再生成 low-S DER ECDSA 签名。不得签 Claim ID 裸 bytes、nonce 裸 bytes、二者字符串拼接、hex、JSON、完整五元请求或仲裁交易 sighash。

`retrieval_nonce` 由 Buyer **应用**使用密码学安全随机源生成，再显式传入 SDK。SDK 不调用随机源，不用时间戳、自增序号、Claim ID 前 32 字节或全零值代替随机 nonce。

最大请求尺寸必须从子字段上限派生：

```text
1 array head
+ 1 version
+ 1 kind
+ 34 Claim ID bstr
+ 34 nonce bstr
+ 259 max signature bstr
= 330 bytes
```

不得使用 16 KiB/64 KiB 一类无依据的宽松常量。

### 2.2 Kind 11·Arbiter 托管内容取回响应

方向固定为 Arbiter → Buyer。报文固定为四元 deterministic CBOR：

```text
ArbitrationContentResponse = [
  4,
  11,
  exact_arbitration_request_cbor,
  exact_arbitration_response_cbor
]
```

两个子文档都作为 `bstr` 嵌入：

- `exact_arbitration_request_cbor` 必须是 Arbiter 托管库中保存的 exact canonical Kind 8；它已包含 ClaimCBOR、SellerClaimSignature 和 `ContentPayloadsCBOR`；
- `exact_arbitration_response_cbor` 必须是同一条记录中已持久化的 exact canonical Kind 9；它包含与 Claim ID 匹配的 Receipt 和 ArbiterReceiptSignature。

这个外壳不新增第三条 Arbiter 签名。原因是：

```text
SellerClaimSignature
  -> exact ClaimCBOR
  -> Buyer signed TermsCBOR
  -> ordered content hashes

ArbiterReceiptSignature
  -> exact ReceiptCBOR
  -> same Claim ID
  -> fee + Arbiter transaction signature

ContentPayloadsCBOR[i]
  -> SHA-256
  -> exact ordered content hashes[i]
```

Buyer 必须验证上述整条链；Kind 11 外壳只是把两份已有规范证据一次性返回，不创造第二份托管真值。

响应中不再重复 `claim_id`、`content_payloads_cbor`、`receipt_cbor`、Buyer/Seller/Arbiter 公钥、OpeningProof、FundingTx、PaymentAuthorizationHash 或任何 raw candidate。Payload 只在内嵌 exact Kind 8 中出现一次。

Kind 11 最大尺寸必须由当前 Kind 8/9 上限组合派生：

```text
1 array head
+ 1 version
+ 1 kind
+ 5-byte bstr head + MaxArbitrationRequestBytes
+ 3-byte bstr head + MaxArbitrationResponseBytes
= 16,844,188 bytes   // 按当前 16,843,609 / 568 上限
```

若施工时子上限已变化，必须从实际常量重新派生并用测试钉死，不得照抄过期数字。

### 2.3 CDDL 唯一形状

```cddl
arbitration-content-request = [
  4, 10, arbitration-claim-id, retrieval-nonce,
  buyer-retrieval-signature
]

retrieval-nonce = bstr .size 32
buyer-retrieval-signature = bstr .size (1..256)

arbitration-content-response = [
  4, 11, exact-arbitration-request-cbor,
  exact-arbitration-response-cbor
]

exact-arbitration-request-cbor =
  bstr .size (1..16843609) .cbor arbitration-request

exact-arbitration-response-cbor =
  bstr .size (1..568) .cbor arbitration-response
```

CDDL 无法表达的约束必须由 Go verifier 执行：nonce 非全零、Buyer 签名、两份内嵌证据的 Claim ID 一致、Seller/Arbiter 签名、Arbiter transaction signature、payload 数量/顺序/hash，以及 Buyer 本地 expected ClaimCBOR 与内嵌 ClaimCBOR 逐字节相等。

## 3. 唯一业务流程

### 3.1 Arbiter 已有的 007 持久化顺序不变

```text
strict decode exact Kind 8
  -> 应用 UTXO 前置检查
  -> 应用计算并冻结 arbiter fee
  -> PreparePayment
  -> 原子持久化 exact Kind 8 / Claim ID / payload / fee
  -> SignPreparedPayment
  -> 原子追加 exact canonical Kind 9
```

008 不改变这个顺序。只有同一 Claim ID 的 exact Kind 8 和 exact Kind 9 都已持久化，记录才进入应用状态 `Retrievable`。

`PreparePayment` 成功但 Kind 9 还没有产生/持久化的记录只是 `CustodyPrepared`，不得向 Buyer 返回 payload。本次不要求 Seller 已合并自身交易签名、已广播或已上链才允许取件；Kind 9 已签署并持久化是本协议的释放边界。Seller 后续合并/广播/对账仍是 Seller 应用责任。

### 3.2 Buyer 构造取件请求

Buyer 应用按自己保存的 exact opening 和 exact signed 003 选定要取回的一批内容：

```text
load OpeningProof
load exact SignedContentRequest (003)
generate 32-byte cryptographically-random nonce
BuildArbitrationContentRequest(opening, authorization, nonce)
persist exact Kind 10 before send
send Kind 10 to the Arbiter selected in opening
```

Buyer workflow 必须：

1. 验证 workflow 私钥匹配 OpeningProof Buyer key；
2. 验证 OpeningProof 的签名和交易关系；
3. 验证 signed 003 属于该 opening 且 Buyer 签名有效；
4. 从 opening 派生 pool amount/script，与 exact TermsCBOR/BuyerSignature/RefundTx 构造和 Seller 完全相同的 ClaimCBOR；
5. 计算 Claim ID，对 `[4,10,claim_id,nonce]` 签名并自验；
6. 返回 deep-copy 的 Kind 10 对象。

取件是事后恢复，不得在这个 builder 中重新应用“003 delivery deadline 必须未过”或“refund 必须未到期”条件。这些时间门禁已在 Arbiter 当初签署 Kind 9 之前执行；事后取件只验证已固定的证据。

### 3.3 Arbiter 鉴权并返回托管证据

Arbiter 应用的固定顺序是：

```text
strict decode Kind 10
  -> 按 Claim ID 查 custody record
  -> 要求记录已有 exact Kind 8 + exact Kind 9
  -> SDK 完整验证存储证据和 Buyer 签名
  -> 应用原子写入 unique(ClaimID, Nonce) 访问记录
  -> 构造 Kind 11，内嵌已保存 exact Kind 8/9
  -> send Kind 11
```

SDK 完整验证包括：

- Kind 10 的 Claim ID 和 nonce 尺寸/canonical 形状；
- 存储 Kind 8/9 的 strict canonical decode；
- 从 Kind 8 Claim 重算 Claim ID，与 Kind 10 和 Kind 9 Receipt 同时比较；
- 从 Claim pool script 恢复固定角色顺序和 Buyer/Seller/Arbiter 公钥；
- Buyer 对 Kind 10 signing domain 的签名；
- Buyer 对 exact 003 TermsCBOR 的签名；
- Seller 对 exact `[4,8,claim_cbor]` 的签名；
- payload 的数量、顺序、大小、canonical CBOR 和逐项 SHA-256；
- Arbiter 对 exact `[4,9,receipt_cbor]` 的签名；
- 用 Receipt 费用重建 candidate 后的 Arbiter transaction signature。

SDK 不查询数据库，也不自己记录 nonce。`unique(ClaimID, Nonce)` 必须由应用用数据库唯一键、事务/CAS 或等价原子机制实现。先验签，再原子占用 nonce；未通过签名的请求不得污染 nonce 表。

### 3.4 Buyer 验收仲裁内容

Buyer 收到 Kind 11 后必须使用自己发出的 exact Kind 10、OpeningProof、exact signed 003、对应 Quote、上一个已接受 PaymentState 和必要的 Seed 做完整验收：

```text
AcceptArbitratedContent(
  quote,
  opening,
  previous,
  authorization,
  retrievalRequest,
  retrievalResponse,
  seed,
)
```

验收顺序固定为：

1. 验证 Buyer workflow 密钥与 opening Buyer key 匹配；
2. 验证 opening、Quote 签名、exact 003 Buyer 签名、QuoteTermsHash 和角色绑定；
3. 从本地 opening + exact 003 构造 expected ClaimCBOR/Claim ID；
4. 验证 exact Kind 10 中的 Claim ID、nonce 和 Buyer 签名；
5. strict decode Kind 11 内嵌的 exact Kind 8/9；
6. 要求内嵌 ClaimCBOR 与本地 expected ClaimCBOR **逐字节相等**，不只比较 hash；
7. 验证 Seller Claim signature、Receipt Claim ID、Arbiter Receipt signature 和 Arbiter transaction signature；
8. 验证 payload 数量、顺序、逐项 hash、seed/block membership、协议长度和定价；
9. 验证 `previous.PaymentSequence + 1 == terms.PaymentSequence` 和 `previous.SellerAmountSat + price == terms.SellerAmountAfterSat`；
10. 只返回 deep-copy payload、Claim ID 和 Receipt 审计数据，**不构造、不签名、不返回 005 PaymentUpdate**。

这个验收入口不重新执行“当前必须早于 Quote 过期、DeliveryDeadline 或 Refund nLockTime”。这些是 Seller/Arbiter 当时是否可以开始 007 并签署 Kind 9 的时间条件，不是 Buyer 事后检查已签证据和取回已托管 bytes 的时间条件。

## 4. SDK 与应用边界

### 4.1 SDK 负责

- ClaimCBOR 和 Claim ID 的唯一构造/计算；
- Kind 10/11 的 strict deterministic CBOR 编解码和尺寸上限；
- Kind 10 Buyer 签名的生成、自验和验证；
- exact Kind 8/9 托管证据链的时间无关验证；
- Buyer 本地 expected ClaimCBOR 与返回 ClaimCBOR 的逐字节比较；
- payload 数量、顺序、hash、membership、长度和价格复核；
- 返回可持久化的 deep-copy 验证结果。

### 4.2 应用负责

- 根据 Arbiter 公钥找到可连接的 endpoint/P2P route；
- 用密码学安全随机源生成 32 字节 nonce；
- 在发送前保存 exact Kind 10，在验收后保存 exact Kind 11 和内容；
- 用 Claim ID 查询 custody store，并要求 exact Kind 8/9 同时存在；
- 实现 `(ClaimID, Nonce)` 原子唯一性、访问记录、限流和审计；
- 通过 TLS 或等价安全传输保护请求和内容；
- 定义并公开 retention 策略，在留存期内允许 Buyer 用新 nonce 重复下载；
- 处理 NotFound、NotReady、Unauthorized、NonceReused、Gone、RateLimited 等传输/业务错误；
- 处理分块传输、断点重试、超时和大 payload 内存限制；
- 保留 Buyer 到期广播 RefundTx 的原有路径。

SDK 不新增 Store/Repository/HTTP client/server/nonce cache/random source/clock injection/node/broadcaster/retention scheduler。

### 4.3 nonce 和重试语义

- nonce 是请求重放键，不是 Claim ID，也不是一次性下载授权的长期 token；
- 同一 `(ClaimID, Nonce)` 只能成功占用一次，并发请求由数据库唯一键决定唯一胜者；
- 请求或响应超时后，Buyer 生成新 nonce、新 Kind 10 签名重试；不要求 Arbiter 重放旧 nonce 的内容；
- 同一 Claim ID 在 retention 期内可以用多个不同 nonce 合法重复下载；
- 旧 nonce 去重记录至少保留到对应 custody record 删除；不得提前删 nonce 记录使旧签名恢复可重放。

nonce 不能代替 TLS。攻击者如能在 Buyer 发送前窃取完整有效 Kind 10，仍可能抢先占用 nonce。生产传输必须同时提供机密性、完整性和 Arbiter endpoint 身份认证。

## 5. 明确不能怎么做

- 不做 Buyer → Arbiter 关池、快速退款、强制 close、Buyer+Arbiter 合签关池交易或 Seller challenge window。
- 不用“Arbiter 当前没查到 Seller Claim”作为帮 Buyer 花费池输出的证据。
- 不修改 Kind 8/9 形状、字段、签名域、费用公式或交易 candidate。
- 不复用 Kind 6 `ContentDelivery`。Kind 6 是 Seller 直连交付且 Buyer 验收后会进入 005；008 是 Arbiter 托管取件且绝不产生 005。
- 不调用现有 `buyer.AcceptDelivery` 完成 008；必须有不签付款交易的独立验收入口。
- 不把 Claim ID 当作 bearer token。只提交 Claim ID 或只知道 URL 的请求不得下载内容。
- 不在 Kind 10 重复 BuyerPubKey、RefundTemplateTxID、PaymentAuthorizationHash、OpeningProof、TermsCBOR 或 ClaimCBOR。Arbiter 从 Claim ID 对应的已存 Claim 恢复 Buyer key。
- 不用时间戳、自增 ID、全零、短 nonce 或可预测 PRNG 产生 retrieval nonce。
- 不让 SDK 自己生成 nonce、保存 nonce、读数据库、查找 Claim 或记录下载次数。
- 不在 Kind 11 重复 payload 或拆出第二份 Receipt。返回已保存 exact Kind 8/9，payload 只在 Kind 8 中出现一次。
- 不重新编码存储的 Kind 8/9 后声称是 exact 证据；Kind 11 嵌入的必须是持久化的 canonical raw bytes。
- 不只验 Receipt 签名就返回 payload；Seller Claim、Buyer terms、payload hash 和 Arbiter transaction signature 也必须完整验证。
- 不因为取件时 deadline/refund 已过而拒绝一份当初已合法签署且仍在 retention 期内的托管记录。
- 不在 Kind 11 内宣称 Seller 仲裁交易已广播、已上链或已最终结算；它只证明 exact Kind 9 已由 Arbiter 签署并持久化。
- 不把 nonce 当作加密、不用协议签名代替 TLS，不在日志中记录原始 payload、私钥或可直接重放的完整请求。
- 不编码“拒绝响应”为结构合法的 Kind 11；Kind 11 只表达成功取回。失败走应用错误通道。
- 不修改 `spec/v1/**`、`spec/v3/**`、`vendor/**`、MultisigPool module cache 或历史文档来伪造当前协议一致。

## 6. 特殊情况与固定处理

| 特殊情况 | 必须处理方式 |
|---|---|
| Claim ID 查不到 | 返回应用层 `NotFound`；不泄露其他 Claim、Buyer/Seller 或 payload 信息，不转为关池请求。 |
| 只有 Kind 8，Kind 9 未持久化 | 返回 `NotReady`；不提前释放 payload。Buyer 可以稍后用新 nonce 重试。 |
| Kind 8/9 存储字节损坏或非 canonical | 失败关闭，隔离记录并报警；不重编码、不猜测修复、不返回部分 payload。 |
| Receipt Claim ID 与 Kind 8 Claim ID 不同 | 持久化冲突/攻击，立即拒绝并报警。 |
| Kind 10 Claim ID 与存储 Claim 不同 | 拒绝为 invalid evidence；不按其他字段模糊查找。 |
| Buyer 签名不属于 Claim 中的 Buyer key | 返回统一 `Unauthorized`；不说明 Claim 是否存在或哪个字段失败。 |
| nonce 非 32 字节或全零 | strict decoder/validator 拒绝；不进入存储查询。 |
| `(ClaimID, Nonce)` 已使用 | 返回 `NonceReused`；Buyer 生成新 nonce 重新签名。 |
| 两个相同 nonce 请求并发 | 数据库唯一键/CAS 只允许一个成功，另一个返回 `NonceReused`。 |
| Kind 11 发送超时或 Buyer 未收完 | Buyer 不复用旧 nonce，使用新 nonce 和新 Kind 10 重试；Arbiter 返回同一份已保存 exact Kind 8/9。 |
| 同 Claim ID 需要多次下载 | retention 期内允许，每次必须使用新 nonce 和新 Buyer 签名。 |
| 取件时 Quote/deadline/refund 已过期 | 不以当前时间拒绝已签署的托管证据；只要记录仍在 retention 期就正常验收。 |
| Arbiter retention 已结束且内容已安全删除 | 返回 `Gone`；不从 Seller 即时代理、不返回空 payload、不触发关池。retention 策略由产品对 Buyer/Seller 提前公开。 |
| Seller 从未提交 007 | Buyer 无内容可从 Arbiter 取回；继续尝试直连 Seller，或等 RefundTx 到期。 |
| Seller 已提交 Kind 8 但仲裁被拒绝 | 不产生 Kind 11；Buyer 不获得未完成托管交付的 payload。 |
| Seller 没有完成合并/广播 | 不影响已进入 `Retrievable` 的记录；Kind 11 不声称 Seller 已获得链上结算。 |
| Arbiter 公钥匹配但 endpoint 不可达 | SDK 无法处理网络故障；Buyer 应用重试路由或等网络恢复，不降级到无鉴权下载。 |
| 三方均无法联网 | 协议无法越过完全断网工作；等待任一必要连接恢复。 |
| payload 任一项数量/顺序/hash/大小错误 | 整批拒绝，不返回前缀、不尝试补齐、不产生已验证结果。 |
| Buyer 本地 expected ClaimCBOR 与返回 ClaimCBOR 不同 | 即使其他签名看似有效也拒绝；不靠 hash-only 比对继续。 |
| hash collision 或同 Claim ID 对应不同 exact Claim | 停止自动处理、隔离数据并报警，绝不覆盖原托管记录。 |
| Buyer 内容保存失败 | 不把该批标记为已完成；用新 nonce 重新取回，直到应用自己的原子保存成功。 |
| Buyer 已广播 RefundTx | 取件证据验证仍是时间无关的；是否继续下载由应用和 retention 策略决定，Kind 11 不更改链上事实。 |

Kind 11 只表达成功返回一对已签署托管证据。NotFound/NotReady/Unauthorized/NonceReused/Gone/RateLimited/内部损坏都走应用错误通道。若未来需要可转交验证的已签拒绝回执，必须另设固定 kind/结构，不得在 Kind 11 中加 optional status union。

## 10. 完成定义

只有当代码、规范、wire、golden、集成、demo、中英文当前文档、安全负向矩阵和仓库门禁在同一工作树状态下全部满足第 9 节，才算本次硬切换完成。

以下任一状态都不算完成：

- Kind 10/11 能编解码，但 Buyer workflow 不能独立构造 Claim ID 或验收内容；
- Arbiter 只按 Claim ID 返回内容，没有 Buyer 签名鉴权或 nonce 原子去重；
- Buyer 验 Receipt 但没有验 Seller Claim、payload hash 或 Arbiter transaction signature；
- 008 复用 004/`AcceptDelivery` 并生成第二份 005；
- Kind 11 重复 payload，或用重编码字节冒充 Arbiter 持久化的 exact Kind 8/9；
- 取件时重新应用 deadline/refund 未过期门禁，导致事后恢复无法工作；
- 为了“顺便”增加 Buyer+Arbiter close、挑战期或快速退款；
- 单元测试通过，但 CDDL、wire golden、demo、英文规范或中文 current 仍缺失；
- SDK 新增数据库、HTTP、nonce cache、随机源、retention scheduler 或广播副作用；
- 为了让旧 fixture 通过而保留双 kind/双 shape/optional 回退。

本施工单是一次性最终施工边界，不是分阶段迁移计划。实施时可以按文件依赖顺序开发，但只能以完整 001–008 当前真值一次性交付。
