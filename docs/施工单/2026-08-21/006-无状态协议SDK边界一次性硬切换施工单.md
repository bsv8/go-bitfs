# 无状态协议 SDK 边界一次性硬切换施工单

## 0. 施工性质与唯一目标态

本施工单把 `go-bitfs` 硬切换为一个**无状态、无基础设施副作用的 BitFS v4 协议 SDK**。

SDK 的唯一职责是：

> 给定显式协议输入以及调用方选择的基准状态，严格判断协议结构、密码学证据和交易约束是否合法，并计算下一份协议报文、交易或本地角色结果。SDK 不判断调用方数据库中的“最新状态”，也不替业务决定应结算的目标金额。

应用的唯一职责是：

> 决定数据从哪里来、保存到哪里、何时发送或广播、如何串行化、如何重试、如何授权以及如何从故障中恢复。

本次为尚未上线前的一次性破坏式硬切换，不分阶段实施，不提供双 API，不保留兼容适配层。协议版本继续保持 v4。关联字段从容易误导实施者重复哈希的 `RefundTxHash` 一次性改名为 `RefundTemplateTxID`；Go 字段、wire/CDDL 字段名、文档、demo 和环境变量全部同步改名，不保留旧名 alias 或双 decoder。该改名不改变 32 字节编码值、CBOR 数组位置和签名域。

本施工单取代此前施工单中所有要求 SDK workflow 自动加载、保存、锁定、广播或对账的内容；此前确定的规范交易 TxID 算法和全生命周期关联规则继续有效，但唯一现行名称是 `RefundTemplateTxID`。

实施开始前必须先识别并清理当前工作树中被中断的平台文件锁改造半成品，包括未跟踪的 `process_lock_linux.go`、被删除或改写的 `process_lock_unix.go` / `process_lock_other.go`。不得把这些半成品误当成目标设计继续完善。

## 1. 缘由

当前 Buyer/Seller workflow 同时承担协议计算和应用运行时编排：它们从 Store 加载状态、执行并发租约、调用内容仓库、调用节点 backend、保存新状态，并在部分失败时标记 uncertain/closing 状态。`FileStore`、`FileQuoteStore` 又进一步把文件 schema、快照写入、平台文件锁和崩溃恢复责任带入 SDK。

这些能力没有统一的正确实现：

- 数据库会使用事务、唯一约束、CAS、行锁或数据库原生幂等键，SDK 文件锁反而多余；
- 单机文件、浏览器、移动端、服务端数据库和分布式系统的持久化边界完全不同；
- 广播超时、outbox、重试、链上对账和多租户授权是部署策略，不是 BitFS wire 规则；
- SDK 在签名、保存和广播之间自行安排副作用，会强迫所有调用方接受同一种故障模型；
- 存储钩子使看似协议方法的返回值隐含依赖进程历史，难以离线验证、生成测试向量和复放。

因此，不能继续修补 FileStore 的 Linux/Windows 行为，也不能用新的 Store hook、Lock hook、Transaction hook 替代它。正确方向是彻底移除 SDK 的存储和节点副作用，让应用显式持有本地状态。

## 2. 最终边界

| 属于协议 SDK | 属于调用方应用 |
|---|---|
| v4 报文结构、严格 CBOR 编解码 | 数据库、文件存储、浏览器存储 |
| `RefundTemplateTxID` 派生与一致性校验 | 事务、锁、CAS、唯一约束 |
| 交易构造、规范解析、TxID 计算 | 并发串行化、租约、排队 |
| 使用官方 BSV 私钥类型签名、固定验签、签名合并 | 私钥持久化、备份、轮换和访问控制 |
| 协议序号形状、金额边界、角色和签名证据验证 | “哪个状态最新”、目标结算金额和是否接受旧结果 |
| 给定调用方选择的基准状态计算候选状态 | 网络会话、报文路由、业务 request ID、超时策略 |
| 返回待发送报文和本地角色状态 | 保存结果、权限控制、多租户隔离 |
| 直接读取一次系统 UTC；验证调用方提供的区块高度 | 系统校时、区块高度来源及可信度 |
| 验证调用方提供的内容/seed | 内容仓库、内容交付和落盘 |
| 规范 raw、输出和签名是否彼此一致 | 是否发送、接受或广播某个业务候选 |

### 2.1 必须保留的协议能力

- `spec/v4` 定义的 001–007 报文真值和严格 CBOR 读写；
- `RefundTemplateTxID = canonical RefundTx.TxID().CloneBytes()`，其中 `RefundTx` 是未嵌入角色签名的规范退款模板；不翻转字节，不对 raw 再做一次 SHA-256；
- 固定 MasterSeed 与 MultisigPool v4 交易实现；
- 交易 canonical parse、构造、费用、锁定时间、输出角色和容量检查；
- 报价、内容授权、交付、付款、关闭、退款和仲裁证据验证；
- 给定调用方选择的基准 `PaymentState` 时，验证候选与该输入之间的协议关系；SDK 不声称该输入是业务最新状态；
- 金额编码、容量、输出守恒以及“金额是否与显式签名授权相符”等协议约束；不判断业务最终应该结算多少；
- 固定消息摘要和 sighash 生成、官方 BSV 私钥签名、固定 DER 验签、sighash flag 规范化和角色签名合并；
- 防御性复制和输入不变性，避免调用方在返回后修改 SDK 内部结果；
- 从私钥派生公钥并与协议角色公钥绑定校验。

这些是协议合法性，不属于并发控制，不能随 Store 一起删除。

### 2.2 必须移出 SDK 的能力

- 任何 Store、Repository、Source、Sink 形式的持久化钩子；
- 文件快照、JSON schema、临时文件、rename、fsync、文件锁和平台存储分支；
- mutex、租约、`TryAcquire`、`Release`、进程内或跨进程串行化；
- 自动加载 quote、opening、previous payment、pending request；
- 自动保存 proof、payment、content、pending state；
- 节点 RPC/backend、广播、提交结果接受和链上查询；
- `uncertain`、`closing`、retry、reconcile 等运行状态机；
- HTTP、WebSocket、libp2p、MQ、session、trace ID 和路由实现；
- 数据库事务回调、UnitOfWork、锁注入或“通用持久化 hook”。
- 判断数据库中的最新付款状态、选择目标结算金额、判断某个延迟关闭结果是否仍应接受或广播；
- 私钥文件、助记词、WIF 文本的保存、加密、备份、轮换和恢复。

## 3. 公开 API 最终形态

### 3.1 Workflow 定位

保留 `buyer.Workflow`、`seller.Workflow`、`arbitration.Workflow` 名称，避免调用方自行拼接容易出错的 001–007 步骤，但它们必须变成无状态角色协议编排器：

- 对象中只允许保存角色私钥等不随业务流程演进的运行时配置；持有私钥不等于持有会话状态；
- 不保存 quote、opening、payment、pending、content 或 node backend；
- 每个方法的业务依据全部通过参数显式传入；
- 每个方法只返回计算结果，不加载、不保存、不发送、不广播；
- 调用方负责决定所传基准状态是否为业务最新状态，以及返回结果是否应该接受、保存、发送或广播。

Go 实现的三个构造器统一直接接受项目已经依赖的官方 BSV Go SDK 私钥类型：

```go
import ec "github.com/bsv-blockchain/go-sdk/primitives/ec"

type WorkflowConfig struct {
    PrivateKey *ec.PrivateKey
}
```

不得保留 `pool.Signer`、消息 signer callback、远程签名 callback 或可替换 verifier。Workflow 从私钥派生压缩公钥、生成规范摘要并签名；所有验签走 SDK 固定实现。不需要签名的底层 Build/Read/Verify 函数继续保持纯函数，不得为了统一形式强迫纯验证函数经过 Workflow。

TypeScript 协同实现使用 `@bsv/sdk` 的原生 `PrivateKey`。所谓“统一私钥类型”是各语言使用对应官方 BSV SDK 的原生私钥对象，不是把 Go 对象、TS 对象、WIF 或 32 字节私钥加入 wire 报文。

### 3.2 显式输入与复合输出

角色方法必须把 wire 报文和调用方需要保存的本地状态区分命名。建议结果形态如下，最终命名可以按现有包风格调整，但语义不得回退：

```go
type PoolOpeningPreparation struct {
    Request *pool.RefundPresignRequest // 发送给 Seller 的 wire 报文
    State   *BuyerOpeningState         // Buyer 自己保存，不上网
}

type BuyerOpeningState struct {
    RefundTemplateTxID pool.RefundTemplateTxID
    Request      *pool.RefundPresignRequest
    FundingTx    []byte
}

type RefundPresignAcceptance struct {
    Reference      pool.Reference
    Opening        *pool.OpeningProof
    InitialPayment *pool.PaymentState
}

type SellerPresignResult struct {
    Response *pool.RefundPresignResponse // wire 报文
    Opening  *pool.OpeningProof           // Seller 本地保存的预签证据
}
```

原则如下：

- 0201 返回 request 与 Buyer 私有状态；应用先保存私有状态，再发送 request；
- 0202 Seller 返回 response 与本地 presign proof；应用先保存 proof，再发送 response；
- Buyer 接收 0202 时，应用用 `RefundTemplateTxID` 加载 `BuyerOpeningState` 并显式传入 SDK；
- 0204 由调用方把已验证 `OpeningProof` 显式传入构造函数，不由 SDK 按 txid 加载；
- 0205 Seller 由调用方加载 presign proof，与 delivery 一并传入 SDK；
- 后续 003–007 同样显式传入 quote、opening、previous payment、authorization 和本地阶段状态。

### 3.3 内容与付款之间的本地状态

现有 `PendingRequest` 是并发租约，不属于协议 SDK，必须删除。Seller 在生成 004 后仍需要记住“这次交付允许的付款增量”，应改为没有锁语义的本地角色结果，例如：

```go
type ContentDeliveryState struct {
    RefundTemplateTxID     pool.RefundTemplateTxID
    ContentRequestHash     pool.Hash32
    BasePaymentSequence    uint32
    BaseSellerAmountSat    uint64
    ExpectedSellerAmountSat uint64
}
```

SDK 返回该值，调用方自行保存并在接收 005 时重新传入。该类型只表达验证 005 所需的协议上下文，不提供 owner、lease、acquire、held、release 或 expiry 等并发概念。

### 3.4 节点提交拆分

所有当前名为 `Submit...` 或内部自动调用 backend 的方法必须改成 Build/Verify/Accept/Complete 语义，只返回：

- 待广播或待提交的规范 raw transaction；
- SDK 从该交易解析出的 `PaymentState`；
- 规范 txid；
- 调用方下一步需要保存的本地状态。

SDK 不把“构造并验证成功”命名成“节点已接受”。只有调用方的节点适配器可以声明广播/接受结果。

### 3.5 时间、高度和内容输入

- 所有需要当前时间的公开 API 直接在一次操作开始时读取一次 `time.Now().UTC()`，该次操作的所有时间判断复用同一值；
- 公共 API 不接收 `now time.Time`，不提供 `...At` 变体，也不注入 `Clock`、`NowFunc` 或可替换全局时钟；
- 包内可以用不导出的、显式接收时间的纯 helper 覆盖边界测试，但它不能成为公共 API；
- 需要当前区块高度的退款验证由调用方显式传入高度；SDK 不查询节点，也不把系统时间换算成区块高度；
- Seller 交付内容时，调用方显式传入 seed/block bytes；
- Buyer 验证内容时，调用方显式传入验证所需 seed 和收到的 payload；
- SDK 验证这些字节是否匹配报价和 MasterSeed 证明，但不负责读取或保存它们。

系统时钟失准属于运行环境问题。SDK 正常返回“尚未生效”或“已经过期”等协议错误，不负责 NTP、校时、可信时间证明或审计时钟。

### 3.6 私钥、签名与固定验签

- 私钥只进入 Workflow/签名函数的运行时参数，绝不进入 CBOR、wire、local result、错误文本或日志；
- Go 消息签名固定为 `SHA-256(canonical CBOR)` 后调用 `(*ec.PrivateKey).Sign(digest)`，结果必须是 low-S DER；
- 交易签名固定使用 MultisigPool v4 指定 sighash，不能把 sighash 再当普通消息多哈希一次；
- 收到签名后必须由 SDK 固定解析公钥和 DER 并验证，不接受调用方 verifier；
- Go/TypeScript 必须共享固定向量。TS `PrivateKey.sign(message)` 自己执行消息 SHA-256，不能机械地对已经算好的 digest 再调用它造成双哈希；交易签名应走 TS SDK 与固定 sighash 语义匹配的交易签名路径；
- 构造器拒绝 nil 私钥；Workflow 使用派生公钥验证角色归属，调用方不能同时传一个可冲突的“自称公钥”。

### 3.7 立即关闭与业务状态边界

`CompleteImmediateClose` 的承诺仅是：返回值是指定 opening 下密码学、编码和交易结构均合法的最终关闭交易。它不承诺该交易对应调用方当前 pending 请求，不承诺它基于数据库最新状态，也不承诺业务应当广播。

- `BuildImmediateClose` 可以接收调用方选择的基准状态和目标金额，用于构造候选；“选择的是不是最新状态、目标金额是否符合业务”由调用方决定；
- `SignImmediateClose` 固定验证 opening、候选结构、Buyer 角色签名和协议金额边界，但不读取或推断 Seller 数据库最新金额；
- `CompleteImmediateClose(opening, sellerResult)` 不新增 `latest` 或 session 参数，不执行业务新旧判断；
- 若应用需要把响应与某次 pending 请求精确对应，应在应用数据库中保存业务 request ID 和原候选。SDK 可以保留“完整交易去签名后是否等于给定 unsigned candidate”的纯比较 helper，但不得把它变成隐式会话状态或强制业务策略；
- `RefundTemplateTxID` 只标识资金池，不标识同一资金池内的某次关闭尝试。

## 4. 一次性实施顺序

这是一个原子迭代，不允许把任何中间态合并到主分支。施工顺序只用于降低实现风险，不表示分阶段发布。

1. 先冻结全部 001–007 CBOR 编码 bytes、签名域和 MultisigPool 交易向量；字段标识符允许改名，但编码 bytes 必须逐字节不变。
2. 全仓一次性把 `RefundTxHash` 改为 `RefundTemplateTxID`，包括 Go、CDDL、文档、demo、fixture 字段名和环境变量；不保留旧名。
3. 删除 `Signer` 和所有 signer/verifier callback，Workflow 改为直接接收官方 BSV Go SDK `*ec.PrivateKey`，固定摘要、签名和验签路径。
4. 收敛时间 API：公开方法删除 `now` 参数和 `...At` 变体，操作内只读取一次 UTC；区块高度继续由调用方提供。
5. 删除文件锁半成品和所有具体 Store/Node adapter，清理只服务于基础设施的类型和错误。
6. 定义无状态角色方法所需的显式 input/result/local-state 类型，并把“base/candidate”与业务“latest/accepted”措辞区分开。
7. 重写 Buyer/Seller/Arbitration workflow：移除读取、保存、租约、内容 source/sink、节点提交和运行时标记；立即关闭不判断业务最新状态或目标金额。
8. 重写 package/integration tests，使调用方选择的基准状态由测试显式持有和传递，并增加固定验签、UTC 和跨语言签名向量。
9. 修改 demo：让 demo 作为调用方演示保存和恢复本地状态，不能把 demo checkpoint 再包装成 SDK Store。
10. 更新中英文 SDK 文档、完整购买文档和生成 API 翻译；删除旧边界真值。
11. 完成全仓静态搜索、Linux/Windows 编译、测试、race、vet 和 wire fixture 比对后，才允许整体合并。

## 6. 明确不能怎么做

1. 不保留 `FileStore`、`FileQuoteStore`、`MemoryStore` 的 alias、deprecated wrapper、子包迁移版或 build-tag 版本。
2. 不把 Store 接口从 `pool` 移到 `buyer`/`seller` 后继续注入；换包不等于移出 SDK。
3. 不新增 `Locker`、`Transaction`、`UnitOfWork`、`RepositoryFactory`、`StateCallback` 等更抽象的基础设施 hook。
4. 不在 Workflow 内使用全局 map、mutex、channel、goroutine、singleflight 或 cache 偷偷恢复并发控制。
5. 不用 transport session、HTTP request ID、连接顺序或数据库 ID 替代协议中的 `RefundTemplateTxID`；应用可以另用业务 request ID 管理同一资金池内的多次尝试，但不能把它冒充协议 ID。
6. 不让调用方重复传入可从已验证证据唯一派生的协议字段，并把字段冲突交给业务层决定。
7. 不为了无状态而删除固定 sequence 形状、金额编码/容量/守恒、签名角色、显式证据关系和 opening ownership 验证；也不得反向要求 SDK 判断数据库最新状态、业务目标金额或是否接受旧候选。
8. 不在 SDK 内发送网络报文、广播交易、读取节点高度、读取内容或写入已验证内容。
9. 不把“返回了 raw transaction”命名为“已提交”“已接受”或“已上链”。
10. 不因 Go API 破坏性调整增加 v5；也不借边界改造改变 v4 wire bytes。
11. 不加入仅 Linux 可编译的 syscall；Linux 和 Windows 必须使用同一纯协议实现。AIX/Solaris 不在支持范围，不需要专项兼容或文档承诺。
12. 不分两次合并“先删除 Store、以后再改 workflow”；没有最终显式输入输出的中间态不可交付。
13. 不保留 `Signer`、`QuoteTermsSigner`、`ContentTermsSigner`、任何 `SignatureVerifier` 或“默认固定验签但允许覆盖”的选项。
14. 不在公共 API 暴露 `now time.Time`、`...At`、`Clock`、`NowFunc` 或可修改的包级时钟变量。
15. 不接收原始私钥 `[]byte`、hex/WIF 字符串作为核心 Workflow 配置；调用方先用官方 BSV SDK 解析为原生 `PrivateKey`。
16. 不把私钥、公钥派生中间值或私钥序列化结果写入 wire、local result、日志、panic 或错误信息。
17. 不保留 `RefundTxHash` 的字段、函数、CDDL、环境变量、deprecated alias 或兼容 decoder。

## 7. 特殊情况与调用方处理规则

### 7.1 重复、并发或乱序报文

- 调用方按 `RefundTemplateTxID` 路由到资金池，并用自己的业务 request ID 区分同池多次尝试；SDK 不加锁。
- 后续报文到达但本地状态不存在时，调用方可延迟、重试、死信或拒绝；SDK 不猜测 session。
- 调用方把找到的本地状态和报文一起传入 SDK；SDK 必须重新派生 `RefundTemplateTxID` 并拒绝错配。
- 如果调用方并发调用两次，SDK 可以返回两份各自合法的计算结果；去重和唯一副作用由调用方保证。

### 7.2 签名成功但应用保存失败

- SDK 直接使用 Workflow 持有的官方 BSV 私钥签名，但不承诺签名与应用保存构成 exactly-once 事务。
- 应用应在对外发送前保存第一次成功结果，重试时优先重放已保存结果。
- 如果没有保存成功，是否重新执行完整操作由应用的审计和幂等策略决定，不由 SDK 创建隐藏缓存。
- 无论重试多少次，`RefundTemplateTxID` 仍必须从规范未嵌入角色签名的 RefundTx 模板 TxID 派生。

### 7.3 保存成功但发送失败

- 应用重发已保存的同一 wire bytes，不重新构造业务字段。
- 对端仍以 `RefundTemplateTxID` 和完整证据验证，不依赖连接是否相同。

### 7.4 广播超时或节点结果不确定

- 应用先持久化待广播 raw 和 canonical txid，再调用自己的节点适配器。
- 超时后由应用按 txid/outpoint 查询节点或链状态并对账。
- SDK 只提供 raw 验证和 canonical txid 计算，不保存 uncertain 标记，也不决定是否重播。

### 7.5 基准状态过期或发生竞争

- SDK 只验证候选是否与本次显式传入的 base state、授权和 opening 在协议上相容，不判断 base 是否为调用方数据库中的最新记录。
- 如果业务发现 base 已过期、目标金额变化或响应对应旧 pending 请求，由调用方重新加载、比较并决定重新计算、拒绝、接受或转仲裁。
- `CompleteImmediateClose` 验证通过只表示最终交易协议合法，不能作为“业务最新”或“应该广播”的证明。
- SDK 不自动 reload，也不把业务 stale state 解释为协议错误或数据库冲突。

### 7.6 崩溃发生在多步业务之间

- 应用使用自己的事务、状态机、inbox/outbox 或补偿流程。
- SDK 每一步都应能从显式输入重新验证，不依赖内存历史。
- 不要求多个跨网络步骤处于同一数据库事务；应用必须保存足以恢复下一步的本地角色状态。

### 7.7 时间、区块高度或链重组

- SDK 在每次相关操作开始时读取一次系统 UTC 并复用于该操作；调用方只提供其认可的当前区块高度。
- 高度来源失败时，调用方不得伪造 0 继续执行退款；应延迟或切换可信节点。
- 系统 UTC 失准时 SDK 可能正常返回过期/未到期错误；调用方负责主机校时和运行环境监控。
- 链重组和确认策略由调用方处理，SDK 不缓存链状态。

### 7.8 内容读取或保存失败

- Seller 在调用 SDK 前读取 seed/block；读取失败时不生成 004。
- Buyer 先让 SDK 验证 payload，再自行保存；保存失败时不得声称业务已完成，可重用同一验证结果或重新验证。
- SDK 返回内容字节不等于已经交付到应用最终存储。

### 7.9 多租户与权限

- `RefundTemplateTxID` 是资金池路由 ID，不是授权令牌，也不是单次业务请求 ID。
- 调用方先做租户/账户授权，再加载证据；SDK继续校验由私钥派生的公钥与 opening/quote 的协议角色绑定。
- 不能因为数据库按 `RefundTemplateTxID` 找到了记录，就跳过 SDK 的角色和证据验证。

### 7.10 上一版 v4 数据和未上线状态

- 项目未上线，不提供旧 Store snapshot 迁移器，也不接受旧 wire shape。
- 开发环境旧文件状态直接删除并从 0201 重建。
- 版本继续是 v4，不能用“兼容旧 v4”为理由保留双字段、双 decoder 或 Store shim。

## 8. 测试重构原则

### 8.1 必须删除的测试类型

- FileStore/FileQuoteStore restart、schema、atomic rename、文件权限测试；
- process lock、跨进程、跨 Store 实例并发测试；
- MemoryStore mutex、lease、TryAcquire/Release 测试；
- fake backend 广播接受、超时、uncertain/reconcile 测试；
- workflow 自动加载/保存/内容 sink/source 的 mock 交互测试。

### 8.2 必须保留或新增的测试类型

- 001–007 wire fixture 逐字节稳定；
- 每个角色方法只凭显式输入即可执行，新的 Workflow 对象不含历史状态；
- 同一显式输入在不读取当前时间的纯 Build/Verify 路径产生确定结果；
- nil/错误角色私钥必须拒绝；固定验签必须拒绝错误公钥、错误签名、畸形 DER，不能由回调放行；
- `RefundTemplateTxID` 与 request/response/opening/delivery/payment/arbitration 的交叉校验；
- wrong tenant key、wrong opening、wrong previous、wrong authorization、wrong content 必须拒绝；
- skipped/非法 sequence、金额编码/容量/签名授权不一致、错误 outpoint 必须拒绝；不得用测试要求 SDK 识别数据库最新记录或替业务决定立即关闭金额；
- Buyer/Seller/Arbiter 合并后的交易脚本和 txid 与固定 fixture 一致；
- Go/TypeScript 共享消息签名向量证明规范 CBOR 只做一次 SHA-256；交易签名向量证明 sighash 没有被普通消息 API 二次哈希；
- 公开 API 无 `now`/`...At`；时间相关测试使用包内私有 helper 或围绕当前 UTC 构造不抖动的边界数据；
- 调用方复制并修改输入或输出切片不能污染其他结果；
- Linux 与 Windows 编译同一套文件，不存在平台锁 build tag。

并发正确性不再作为 SDK 测试目标。可以在文档的应用伪代码中展示按 `RefundTemplateTxID` 建唯一键或事务，但仓库测试不得把某一种数据库并发模型重新固化为 SDK 责任。

## 9. 最终验收清单

## 10. Review 阻断条件

出现以下任一情况即不得验收：

1. Workflow 仍能在调用方不可见的情况下加载或修改状态；
2. 删除 FileStore 后又出现数据库/事务/锁的抽象注入；
3. 方法返回前已经广播交易、发送网络报文或保存内容；
4. 为了无状态化而跳过显式 base/previous 证据关系、`RefundTemplateTxID`、协议金额边界、角色或固定签名验证；
5. demo checkpoint 被包装成公共 SDK Store；
6. wire bytes、CDDL 数组结构/字段类型或交易 fixture 因边界改造发生变化；CDDL 关联字段标签的约定改名除外；
7. 继续用 `Submit`/`Accepted` 命名没有发生的外部副作用；
8. Linux 通过但 Windows 因平台文件或 syscall 无法编译；
9. 中英文文档仍把旧 Store/backend 当作现行 API；
10. 只完成删除，没有提供可完整执行 001–007 的显式 input/result API。
11. 仍保留 `Signer`/Verifier/Clock/`...At` 扩展点，或 Workflow 不直接使用官方 BSV 私钥类型；
12. 仍存在 `RefundTxHash` 旧名、兼容 alias、双字段或双 decoder；
13. `RefundTemplateTxID` 被实现为 `SHA-256(raw RefundTx)`、被再次哈希或被显式翻转字节序；
14. SDK 开始判断数据库最新状态、立即关闭业务目标金额、旧响应是否应接受或交易是否应广播；
15. Go 与 TypeScript 消息签名发生单哈希/双哈希分歧，或交易 sighash 被普通消息签名路径再次哈希；
16. 私钥进入 wire、序列化本地状态、日志或错误信息。

只有代码、测试、demo、规范说明和两种语言文档同时达到本施工单唯一目标态，才算本次硬切换完成。

## 11. 新修复指南（按本轮对齐结论执行）

本节是当前实现到目标态的直接修复路径。它与第 4 节同属一次原子迭代，不代表可以分批发布或保留中间兼容态。

### 11.1 先做全仓符号硬改名

统一映射如下：

| 旧名称 | 唯一目标名称 |
|---|---|
| `RefundTxHash` | `RefundTemplateTxID` |
| `refund_tx_hash` | `refund_template_txid` |
| `refund-tx-hash` | `refund-template-txid` |
| `REFUND_TX_HASH_HEX` | `REFUND_TEMPLATE_TXID_HEX` |
| `DeriveRefundTxHash`/同义 helper | `DeriveRefundTemplateTxID` |

实施要求：

1. 先新增专用 `pool.RefundTemplateTxID [32]byte` 并把所有资金池关联字段切换到该类型；普通 CBOR 内容哈希继续使用各自的 `Hash32`，不能把所有 32 字节值混成 TxID。
2. 派生函数必须 canonical parse `RefundTx`，确认它是协议允许的未嵌入角色签名退款模板，然后返回 `tx.TxID().CloneBytes()`。
3. 同步修改 Go、CBOR struct/array 字段、CDDL 标签、demo JSON/checkpoint、环境变量、测试名、中英文文档和翻译 key。
4. 不改变 CBOR 数组位置和 32 字节值；用改名前冻结的 encoded bytes 做回归。
5. 删除旧符号，不能用 type alias、deprecated wrapper 或 decoder fallback 让旧名继续编译。

### 11.2 把签名入口收敛到官方私钥类型

按以下顺序修复：

1. 删除 `pool.Signer`、测试 signer 实现、`QuoteTermsSigner`、`ContentTermsSigner` 以及所有 `*SignatureVerifier`。
2. Buyer、Seller、Arbitration 的 `WorkflowConfig` 只接收 `*ec.PrivateKey`；构造器立即拒绝 nil，并防御性地确保派生公钥有效。
3. Workflow 不再分别向调用方索取“自己的公钥”；统一从私钥派生 33 字节压缩公钥，并在 opening/quote/authorization 中做角色匹配。
4. 报价和内容消息签名由 SDK 编码 canonical CBOR、执行一次 SHA-256、调用 Go SDK 私钥对 digest 签名，然后立刻用固定 verifier 自校验。
5. 交易签名由 SDK 计算固定 MultisigPool sighash，直接用 Go SDK 私钥签 digest；DER 和 sighash flag 的合并位置保持协议唯一实现。
6. 所有接收路径固定调用 SDK verifier，调用方不能传函数、接口或选项改变验签结果。
7. 清理测试中的 permissive verifier 和 fake signer；改用确定性 fixture 私钥、错误角色私钥、篡改 DER 和错误 payload。

Go 与 TypeScript 的协同不能只看同名方法：

- Go `(*ec.PrivateKey).Sign` 接收已经计算好的摘要；
- TS `PrivateKey.sign(message)` 会对普通消息自行执行 SHA-256；
- 普通消息的共享真值是 `ECDSA(SHA-256(canonicalCBOR))`；
- 交易共享真值是对固定 transaction sighash 签名，TS 不能把 sighash bytes 再交给会自动哈希的普通消息入口。

至少建立一组 Go 生成、TS 验证和一组 TS 生成、Go 验证的普通消息向量，并为 funding/refund/payment/close/arbitration 保留交易签名向量。

### 11.3 收敛系统时间与区块高度 API

公开方法按下列规则机械调整：

| 当前形态 | 目标形态 |
|---|---|
| `AcceptQuote(..., now)` | `AcceptQuote(...)`，内部取一次 UTC |
| `CreateQuote(..., now)` | `CreateQuote(...)`，内部取一次 UTC |
| `BuildContentRequest(..., now)` | 删除 `now`，内部取一次 UTC |
| `BuildContentDelivery(..., now)` | 删除 `now`，内部取一次 UTC |
| `AcceptDelivery(..., now)` | 删除 `now`，内部取一次 UTC |
| `BuildRefundAfterExpiry(..., now)` | 删除 `now`；时间锁内部取 UTC，高度锁读取外部高度 |
| 任意公开 `...At` | 删除，不提供替代 alias |

每个公开操作在入口执行一次：

```go
now := time.Now().UTC()
```

随后把 `now` 传给包内不导出的 helper，不能在一次操作的多个校验点重复读取时钟。删除 `TimeFacts.Now`；如果仍需聚合高度事实，类型中只保留 `BlockHeight`。不得新增 `Clock` 接口或可变包级 `nowFunc`。

### 11.4 修正立即关闭和退款的责任边界

立即关闭目标 API 语义：

```text
BuildImmediateClose(opening, base, targetAmount, blockHeight)
    -> unsigned candidate + Buyer signature

SignImmediateClose(opening, unsigned, buyerSignature, blockHeight)
    -> fully signed close

CompleteImmediateClose(opening, fullySignedClose)
    -> protocol-verified raw/state
```

- `base` 是调用方选择的构造输入，不得命名或描述为 SDK 认可的数据库 latest。
- SDK 校验 target amount 能被协议编码、不溢出、不超过资金池、输出守恒，并验证角色签名；是否符合订单、账本或最新累计金额由业务决定。
- Seller 是否愿意签、Buyer 是否愿意接受、应用是否愿意广播，均在调用 SDK 前后由应用判断。
- `CompleteImmediateClose` 不增加 `latest`、pending state 或 session，也不因为没有原始候选而报协议错误。
- 应用若要严格匹配某次请求，自己保存 request ID 和 unsigned candidate；需要时调用纯 candidate 比较 helper。

退款构造只验证 opening、退款模板、双方签名和锁定条件。SDK 不因为调用方存在某个本地付款状态而拒绝构造；是否与业务已接受状态冲突、是否实际广播由应用决定。

### 11.5 保留协议金额校验，删除业务金额判断

实施者不得把“金额由业务决定”误解成 SDK 完全不检查金额。

必须保留：

- satoshi 类型范围、加减法溢出和资金池容量；
- 固定输出数量、角色输出位置、费用和输出守恒；
- 明确签名授权中写入的金额与候选交易输出是否一致；
- 调用方显式要求从某个 base 构造下一候选时，该候选与该 base 的协议关系。

必须删除或改写：

- “SDK 证明这是数据库最新付款”的断言；
- “SDK 决定 Seller 业务上应该得到多少”的断言；
- `CompleteImmediateClose` 对业务 latest 的强制参数和比较；
- 把延迟响应、并发请求或旧候选一律当作协议畸形；
- 把“协议验证通过”写成“建议广播”或“业务已接受”。
