# 002 · 通用 2-of-3 费用池开池规范

本规范定义买方和卖方建立一条 **通用 2-of-3 费用池** 时交换的首组报文。它只解决一件事：资金真正进入 2-of-3 池输出前，买方先取得卖方对到期退款交易的签名保证。

费用池不是 BitFS 购买凭证，也不是文件会话。开池报文中不得出现 `seed_hash`、报价凭证、文件哈希、文件名、块序号、票据或价格。它们只在后续“验货后支付”报文中绑定到某一次支付状态推进。

业务参与方只有：

- **买方**：出资者，也是初始退款的受益人；
- **卖方**：退款交易的预签者，后续才有获得支付的机会；
- **仲裁者**：2-of-3 锁定脚本中的第三把钥匙。仲裁者不参与正常开池报文。

这里没有“服务端”或“服务端状态”。每一方保存自己收到的交易与签名；数据和签名才是可验证真值，存储只负责保存和按内容索引它们。

## 需求本质与利益关系

买方若先把资金交易广播，使资金进入 2-of-3 输出，再请求卖方签后续交易，卖方可以拒绝签名。此时买方资金可能被锁到到期甚至仲裁，买方承担了不必要的风险。

反过来，卖方在资金交易尚未公开、尚未上链前签一笔到期退款交易，不会损失既有资金：该交易尚无可花费的输入。卖方最多付出一次签名操作，并获得未来得到付款的机会。因此顺序必须是：

```text
买方先取得卖方对到期退款交易的签名
    ↓
买方已具备退款保证，才交出资金交易
    ↓
卖方核验资金交易对应自己签过的退款交易，再提交资金交易
```

这保证：

- 卖方在预签阶段拒绝或不作为，买方只损失时间，资金尚未入池；
- 买方取得卖方签名后，卖方以后不作为也不能使买方资金丢失；
- 卖方只有在资金交易被交付并提交成功后，才知道池中确实已有可供未来支付的资金；
- 初始退款交易不给卖方任何金额。卖方得到的是后续支付机会，不是开池即得的款项。

## 交易与固定术语

| 名称 | 中文含义 | 是否上链 | 谁先持有 |
|---|---|---:|---|
| `FundingTx` | 资金交易。买方出资，并在指定输出创建 2-of-3 费用池。 | 第 7 步才提交 | 买方 |
| `PoolOutpoint` | `FundingTx` 中的池输出：`funding_txid + pool_output_index`。 | `FundingTx` 提交后存在 | 由 `FundingTx` 内容唯一确定 |
| `RefundTx` | 花费该未来池输出、带到期条件的退款交易。 | 开池时不提交 | 买方先构造，卖方后签名 |
| `BuyerRefundSignature` | 买方对 `RefundTx` 的交易签名。 | 不单独上链 | 买方 |
| `SellerRefundSignature` | 卖方对同一 `RefundTx` 的交易签名。 | 不单独上链 | 卖方生成、买方保存 |

池输出锁定脚本固定为 2-of-3 多签，公钥顺序固定为：

```text
[buyer_pubkey, seller_pubkey, arbiter_pubkey]
```

公钥顺序是脚本真值的一部分，不得由实现按字典序重排。仲裁者只因该锁定脚本而出现；开池时不需要仲裁者的签名或确认。

`RefundTx` 的开池初始语义固定为：

- 花费唯一的 `PoolOutpoint`；
- 使用买方和卖方两份交易签名；
- 使用链上到期条件（`nLockTime` 对应的区块高度）；
- 到期后将池中可花费余额退回买方；
- 卖方初始分配为 `0`，不得设置卖方收款输出；
- 矿工费从池金额中扣除，因此买方退款金额等于池输出金额减去该交易矿工费。

本规范不在开池阶段定义后续付款、更新交易、关闭交易或仲裁交易如何重新分配金额。

## 开池报文

全部外层报文和独立子结构均使用 deterministic CBOR。正式数组位置见 [`../spec/v1/settlement.cddl`](../spec/v1/settlement.cddl)。BSV 原始交易、交易签名与锁定脚本都是 `bytes`，不得转换成可变格式的 JSON、hex 文本或数据库 ID 再作为签名真值。

### 1. `PoolRefundPresignRequest`

方向：买方 → 卖方。

它只交付卖方产生退款签名所需材料，**不包含 `FundingTx` 原始字节**。

| 字段 | 中文说明 |
|---|---|
| `version` | 报文版本，当前为 `1`。 |
| `refund_tx` | `RefundTx` 的确定原始交易字节。它的输入已引用未来的 `funding_txid + pool_output_index`，但该 `FundingTx` 尚未交给卖方。 |
| `funding_txid` | 买方本地构造的 `FundingTx` 的交易 ID。必须等于 `refund_tx` 唯一输入的来源交易 ID。 |
| `pool_output_index` | 池输出在 `FundingTx` 中的输出索引。必须等于退款交易输入的来源输出索引；不得假定恒为 `0`。 |
| `pool_output_satoshis` | 池输出金额。交易 wire 输入不携带来源金额，卖方计算 BSV 交易签名摘要时需要它。 |
| `pool_locking_script` | 池输出的精确 2-of-3 锁定脚本。卖方计算签名摘要时需要它；其公钥顺序必须符合本规范。 |
| `buyer_refund_signature` | 买方对 `refund_tx` 的原始交易签名。 |

`funding_txid`、`pool_output_index`、金额和锁定脚本是退款交易输入的来源输出描述。它们不是另一份独立条款；卖方在第 7 步拿到 `FundingTx` 时必须逐项与真实输出比较。

卖方在本步骤的职责是：对所给交易产生自己的交易签名、保存请求中的退款交易和来源输出描述、返回签名。卖方**不做业务验证，也不需要在本步骤验证**退款金额、到期条件、文件购买关系或 `FundingTx`。此时不存在已上链的资金，卖方签名不会使其损失既有利益。

### 2. `PoolRefundPresignResponse`

方向：卖方 → 买方。

| 字段 | 中文说明 |
|---|---|
| `version` | 报文版本，当前为 `1`。 |
| `seller_refund_signature` | 卖方对请求中同一 `refund_tx`、同一来源输出描述产生的原始交易签名。 |

本响应不需要请求 ID。签名本身只能在指定交易、指定输入、指定来源金额与锁定脚本下验证；这就是它与请求的内容绑定。

买方收到响应后必须验证卖方签名，确认它与自己保存的 `refund_tx`、`PoolOutpoint`、来源金额和锁定脚本完全对应。验证成功后，买方必须先把完整开池证明交给调用方保存；然后才可以进入第 3 步。

**买方侧开池成功的定义**：买方已验证并保存卖方的退款交易签名。它不依赖 `FundingTx` 已提交，更不依赖链上确认。

### 3. `PoolFundingTxDelivery`

方向：买方 → 卖方。

| 字段 | 中文说明 |
|---|---|
| `version` | 报文版本，当前为 `1`。 |
| `funding_tx` | 已由买方签好的 `FundingTx` 原始交易字节。 |

这是买方首次把资金交易交给卖方。它不重复附带退款交易、签名、报价或任何 BitFS 业务材料。

旧 gateway 的激活请求另带一份对资金交易字节的应用层 `client_sig`。本规范不保留该字段：`FundingTx` 本身必须已经包含其资金输入所需的链上签名，且卖方会在本步骤把它与自己保存的退款交易逐项对照。额外的报文签名既不增加退款保证，也不应成为另一份可漂移真值。

卖方收到 `funding_tx` 后，以交易内容计算 `funding_txid`，并用它在自己保存的退款交易中查找引用该 ID 的 `PoolOutpoint`。该内容关系完成关联，不需要独立的会话 ID 或数据库 ID。

卖方必须在本步骤验证：

1. `FundingTx` 的交易 ID 等于保存的 `funding_txid`；
2. `FundingTx` 的 `pool_output_index` 存在；
3. 该输出的金额等于保存的 `pool_output_satoshis`；
4. 该输出的锁定脚本逐字节等于保存的 `pool_locking_script`，并确为规定公钥顺序的 2-of-3 脚本；
5. 保存的 `RefundTx` 唯一输入精确花费此输出；
6. 买卖双方对该 `RefundTx` 的签名都能按此来源输出验证。

任一项不成立，卖方不得提交 `FundingTx`。

全部成立后，卖方通过调用方提供的交易提交钩子提交 `FundingTx`。提交钩子成功返回的交易 ID 必须等于 SDK 从 `funding_tx` 原始字节计算的 `funding_txid`；否则视为提交失败。广播节点接受该交易并返回该 ID，即为卖方侧开池成功；本规范不要求等待确认数、订阅链上观察事件或把观察结果回传给买方。

`PoolFundingTxDelivery` 没有必须的卖方响应。卖方提交成功是卖方自己的链提交结果，不是需要作为开池真值重复传输的业务报文。

## 完整时序与双方保存责任

```text
买方                                      卖方
 │ 本地构造 FundingTx（不公开）              │
 │ 本地构造并签 RefundTx                    │
 │                                            │
 │── PoolRefundPresignRequest ──────────────>│
 │                                            │  直接签名并保存退款交易
 │<─ PoolRefundPresignResponse ──────────────│
 │ 验签并保存完整退款证明                     │
 │ 买方侧开池成功                             │
 │                                            │
 │── PoolFundingTxDelivery(FundingTx) ──────>│
 │                                            │  比对已保存退款交易
 │                                            │  提交 FundingTx
 │                                            │  提交成功：卖方侧开池成功
```

| 时点 | 买方必须保存 | 卖方必须保存 |
|---|---|---|
| 卖方预签前 | `FundingTx`、来源输出描述、`RefundTx`、买方签名 | 无 |
| 卖方预签后 | 上述材料加卖方签名，构成可退款的完整证明 | `RefundTx`、来源输出描述、卖方签名 |
| 资金交易交付后 | 完整开池证明 | 上述材料加 `FundingTx` |

## SDK 外部能力钩子

SDK 不直接依赖数据库、文件系统、链节点、钱包 RPC、BSV 交易库或网络传输。凡是需要访问外部世界的动作，都由调用方实现的开池流程钩子完成。SDK 不以函数回调参数散落这些依赖，而是按能力定义 Go 接口；买方和卖方只实现自己实际使用的组合接口。

```go
type PoolOpeningProofStore interface {
    SavePoolOpeningProof(ctx context.Context, proof *PoolOpeningProof) error
    LoadPoolOpeningProofByFundingTxID(
        ctx context.Context,
        fundingTxID []byte,
    ) (*PoolOpeningProof, error)
}

type RefundTxSigner interface {
    SignRefundTx(ctx context.Context, request *PoolRefundPresignRequest) ([]byte, error)
}

type RefundTxSignatureVerifier interface {
    VerifySellerRefundSignature(
        ctx context.Context,
        request *PoolRefundPresignRequest,
        signature []byte,
    ) error
}

type TransactionIDCalculator interface {
    TransactionID(ctx context.Context, rawTx []byte) ([]byte, error)
}

type FundingTxVerifier interface {
    VerifyFundingTx(ctx context.Context, fundingTx []byte, proof *PoolOpeningProof) error
}

type TransactionSubmitter interface {
    SubmitTransaction(ctx context.Context, rawTx []byte) ([]byte, error)
}
```

代码中的 `BuyerPoolOpeningHooks` 组合“保存、卖方退款签名验证、交易 ID 计算”；`SellerPoolOpeningHooks` 组合“保存和读取、卖方退款签名、交易 ID 计算、资金交易验证、交易提交”。因此买方不需要实现广播钩子，卖方也不需要实现买方验签钩子。

`PoolOpeningProof` 是证明数据，不是数据库实体。它至少包含本规范“双方保存责任”表中该阶段已有的原始交易、来源输出描述和交易签名；卖方在收到 `FundingTx` 前保存的是尚未附带 `FundingTx` 的待激活证明，收到后保存完整证明。

调用方可以把钩子实现为 SQLite、文件、硬件钱包关联存储、浏览器存储、链节点 RPC、钱包广播 API 或测试中的内存实现。SDK 只规定以下硬顺序：

1. 买方验到卖方签名后，必须先成功调用 `SavePoolOpeningProof`，才向卖方发送 `PoolFundingTxDelivery`；
2. 卖方签出退款交易后，必须先成功调用 `SavePoolOpeningProof`，才返回 `PoolRefundPresignResponse`；
3. 卖方收到 `FundingTx` 后，必须先用 `TransactionID` 从原始交易计算 `funding_txid`，再通过 `LoadPoolOpeningProofByFundingTxID` 取回先前材料并完成第 7 步验证；
4. 验证成功后，卖方先保存含 `FundingTx` 的完整证明，再调用 `SubmitTransaction`；
5. `SubmitTransaction` 返回的 ID 必须等于 `TransactionID(FundingTx)`。

若提交成功后的调用方进程崩溃，可以按同一份 `FundingTx` 重试提交或保存；因为交易 ID 由原始交易内容确定，重复提交不会制造另一笔资金交易。任何调用方若无法可靠实现这些钩子，就不应执行对应的开池流程步骤。

### SDK 流程 API

交易构造由买方钱包/交易实现完成；SDK 不自行创建 UTXO、私钥或链连接。构造完成后，SDK 提供以下流程入口：

```go
// 卖方：直接签名并先保存待激活证明，成功后才返回响应。
response, err := settlement.SellerPresignRefund(ctx, request, sellerHooks)

// 买方：验证卖方签名，核对 FundingTx 的 txid，先保存完整证明。
buyerProof, err := settlement.BuyerAcceptRefundPresign(
    ctx, request, response, fundingTx, buyerHooks,
)

// 买方将 NewPoolFundingTxDelivery(fundingTx) 通过任意 transport 发给卖方。

// 卖方：由 FundingTx 内容找到已保存证明，验证、保存、提交。
sellerProof, err := settlement.SellerAcceptFundingTx(
    ctx, settlement.NewPoolFundingTxDelivery(fundingTx), sellerHooks,
)
```

`SellerPresignRefund` 在签名前只做 CBOR 字段完整性检查，不调用 `VerifyFundingTx`；`SellerAcceptFundingTx` 才调用它。这样 SDK 的实际控制流与本规范的利益关系保持一致。

## 开池证明与后续引用

双方可将上述完整材料编码为 deterministic CBOR 的 `PoolOpeningProof`，并计算：

```text
PoolOpeningProofHash = SHA256(PoolOpeningProofCBOR)
```

这个哈希用于本地去重、审计和高效引用；它不是数据库生成的池 ID。链上池的天然内容引用是：

```text
PoolOutpoint = funding_txid + pool_output_index
```

后续付款报文可以引用 `PoolOutpoint` 或 `PoolOpeningProofHash`，但接收方必须用自己保存的开池证明验证该引用。后续付款才会把池状态推进与 BitFS 的购买凭证、内容哈希和应付金额绑定；本规范不提前引入这些字段。

## 非目标与明确禁止

- 不把报价、`seed_hash`、文件、ticket 或支付金额写入开池报文；
- 不以数据库会话 ID、服务端查询结果或“当前池状态”作为开池真值；
- 不在卖方返回退款签名前公开或提交 `FundingTx`；
- 不要求卖方在预签阶段做业务验证；
- 不给卖方初始付款；
- 不把链上确认等待、监听或重试机制定义为开池报文的一部分；
- 不要求在后续报文反复携带 `FundingTx`、退款交易或已有签名。

## 与旧 gateway 开池流程的关系

旧 gateway 的 `PoolPresign` 后 `PoolActivate` 的两段顺序可作为本规范的机制来源：先取得对退款交易的签名，再交付资金交易。旧实现中的 `server`、`PoolState`、数据库会话语义不是本规范的一部分；在本规范中，它们分别应理解为卖方的本地实现细节，而不是额外信任主体或业务真值。
