# 005 · 累计支付规范

本规范定义买方验收 004 后，向卖方交付一笔可覆盖前一状态的部分签名 BSV 交易。该交易由 BSV 非最终交易池保存和覆盖；它不是每次付款都立即上链的交易，也不是应用层另造的一张金额单据。

## 交易拓扑

一个费用池只有一个由 002 `FundingTx` 创建的 2-of-3 基础资金输出。后续所有状态均花费该**同一个输出**：

```text
基础资金输出
  └─ 初始远期花费状态：nSequence = 1，卖方金额 = 0，买方金额 = 全额
       └─ 累计支付更新：同一输入，nSequence 递增，卖方累计金额增加
       └─ 主动关闭：同一输入，nSequence = 0xffffffff，立即最终化
```

初始远期花费状态的交易 ID 是 002 定义的稳定 `SpendTxID`，仅用作该状态序列的锚点；每一笔更新交易都会有新的交易 ID，后者不得替代 `SpendTxID` 作为 003 的费用池引用。

## BSV 非最终交易池要求

正常累计支付交易必须满足：

1. 输入花费 002 费用池证明中的同一基础资金输出；不得创建 UTXO 推进链。
2. `nLockTime` 保持费用池约定的到期高度或时间；至少一个输入的 `nSequence` 不得为最终值。
3. 更新交易的 `nSequence` 必须大于该池节点已保存最新状态的 `nSequence`，且小于 `0xffffffff`。允许跳号；不得复用或倒退。
4. 输出只分配给约定的卖方和买方找零地址；卖方累计金额不得倒退，买方找零必须等于池金额减去卖方累计金额和交易费。
5. 买方必须以 `SIGHASH_ALL|FORKID` 对该交易签名。交易原始字节及其中的买方签名共同构成付款授权真值。

卖方必须通过支持 BSV 非最终交易池的交易提交钩子提交该交易。节点接受后，以更高 `nSequence` 覆盖旧的非最终状态；到期后，节点将其重新校验并送入可打包状态。SDK 不得把普通交易广播成功误当作非最终更新已被接受。

主动关闭不是普通累计支付：它将同一输入的 `nSequence` 与 `nLockTime` 都设为 `0xffffffff`，并重新取得所需签名，使交易立刻最终化。`0xffffffff` 是关闭专用值，不是可用于内容付款的支付序号。

## 005 CBOR 报文

005 的外层 CBOR 只是传输与关联容器；付款金额、序号、输出和买方授权均以其中的原始 BSV 交易为准，不得在 CBOR 中另建一套可独立解释的金额或签名字段。

```text
CumulativePaymentUpdateCBOR = deterministic CBOR([
  version,
  content_request_terms_hash,
  partial_spend_tx_raw
])
```

数组位置固定为：

| 位置 | 字段 | 中文说明 |
|---:|---|---|
| 0 | `version` | 报文版本，当前为 `1`。 |
| 1 | `content_request_terms_hash` | 已完成的 003 `ContentRequestTermsCBOR` 的 SHA-256，32 字节。仅用于将本次付款与内容请求关联。 |
| 2 | `partial_spend_tx_raw` | 原始 BSV 花费交易字节。它花费费用池基础输出，已经包含买方签名，尚可缺少卖方或仲裁者签名。 |

本报文没有独立的 `BuyerSignature` 或 `TermsSignature`：买方对 `partial_spend_tx_raw` 的 BSV 输入签名就是本次付款的签名。实现必须解析交易并验证该签名，而不是只验证 CBOR 哈希。

## 付款前置校验

买方签出 005 前必须验证：

| 信息 | 实施要求 |
|---|---|
| 费用池 | `partial_spend_tx_raw` 的输入、2-of-3 锁定脚本、公钥及到期条件与 002 开池证明一致。 |
| 前一状态 | 003 的 `BasePaymentSequence` 是买方所知该池最新状态；新交易的 `nSequence` 大于它。 |
| 请求与交付 | 验证 003 `ContentRequestTermsHash`、相应 004 的卖方签名与内容哈希。 |
| 价格 | 由 001 报价和内容类型推导；尾块遵循报价约定的计算及卖方让利规则。 |
| 累计金额 | `SellerAmountAfter = SellerAmountBefore + 本次确认金额`；买方输出为余额减交易费。 |

买方将该 CBOR 报文交给卖方。005 不定义卖方返回“金额确认”报文；卖方对交易的签名及非最终交易池接受结果，才表示付款状态已推进。

## 卖方的单请求门闩

卖方在交付 004 前必须原子地检查并保存以下临时状态：

```text
费用池锚点 SpendTxID + 当前 BasePaymentSequence
  -> 003 条款哈希 + 已验证内容对应的 ExpectedSellerAmountSat
```

同一费用池在任一时刻至多允许一笔进行中的内容请求。卖方只有在收到相应 005、验证无误并确认非最终交易池接受了更高 `nSequence` 后，才可清除该门闩并接受下一笔请求。已存在门闩、请求序号已过时或重复时，卖方必须拒绝新的 003。

卖方验收 005 时不得只检查卖方金额“不下降”。门闩中的
`ExpectedSellerAmountSat` 是在交付前由已验证的 001 报价、003 请求和 004 内容计算并持久化的价格承诺；交易必须满足：

```text
SellerAmountAfter = PreviousSellerAmount + ExpectedSellerAmountSat
```

否则即使买方签名有效，也必须拒绝并且不得提交给非最终交易池。

这是卖方防止同一余额被多次承诺交付的运行保护状态，不是付款真值，也不替代交易和签名。实现必须经存储钩子持久化它，以避免重启后重复交付；其丢失不会改变任何已签交易的真值。

需要并行购买内容时，买方应使用多个费用池。块可以任意顺序购买，但同一池的请求必须串行完成。

## 到期、关闭与仲裁

| 情形 | 结果 |
|---|---|
| 卖方不提交任何累计付款状态 | 买方在到期后提交 002 的初始远期退款状态，获得全额退款。 |
| 卖方提交最新累计付款状态 | 到期后由该状态结算：卖方取得累计金额，买方取得其交易输出中的找零。 |
| 买卖双方协商关闭 | 构造 `nSequence = nLockTime = 0xffffffff` 的最终交易并立即提交。 |
| 卖方无法正常提交买方已签状态 | 卖方可按 007 提交完整证据，请仲裁者补足签名。 |

买方不得因为卖方未提交状态而向仲裁者发起关闭或主张金额。卖方不得自行提高卖方金额，或把已失效、未被节点接受的付款状态作为有效付款依据。
